# My Tasker — принятые решения и этапы разработки

> Версия 1.0 от 2026-09-30. Документ **главный**: где он расходится с `01_ARCHITECTURE_PLAN.md`, `02_DESIGN_SYSTEM.md` или `03_CREATIVE_IDEAS.md`, действует он.
> Секреты не записываются никуда, кроме переменных окружения на сервере и GitHub Secrets.

## 1. Решения по ответам заказчика

### 1.1 Противоречия между архитектурой и дизайном

| # | Вопрос | Решение |
|---|---|---|
| 1 | Корзина | Удалённое лежит в **корзине 30 дней**, потом удаляется физически. Экран «Корзина» есть. Устройство, которое было офлайн дольше 30 дней, делает полную пересинхронизацию. |
| 2 | Конфликты синхронизации | **Только автоматика**: слияние по полям + «последняя правка побеждает» + журнал конфликтов с кнопкой «вернуть моё». Экрана ручного выбора версии нет. |
| 3 | Кнопка «Выключить» сервер | **Убрана полностью.** Приложение серверами не управляет, только наблюдает. Остаётся «Проверить сейчас». |
| 4 | Ключ polza.ai | **Только на сервере** (`POLZA_API_KEY` в env). В интерфейсе поля для ключа нет. |
| 5 | Статусы и приоритеты задач | 5 статусов: Входящие, К выполнению, В работе, Выполнено, Отменено. **Приоритеты P1–P5** (P1 — самый высокий) + «без приоритета». |
| 6 | Формула цели накопления | **Настраивает сам пользователь**: в цели выбирает, какие счета, долги и ожидаемые поступления входят в «Есть» и с каким знаком — как сейчас в Excel. |
| 7 | Долг Ромы | Пользователь **вносит данные сам**. Импорт Excel не делаем. |
| 8 | Функции без экрана | **Экраны добавляются** (список в 1.4). |

### 1.2 Ответы на топ-10 вопросов

| # | Тема | Ответ | Что это значит для продукта |
|---|---|---|---|
| 1 | Кредитка 125 000 | Это баланс | Кредитка — обычный счёт с балансом. По умолчанию входит в «Есть», как в Excel; формулу можно поменять (1.1 #6). |
| 2 | Колонки месяцев у Ромы | Факт | Храним **фактические платежи с датой**. Помесячная разбивка и остаток вычисляются. |
| 3 | Видит ли Рома данные | Нет | Приложение для одного человека: без шаринга, выгрузок для партнёра и ролей. |

| 5 | ZenMoney | Сейчас не пользуется | Основной источник банковских данных — **push-уведомления банков на Android + импорт выписок + сверка баланса**. Адаптер ZenMoney — опция на будущее. |
| 6 | Учёба | Расписание статичное, загружает сам | Редактор расписания + загрузка из файла-шаблона. Чёт/нечёт — опция, по умолчанию «каждую неделю одинаково». API вузов не подключаем. |
| 7 | Модели ИИ | Названия примерные (GPT) | Список моделей берём из каталога polza.ai, быстрый выбор настраивается в приложении. Точные id в коде не зашиваем. |
| 8 | Серверы и бэкапы | Бэкапы потом, S3 есть | Бэкапы проектов — отдельный этап после v1. Данные о серверах вносит пользователь. |
| 9 | Установка | Ставит сам | APK вручную, Windows — MSIX с самоподписанным сертификатом. |
| 10 | Сон и ритм | Браслета нет, ритуалы нужны | Сон вводится вручную. **Утренний план и вечерний чек-ин входят в v1.** |

### 1.3 Приоритеты заказчика

- **Офлайн-режим, включая локальную модель ИИ на телефоне, очень важен** — остаётся в v1.
- **Банки очень важны** — не откладываются, отдельный этап сразу после Финансов.
- **Мониторинг серверов — последним этапом.** Упрощённо: готовый движок (Uptime Kuma или Gatus), наш экран «Пульс», алерты в Telegram. Свой Go-агент — потом.
- **Идеи из `03_CREATIVE_IDEAS.md` пока не берём**, кроме явно принятых здесь (корзина, ритуалы, недостающие экраны). Вернёмся к ним после v1.

### 1.4 Экраны, которые добавляются в дизайн

Вход и «Мои устройства»; онбординг и разрешения (уведомления, батарея One UI, доступ к уведомлениям банков); утренний план и вечерний чек-ин; черновики операций из банковских уведомлений; сверка баланса счёта; мастер импорта выписки; журнал конфликтов синхронизации; взаиморасчёты с партнёром; расход и лимит polza.ai; корзина; архив (закрытые проекты, прошедшие семестры).

### 1.5 Решения, которые я принял сам (можно поменять)

| Вопрос | Решение |
|---|---|

| «Был на паре?» | Одно уведомление **после окончания** пары. |

| Доступ к серверу без домена | API по **IP через HTTPS** с собственным сертификатом (самоподписанный CA), клиент проверяет отпечаток сертификата (pinning). | Визуальный стиль | Главный референс — `ref2_workout_app.jpg`: чёрный, белый, оттенки серого, один синий акцент (#0A84FF) точечно. Единственное исключение — приглушённый красный для удаления и критичных ошибок. Шрифт — только Inter с табличными цифрами. Решение заказчика от 2026-09-30, детали — в `02`. |
| Бэкап базы самого приложения | Ежедневный зашифрованный дамп БД приложения в S3 делаем уже на этапе 1. Это не бэкапы проектов (они позже), а страховка ваших данных в трекере. |

## 2. Как устроена разработка

### 2.1 Две фазы

1. **Фаза кода (этапы 0–10).** Кодовая база пишется и тестируется поэтапно. Каждый этап — законченный модуль, закрытый автотестами по стандарту 2.2 и ревью. Установка на устройства и деплой на VPS в этой фазе не требуются.
2. **Фаза сборки и доводки.** Деплой бэкенда на VPS, сборка APK и MSIX, приёмка на Galaxy A55 и ПК по чек-листам всех этапов («Приёмка» в каждом этапе), замеры локальной модели, правки и замены по итогам.

### 2.2 Роли (обязательное правило)

- **Весь код пишут субагенты на модели Sonnet**: разработчики бэкенда и клиента, авторы тестов, исправления по ревью.
- **Главный агент — оркестратор**: ставит задачи субагентам, принимает архитектурные решения, проверяет каждое изменение (читает диф, запускает тесты), назначает отдельного субагента-ревьюера и возвращает работу на доработку. Сам код не пишет.
- Правило закреплено в `CLAUDE.md` в корне репозитория.

### 2.3 Жизненный цикл этапа

1. **Спецификация.** Субагент уточняет разделы 01/02 под модуль: модель данных, API, экраны и состояния, тест-план. Оркестратор проверяет и утверждает.
2. **Разработка.** Субагенты (Sonnet) параллельно: бэкенд и клиент.
3. **Тесты** по стандарту 2.4 — локально в облачной сессии и в CI GitHub Actions.
4. **Ревью.** Оркестратор читает весь диф, отдельный субагент-ревьюер ищет баги и дыры в безопасности. Всё найденное исправляется до закрытия этапа.
5. **Закрытие.** Коммит этапа, тег `v0.N`, запись в журнал этапов (раздел 5).

### 2.4 Стандарт «полностью протестирован» (Definition of Done)

Этап закрыт, только если выполнено **всё**:

| Уровень | Требование |
|---|---|
| Бэкенд: статика | `ruff` и `mypy --strict` без ошибок |
| Бэкенд: unit | Доменная логика модуля (расчёты денег, остатков, повторений, парсеры) — покрытие строк ≥ 90 % |
| Бэкенд: API | Интеграционные тесты каждого эндпоинта модуля на настоящем PostgreSQL: успех, валидация, права, идемпотентность |
| Синхронизация | Таблицы модуля проходят общий набор sync-тестов: property-based с 2–3 симулированными клиентами, обрывы сети, повторы, удаление против правки, корзина |
| Клиент: статика | `flutter analyze` без предупреждений |
| Клиент: unit | Доменная логика на Dart — покрытие ≥ 90 %. Общие тестовые векторы с бэкендом (одинаковые входы → одинаковые результаты в Python и Dart) |
| Клиент: виджеты | Widget-тест **каждого экрана** модуля во всех состояниях: пусто, загрузка, данные, ошибка, офлайн |
| Клиент: вид | Golden-тесты ключевых экранов на двух размерах: телефон и десктоп |
| Сквозные сценарии | Тесты клиента против настоящего бэкенда: основные сценарии модуля, включая «сделал офлайн → появилась сеть → данные на втором устройстве» |
| Регрессия | Все тесты прошлых этапов зелёные |
| Безопасность | `gitleaks` чистый, секретов в коде нет |

Проверки на реальных устройствах (Android-эмулятор, Windows, Galaxy A55) переносятся в фазу сборки.

### 2.5 Где что выполняется

- Код пишется в облачной сессии, всё хранится в GitHub (`Edvvard0/my_tasker`).
- Облачная сессия: Flutter (unit, widget, golden-тесты), Python 3.13, PostgreSQL в Docker.
- CI GitHub Actions повторяет те же проверки на каждый пуш. Сборка APK и MSIX добавляется в фазе сборки.
- Секреты вносит пользователь сам в GitHub Secrets и env сервера — в чат не присылать.

## 3. Этапы

Размер: **S** — до 1 недели, **M** — 1–2 недели, **L** — 2–4 недели.

### Этап 0. Фундамент — M

**Состав**
- Монорепо: `app/` (Flutter), `backend/` (FastAPI), `deploy/`, `shared-test-vectors/`.
- `CLAUDE.md` с правилами проекта (роли, стандарт тестов, секреты).
- CI: линтеры и тесты бэкенда и клиента, gitleaks.
- Бэкенд-каркас: FastAPI, PostgreSQL, миграции Alembic, конфигурация из env, health-эндпоинты, структурированные логи, docker compose, Caddy с TLS по IP (1.5).
- Клиент-каркас: дизайн-токены (цвета, шрифты, отступы) из `02`, адаптивная навигация (таб-бар на телефоне, боковая панель на ПК), локальная БД Drift (с шифрованием SQLCipher на устройствах), экраны-заглушки модулей, настройка адреса сервера.
- Механизм общих тестовых векторов для Python и Dart.

**Тесты:** CI зелёный; тесты health-эндпоинтов на настоящем PostgreSQL; миграции накатываются и откатываются; widget-тесты навигации на телефоне и десктопе; golden-тесты темы; тест открытия локальной БД.

**Приёмка (в фазе сборки):** APK и MSIX открываются в нашей теме; `https://<IP>/health/ready` отвечает.

### Этап 1. Ядро: вход, устройства, синхронизация — L

**Состав**
- Аккаунт, вход, реестр устройств с отзывом.
- Протокол синхронизации: outbox, push и pull, версии, слияние по полям, журнал конфликтов, SSE-сигнал «есть изменения», фоновая синхронизация (WorkManager на Android, таймер на Windows).
- Корзина 30 дней с восстановлением. Архив не общий механизм: закрытые проекты и прошедшие семестры архивируются в своих модулях (этапы 4 и 7).
- Экраны: вход, «Мои устройства», «Синхронизация» (состояние, ошибки, журнал конфликтов, полная пересинхронизация), корзина.
- Ежедневный зашифрованный дамп БД приложения в S3 и процедура восстановления со сменой «эпохи сервера» (устройства сами делают полную пересинхронизацию).

**Тесты:** property-based тесты синхронизации; сценарий «телефон офлайн 3 дня, ПК онлайн, встреча»; повтор пачки (идемпотентность); удаление против правки; очистка корзины через 30 дней; восстановление из дампа.

**Приёмка (в фазе сборки):** в режиме полёта на телефоне создаёте тестовую запись → включаете сеть → она на ПК; одновременно правите одно поле на двух устройствах → запись не потерялась, конфликт в журнале, «вернуть моё» работает.

**Нужно от вас:** S3 — endpoint, bucket и ключи в env сервера.

### Этап 2. Календарь и задачи (главный экран) — L

**Состав**
- События и задачи: с временем, с датой, без даты; 5 статусов; P1–P5; подзадачи; повторения (RRULE) и исключения.
- Чередование недель (чёт/нечёт) для событий.
- Виды: расписание, день, 3 дня, неделя, месяц; бэклог задач; перетаскивание в сетку на ПК.
- Быстрый ввод с синтаксисом из 1.5.
- Локальные напоминания: Android (работают офлайн) и Windows (трей, toast-уведомления). Праздники РФ.
- Экран «Сегодня».

**Тесты:** развёртка повторений и чёт/нечёт на общих векторах; парсер быстрого ввода (≥ 100 фраз); напоминания срабатывают при переходе через полночь, смену часового пояса и перезагрузку; все экраны — widget и golden.

**Приёмка (в фазе сборки):** неделя реального планирования в приложении без Google Календаря.

### Этап 3. ИИ-чат (онлайн) — L

**Состав**
- Прокси polza.ai на сервере со стримингом; ключ только на сервере.
- Каталог моделей, быстрый выбор и его настройка.
- Агенты по разделам с редактируемыми системными промтами; конструктор контекста (разделы и конкретные данные, превью перед отправкой).
- Чаты и история через синхронизацию.
- Агент создаёт задачи: карточка в чате → правка → одобрить / отклонить.
- Расход и месячный лимит polza.ai.
- Расширяемость: контекст и инструменты агента подключаются через провайдеры. На этом этапе есть провайдеры Календаря и Задач; каждый следующий модуль (Работа, Финансы, Учёба, Сон) добавляет свой провайдер и свои тесты.

**Тесты:** стриминг с обрывом связи; ключ никогда не попадает в ответы API и логи; карточка задачи создаёт ровно одну задачу; лимит расходов блокирует запросы. Контракт с polza.ai — на записанных ответах, чтобы CI не тратил деньги.

**Приёмка (в фазе сборки):** агент видит ваши задачи и расписание, в чате «Работа» — проекты; создаёт задачу, которую вы одобрили.

### Этап 4. Работа — L

**Состав**
- Люди и заказчики; проекты → доработки, у каждой сумма и статус.
- Фактические платежи с датой; помесячная разбивка и остаток вычисляются.
- Взаиморасчёты с партнёром (Рома): доля, кто кому сколько должен.
- Трекер времени по проектам: уведомление-таймер на Android, трей на Windows; доход в час.
- Задачи по проектам (связь с этапом 2); «сколько мне ещё должны и кто».
- Архив закрытых проектов.

**Тесты:** все денежные расчёты (остатки, доли, доход в час) — в копейках, на общих векторах; трекер времени переживает закрытие приложения и перезагрузку; нельзя запустить два таймера.

**Приёмка (в фазе сборки):** вы вносите свои реальные проекты с Ромой, цифры совпадают с вашим пониманием; Excel «Эдвард_Рома» больше не нужен.

### Этап 5. Финансы — L

**Состав**
- Счета: карты, наличные, кредитка (как баланс); общий баланс.
- Операции, категории, переводы между своими счетами.
- Долги: мне должны / я должен.
- Цели с настраиваемой формулой «Есть» и «Не хватает».
- Ожидаемые поступления из Работы.
- Аналитика по месяцам и категориям; глоссарий метрик.
- Замок раздела (PIN или биометрия) и режим «скрыть суммы».

**Тесты:** формула цели на векторах (включая ваш случай из Excel); переводы не считаются доходом или расходом; баланс = начальный + операции.

**Приёмка (в фазе сборки):** Excel «Финансовая таблица» больше не нужен; цифры цели совпадают с ожидаемыми.

### Этап 6. Банки — M

**Состав**
- Android: слушатель уведомлений Т-Банка и ВТБ → черновики операций → подтвердить / поправить / отклонить; дедупликация.
- Импорт выписок (форматы по тем файлам, которые реально выгружают ваши банки) с сопоставлением категорий.
- Сверка баланса счёта с банком; нераспознанное уходит в «Требует проверки».
- Экраны: черновики, мастер импорта, сверка.

**Тесты:** парсеры на ваших реальных (обезличенных) текстах уведомлений и выписках — каждый образец становится тестом; дубль «уведомление + выписка» не создаёт две операции; выживание слушателя после перезагрузки и оптимизации батареи One UI.

**Приёмка (в фазе сборки):** неделя трат — операции появляются сами, баланс сходится с банком.

**Нужно от вас:** 30–50 текстов банковских уведомлений (суммы и имена можно заменить) и по одной выписке из каждого банка.

### Этап 7. Учёба — M

**Состав**
- Семестр, предметы, преподаватели.
- Статичное расписание: редактор и загрузка из файла-шаблона; чёт/нечёт — опция. Пары показываются в календаре.
- Посещаемость: «Был на паре?» после окончания; счётчик пропусков с лимитом по предмету.
- Учебные долги → задачи.
- Архив прошедших семестров.

**Тесты:** расписание на семестр с чётом и нечётом; счётчики пропусков; уведомление не приходит в праздники и отменённые пары.

**Приёмка (в фазе сборки):** вы загружаете своё расписание, неделю отмечаете посещаемость.

### Этап 8. Сон и ежедневные ритуалы — M

**Состав**
- Сон: ручной ввод «лёг / встал», быстрый ввод из утреннего уведомления, история и простые графики.
- **Утренний план** (~2 минуты): сон, задачи на сегодня, пары, события, выбор главного.
- **Вечерний чек-ин**: что сделано, что перенести, короткая оценка дня.
- Простая связь сна с выполненными задачами за неделю.

**Тесты:** сон через полночь; пропущенные дни; перенос задач из чек-ина меняет даты правильно.

**Приёмка (в фазе сборки):** неделя с ритуалами каждый день.

### Этап 9. Серверы: мониторинг и Telegram — M

**Состав**
- Готовый движок проверок (Uptime Kuma или Gatus) рядом с бэкендом.
- Проверки HTTP, TCP, DNS, SSL.
- Экран «Пульс»: карточки, статус, доступность %, отклик, инциденты.
- Алерты о падении и восстановлении в Telegram с антиспамом.
- Серверы и проекты вносите вы.
- Кнопки «Выключить» нет.

**Тесты:** падение → алерт ровно один раз → восстановление; кэш дашборда офлайн.

**Приёмка (в фазе сборки):** гасите тестовый сервис — алерт в Telegram приходит за ≤ 2 минуты.

**Нужно от вас:** `TELEGRAM_BOT_TOKEN` (перевыпущенный) и `TELEGRAM_CHAT_ID` — только в env сервера; список серверов и URL.

### Этап 10. ИИ офлайн на телефоне — M

**Состав**
- **Замеры на Galaxy A55** (проводятся здесь, на последнем этапе): бенчмарк Gemma 4 E2B (LiteRT-LM) против Qwen (llama.cpp) — скорость, память, нагрев, качество русского и JSON на 20 фразах. По итогам выбираем модель и рантайм.
- Код готовится заранее за абстракцией «локальная модель», чтобы замена модели не трогала чат.
- Загрузка модели по Wi-Fi, хранение, удаление.
- Стриминг, создание задач по той же карточке, лёгкий контекст.
- Автопереключение: нет сети → локальная модель; отложенные запросы к облачной модели уходят при появлении сети.

**Тесты:** JSON задач на наборе русских фраз (порог точности фиксируется по итогам замеров); память и нагрев в пределах замеров; переключение сеть ↔ офлайн посреди чата.

**Приёмка (в фазе сборки):** в режиме полёта чат отвечает и создаёт задачу.
