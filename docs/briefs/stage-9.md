# Выжимка этапа 9. Серверы: мониторинг и Telegram

> Для субагентов. Источник истины — `docs/04_DECISIONS_AND_ROADMAP.md`, этап 9 (и решение 1.1 №3: **кнопки «Выключить» нет**); `01` §5.8 и §6.6 — образец логики (там «свой движок», у `04` приоритет: готовый движок, свой агент — после v1). Контракт — `docs/specs/stage9_monitoring.md`.

## Требования заказчика

1. Готовый движок проверок (Uptime Kuma **или** Gatus) рядом с бэкендом; проверки **HTTP, TCP, DNS, SSL**.
2. Экран «Пульс»: карточки, статус, доступность %, отклик, инциденты (`02` §5.5, референс `ref3_pulse_monitoring.png`). Приложение серверами **не управляет**, только наблюдает; остаётся «Проверить сейчас».
3. Алерты о падении и восстановлении в Telegram **с антиспамом**.
4. **Серверы и проекты вносит заказчик** (в приложении, офлайн-first).
5. Нужно от заказчика: `TELEGRAM_BOT_TOKEN` (перевыпущенный) и `TELEGRAM_CHAT_ID` — **только в env сервера**; список серверов и URL.
6. Приёмка (фаза сборки): гасим тестовый сервис — алерт приходит за ≤ 2 минуты.

## Решения оркестратора (заказчик может поменять)

- **Движок — Gatus** (не Uptime Kuma): настраивается файлом YAML, который **генерирует worker** из данных заказчика (у Kuma конфигурация живёт в его БД и меняется через нестабильный socket.io), один лёгкий контейнер, стабильный JSON API статусов, Apache-2.0. Выбор — решение, а не догма: движок спрятан за интерфейсом `EngineClient` и генератором конфигурации; замена на Uptime Kuma (или на свой движок из `01`) — новый адаптер и новый генератор, остальное не меняется.
- **Движок только измеряет.** Алерты, антиспам, инциденты, доступность и Telegram — **наши** (worker): у Gatus свои алерты не включены, токен Telegram движку не выдаётся.
- **Данные заказчика синхронизируются** (три таблицы: серверы → сервисы/проекты → проверки; каскады, корзина). **Измеренное не синхронизируется**: результаты, инциденты, состояние алертов лежат в серверных таблицах `monitor_*`, клиент читает их через API «Пульс» (снимок целиком + `ETag` для офлайн-кэша).
- **SSRF.** Проверки исполняет наш сервер: адреса внутренней сети, loopback, link-local, metadata, имена без точки и внутренние зоны, URL с логином — запрещены (при записи, при генерации конфигурации и сетевой изоляцией контейнера движка). Редиректы не выполняются.
- **Антиспам:** подтверждение падения (3 неудачи подряд), восстановления (2 успеха), одно сообщение о падении и одно о восстановлении на инцидент, склейка одновременных падений, флаппинг, напоминания (через 1 час, затем каждые 4), тихие часы для некритичных сервисов, очередь с лимитом скорости. Секреты — только `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` из env; в логи, ответы API и конфигурацию движка не попадают.
- **Не входят:** контейнеры X из Y и агент на серверах (после v1), бэкапы, ICMP/heartbeat/ключевые JSON-условия, окна обслуживания и пауза («Выключить»), inline-кнопки Telegram.

## Объём бэкенда

Контракт → миграция `0013` → валидация (SSRF) → эталоны (`targets.py`, `alerts.py`, `stats.py`) + общие векторы `shared-test-vectors/monitoring/*.json` (alerts ≥ 30; сейчас 39) → адаптер движка и генератор конфигурации → Telegram за интерфейсом → цикл опроса, очередь и доставка в worker → API «Пульс» → `deploy/` (сервис `gatus`, тома, сеть, env) → тесты.

## Объём клиента

Экран «Пульс» (карточки, статус-пилюли, доступность, отклик, мини-график, инциденты, «Самопроверка»), редактор серверов/проектов/проверок с той же проверкой адресов (векторы `targets.json`), офлайн-кэш последнего снимка («Данные на HH:MM · нет сети»), кнопка «Проверить сейчас», кнопка «Отправить тестовое сообщение». Кнопки «Выключить» нет.

## Тесты (облегчённый процесс)

Высокий риск — **безопасность и антиспам**: SSRF-векторы и тесты записи, падение → алерт ровно один раз → восстановление (в том числе повторные опросы, падение бэкенда движка, перезапуск), токен и chat id не попадают в логи и ответы, авторизация эндпоинтов, миграции вверх/вниз, синхронизация новых таблиц. Настоящий Telegram и настоящий Gatus в CI не вызываются: записанные ответы и подделки.
