# Выжимка этапа 6. Банки

> Для субагентов. Решения ниже окончательные; первоисточники — только по ссылкам.
> Заказчик: банки **очень важны**; ZenMoney сейчас **не используется** (ответ 2026-09-30). Легального персонального банковского API в РФ нет — источники: **уведомления банков на Android**, **выписки**, **ручная сверка**.

## Что уже есть

- Этап 5 (`docs/specs/stage5_finance.md`): счета с `card_last4`; операции с `source` (`manual` / `notification` / `statement` / `work_payment`), `status` (`confirmed` / `draft` / `needs_review` — в суммы входит только `confirmed`), `external_id`, `dedup_hash` (формат `[0-9a-f]{16,64}`, способ вычисления — **этот этап**), ключ `dedup_key` (§7.2); точки сверки `balance_checkpoints` с `source` (`manual` / `notification` / `statement`) и вычисляемая корректировка (§4.3); проверка `duplicate_external_id` в `integrity_problems`.
- Сервер уникальность не навязывает: **дубли отсекает импортёр до создания строки**.

## Решения оркестратора

### 1. Уведомления банков (только Android, только на устройстве)
- `NotificationListenerService` слушает только пакеты из белого списка (Т-Банк, ВТБ; список расширяемый). Сырой текст уведомления хранится **только локально 30 дней** (не синхронизируется) — на сервер уходит лишь распознанная операция-черновик.
- **Парсер правил как данные**: файл правил `shared-data/banks/notification_rules.json` (банк → пакет → шаблоны: тип операции, сумма, валюта, карта/последние 4 цифры, мерчант, баланс после операции, время). Код парсера — на Dart, общий движок для всех банков; новый формат = новая запись в правилах, без кода.
- Результат: операция `status = draft`, `source = notification`, счёт — по `card_last4` (нет совпадения → `needs_review` и выбор счёта); **баланс из уведомления** → точка сверки `source = notification`.
- Нераспознанное уведомление банка → запись в «Требует проверки» с исходным текстом (локально), можно создать операцию вручную из него.
- Распознавание переводов между своими счетами: исходящий перевод на одном счёте + входящий на другом с той же суммой в окне 10 минут → предложение склеить в один `transfer`.

### 2. Выписки (на сервере)
- Импорт выписки — **через сервер**: клиент загружает файл → сервер разбирает (Python: CSV, XLSX, PDF через pdfplumber) → возвращает список операций-кандидатов → клиент показывает мастер (сопоставление счёта, категории, отметка дублей) → подтверждённые кандидаты клиент создаёт как обычные операции `source = statement`. Сервер файл **не хранит** после разбора.
- Форматы — по реальным выпискам Т-Банка и ВТБ (заказчик пришлёт); до этого — каркас парсеров с синтетическими образцами по публично известным форматам, помеченными как синтетические.
- Остаток на конец периода из выписки → точка сверки `source = statement`.

### 3. Дедупликация и сопоставление (общие правила Python и Dart, векторы)
- `external_id`: если источник даёт идентификатор (некоторые выписки) — он.
- `dedup_hash` (когда id нет): SHA-256 от нормализованной строки `account_id|kind|amount|occurred_at (до минуты, UTC)|merchant_norm`, первые 32 hex. Нормализация мерчанта — общая функция (регистр, пробелы, кавычки, «ООО/ИП», хвостовые города и номера терминалов).
- **Межисточниковое сопоставление** (уведомление ↔ выписка ↔ ручная): кандидат — тот же счёт, тот же тип и сумма, разница во времени ≤ 48 ч (выписка часто только с датой), похожий мерчант (порог похожести — в контракте). Найдено совпадение → **одна операция**: выписка уточняет черновик из уведомления (дата, мерчант), а не создаёт вторую.
- Общие векторы `shared-test-vectors/banks/*.json`: нормализация мерчанта, хеш, сопоставление (≥ 50 случаев: совпадение, близкие суммы, две одинаковые покупки за день, возврат, перевод между своими счетами, иностранная валюта → `needs_review`).

### 4. Категории
- Автокатегория по мерчанту: правила «мерчант → категория», которые пользователь пополняет при подтверждении («запомнить для этого мерчанта») — синхронизируемая таблица правил; плюс встроенный стартовый словарь (MCC/ключевые слова) в `shared-data/banks/`.

### 5. Экраны (клиент)
- «Черновики»: лента распознанных операций → подтвердить / поправить / отклонить, массовое подтверждение.
- «Требует проверки»: нераспознанные уведомления и операции без счёта.
- Мастер импорта выписки, сверка баланса счёта с банком (ввод фактического остатка, показ корректировки).
- Онбординг разрешения «доступ к уведомлениям» и исключения из оптимизации батареи One UI (с инструкцией).

## Объём бэкенда
Контракт `docs/specs/stage6_banks.md` (форматы правил уведомлений, движок разбора, нормализация, хеш, сопоставление с примерами, эндпоинт разбора выписки, таблица правил категорий) → эндпоинт `POST /banks/statements/parse` (лимит размера, без хранения файла) → парсеры выписок (каркас + синтетические образцы) → эталон нормализации/хеша/сопоставления на Python → векторы → тесты.

## Объём клиента
Слушатель уведомлений (тонкая платформенная часть, логика за интерфейсом), движок правил на Dart, черновики, «Требует проверки», мастер импорта, сверка, автокатегории, онбординг разрешений.

## Нужно от заказчика (до приёмки, не блокирует код)
30–50 текстов уведомлений Т-Банка и ВТБ (суммы и имена можно заменить) и по одной выписке каждого банка (CSV/XLSX/PDF — какие банк даёт). Каждый образец станет тестом.

## Тесты (облегчённый процесс)
Высокий риск: парсер уведомлений (по каждому шаблону), нормализация, хеш и сопоставление (векторы, одинаковые на Python и Dart), импорт выписки без дублей, переводы между своими счетами, черновики не попадают в суммы. Golden — черновики и мастер импорта.
