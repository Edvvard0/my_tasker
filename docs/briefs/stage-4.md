# Выжимка этапа 4. Работа

> Для субагентов. Читать вместо больших документов; первоисточники — только по ссылкам.

## Что уже есть

- Этап 1: синхронизация с реестром таблиц (`docs/specs/stage1_sync_and_auth.md`).
- Этап 2: таблицы `projects` (название, цвет, архив) и `people` (имя, архив) — заготовки. **Этап 4 расширяет эти же таблицы новыми необязательными колонками**, id не меняются (`docs/specs/stage2_calendar_tasks.md` §2.3, §4.3). У задач уже есть `project_id`, `person_id`.
- Этап 3: ИИ-чат с реестром инструментов и провайдеров контекста на сервере (`docs/specs/stage3_ai_chat.md`) — этап 4 добавляет инструменты «Работы».

## Решения оркестратора

1. **Рома — заказчик, а не партнёр** (уточнение заказчика от 2026-10-02). Долей, раздела денег и взаиморасчётов с партнёром **нет**: «Рома должен» = неоплаченный остаток по проектам заказчика Ромы. У других проектов свои заказчики (например, Елена).
2. **Как сейчас ведёт пользователь (Excel «Эдвард_Рома»):** проект (базовая сумма) → доработки (у каждой своя сумма и статус «в работе / закрыт»); оплаты разнесены по месяцам. Заказчик подтвердил: **месячные колонки — это факт** полученных денег. Данные пользователь внесёт сам, импорт Excel не делаем.
3. **Сущности** (первоисточник: `docs/01_ARCHITECTURE_PLAN.md` §5.3, §6.5):
   - `projects` (+ заказчик → person, статус: лид / в работе / пауза / завершён / отменён, тип оплаты: фикс / почасовой, базовая сумма, ставка в час, даты, описание, ссылки);
   - `people` (+ роль: заказчик / другое, контакт — свободный текст);
   - `change_requests` (доработки): проект, название, сумма, статус (в работе / закрыта / отменена), дата закрытия, оценка часов, заметка;
   - `payments` (факт поступления): дата, сумма, от кого (заказчик), комментарий;
   - `payment_allocations`: платёж → проект или доработка, сумма (один платёж может закрывать несколько доработок, доработка — оплачиваться частями; сумма распределений не больше суммы платежа);
   - `time_entries`: проект, доработка (необязательно), задача (необязательно), начало, конец (пусто — таймер идёт), оплачиваемое, заметка, источник (таймер / вручную).
   - **Графика оплат (план) в v1 нет**: «сколько ещё должны» = остатки по проектам и доработкам.
4. **Расчёты** — только целые копейки, RUB, одинаково на сервере и клиенте, **общие векторы** `shared-test-vectors/work/*.json`:
   - сумма проекта = базовая + доработки (кроме отменённых); получено = сумма распределений; доля оплаты = получено / сумма; остаток = сумма − получено;
   - **дебиторка по заказчику**: сумма остатков по всем незакрытым проектам заказчика (не отменённым) — «Рома должен мне X», «Елена должна Y»; плюс общий итог «мне должны»;
   - доля оплаты — единственное место с делением; правило округления процента зафиксировать в контракте (копейки никогда не округляются — только целые суммы и разности);
   - доход в час по проекту и общий: показываем оба варианта — **по факту** (полученное / часы) и **по начисленному** (закрытые доработки + базовая сумма завершённых проектов / часы); деление — с округлением вниз до копейки; часы — только оплачиваемые записи;
   - помесячная разбивка полученного (как колонки Excel) — по дате платежа в Europe/Moscow.
5. **Трекер времени:** один идущий таймер на устройстве; если после синхронизации идут два (запущены офлайн на разных устройствах) — показать предупреждение и дать остановить любой. Таймер переживает закрытие приложения и перезагрузку (хранится начало). Android — постоянное уведомление с таймером и кнопкой «Стоп»; Windows — трей. Платформенная часть тонкая, за интерфейсом.
6. **Архив:** проекты со статусом «завершён»/«отменён» можно архивировать; архив — отдельный список, данные не удаляются.
7. **ИИ:** серверные инструменты чтения для агента «Работа»: проекты со статусами и остатками, дебиторка по заказчикам, часы и доход в час за период. Через реестр этапа 3.

## Дизайн

`docs/02_DESIGN_SYSTEM.md` §5.4 «Таблицы и списки Работы: как превратить Excel в интерфейс» и макеты «Работа» в §6. Монохромный стиль (`docs/references/ref2_workout_app.jpg`), крупные цифры, синий — только акцент.

## Объём бэкенда

Контракт `docs/specs/stage4_work.md` (таблицы, валидация, правила расчётов с примерами, инструменты ИИ) → миграция (расширение `projects`/`people` + новые таблицы) → валидация → эталонные расчёты на Python для векторов → инструменты ИИ → тесты.

## Объём клиента

Список проектов (активные / архив), карточка проекта в стиле «Excel-интерфейса» (доработки, оплаты, остаток, часы, доход в час), ввод платежа с распределением, экран «Мне должны» по заказчикам, трекер времени (старт/стоп из проекта и из задачи, уведомление и трей), сводка «кто сколько должен», провайдер контекста ИИ для чата «Работа».

## Тесты (облегчённый процесс, `04` §2.4)

Высокий риск: все денежные расчёты на общих векторах (≥ 60 случаев: частичные оплаты, один платёж на несколько доработок, отменённые доработки, переплата, проект без доработок, несколько заказчиков, дебиторка по заказчику, доход в час с нулём часов), трекер (перезапуск, два таймера после синхронизации). Golden — только список проектов, карточка проекта, «Мне должны».
