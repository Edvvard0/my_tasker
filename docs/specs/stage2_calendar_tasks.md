# Этап 2. Спецификация: календарь и задачи

> Контракт между бэкендом (`backend/`) и клиентом (`app/`). Клиент реализуется по этому документу. Опирается на `stage1_sync_and_auth.md` (синхронизация, корзина, конфликты) и уточняет разделы 5.2, 6.2 и 7.1 из `01_ARCHITECTURE_PLAN.md`; при расхождении с ним действует этот документ, при расхождении с `04_DECISIONS_AND_ROADMAP.md` — 04.
> Идентификаторы, имена колонок и значения перечислений — на английском. Тестовые векторы: `shared-test-vectors/calendar/*.json` (описание в конце). Данные праздников: `shared-data/calendar/holidays_ru.json`.

## 0. Принципы

- **Сервер — хранилище и валидатор.** Всё, что делает календарь, работает **на клиенте офлайн**: разбор быстрого ввода, развёртка повторений, номер недели цикла, праздники, планирование локальных уведомлений. Новых REST-эндпоинтов этап не добавляет: все таблицы ходят через `POST /sync/push` и `GET /sync/pull` (Этап 1). Серверная часть — таблицы, проверки значений и эталонные реализации, которыми проверяются общие векторы.
- Экземпляры повторяющихся событий и задач **не материализуются**: они разворачиваются на лету в видимом диапазоне (5.3).
- Время — UTC-момент + IANA-таймзона; «весь день» и «срок без времени» — дата без времени (раздел 1). Деньги здесь не участвуют.
- Все таблицы имеют служебные поля Этапа 1 (`id`, `created_at`, `updated_at`, `deleted_at`, `server_version`, `origin_device_id`); ниже описаны только прикладные колонки.
- Слияние конфликтов — по полям (Этап 1, 3.4). Поэтому **группы связанных полей клиент всегда отправляет целиком** в одной операции: `(all_day, start_at, end_at, tz, start_date, end_date)`; `(due_date, due_at, due_tz)`; `(rrule)` вместе с началом серии. Иначе слияние двух устройств может собрать невалидное сочетание — сервер отклонит такую операцию с `validation_failed`, и она останется в outbox как `rejected` (Этап 1, 3.3).

## 1. Правила времени

| Что | Хранение | Пример |
|---|---|---|
| Момент события/срока | `datetime` (UTC, `Z`) + `tz` (IANA) | `start_at: "2026-10-05T07:00:00Z"`, `tz: "Europe/Moscow"` |
| Весь день, срок без времени | `text` `YYYY-MM-DD` (реальная дата, годы 1970–2200), колонки `*_date` | `start_date: "2026-10-05"` |
| Экземпляр повторяющегося события | ключ `original_start`: UTC-момент `YYYY-MM-DDTHH:MM:SSZ` (для события с временем) или `YYYY-MM-DD` (весь день) | `"2026-10-06T07:00:00Z"` |

- Значения `datetime` в операциях — ISO 8601 с явной зоной (`Z`), допустимы любые доли секунды; в векторах и в ключах экземпляров — ровно `YYYY-MM-DDTHH:MM:SSZ` (целые секунды).
- `tz` — имя из базы IANA (`Europe/Moscow`, `Europe/Berlin`, `UTC`…), сервер проверяет по списку `zoneinfo.available_timezones()`. Псевдонимы вида `Local`, смещения (`+03:00`) и аббревиатуры (`MSK`) недопустимы.
- **Событие «с временем»** хранится как момент начала/конца (UTC) и `tz`, в которой оно было создано. Отображение — в текущей таймзоне устройства, если пользователь не включил «показывать в таймзоне события»; **повторения всегда считаются в `tz` события** (5.2).
- **Событие «весь день»** — `all_day = true`, даты `start_date`/`end_date` (**`end_date` включительно**, `end_date ≥ start_date`), `start_at/end_at/tz` пусты. Никаких таймзон: 5 октября — это 5 октября везде.
- Событие «с временем» имеет длительность `end_at − start_at` (≥ 0; ноль допустим — «точка во времени»), не длиннее 366 суток. У повторяющегося события каждый экземпляр имеет ту же **абсолютную** длительность (в UTC), а не «ту же настенную».
- Год во всех датах и моментах — 1970…2200.

### 1.1 Перевод «настенного» времени в UTC (переход на летнее время)

Повторения считаются в настенном времени `tz`; для каждого экземпляра нужен его UTC-момент. Правило одно для всех реализаций: **берётся смещение, действовавшее ДО ближайшего перехода**.

- Обычное время — однозначно.
- **Неоднозначное** (осенью 02:30 встречается дважды) — берётся первое вхождение (смещение до перехода, «летнее»).
- **Несуществующее** (весной 02:30 не бывает) — берётся смещение до перехода: экземпляр сдвигается вперёд на величину скачка (02:30 → 03:30 по новому времени).

Векторы: `daily_0230_missing_wall_time_moves_forward`, `daily_0230_ambiguous_wall_time_first_offset`, `daily_count_across_spring_forward`, `weekly_new_york_fall_back` и др. В Dart это шаг «настенное → UTC» надо реализовать явно: пакет `timezone` в разрывах ведёт себя иначе, чем это правило.

## 2. Общие соглашения таблиц

### 2.1 Порядок регистрации и связи

Таблицы регистрируются родителями вперёд (`backend/src/tasker/calendar/tables.py`, `CALENDAR_TABLES`):

```
calendars ─┬─ events ── event_overrides
projects   (без каскада)        people (без каскада)        tags ──────────────┐
tasks ─┬─ subtasks                                                             │
       ├─ task_tags ───────────────────────────────────────────────────────────┘
       └─ task_completions
```

Стрелка = «дочерняя таблица ссылается на родителя» (колонка-внешний ключ, `parent_not_found`, каскады Этапа 1, 3.5).

**Каскады** (делает сервер, клиент шлёт одну операцию `delete`/восстановления родителя):

| Удаляется | Уходит в корзину каскадом |
|---|---|
| `calendars` | его `events`, а с ними их `event_overrides` |
| `events` | `event_overrides` события |
| `tasks` | `subtasks`, `task_tags`, `task_completions` задачи |
| `tags` | `task_tags` с этим тегом |
| `projects`, `people` | **ничего** (мягкая ссылка, см. 2.3) |

Восстановление родителя возвращает только тех потомков, что были удалены каскадом от него (Этап 1, 3.5). Локальная видимость на клиенте — как в Этапе 1: строка видима, если её `deleted_at = null` **и** все её родители видимы.

### 2.2 Детерминированные id

Чтобы два устройства, независимо создавшие «одно и то же» офлайн, не породили дубли, у ряда таблиц `id` вычисляется: `uuid5(ns(table), name)`, где `ns(table) = uuid5(NAMESPACE_URL, "urn:my-tasker:<table>")`. Сервер проверяет id при создании (`invalid_id`). Векторы: `calendar/ids.json`.

| Таблица | `name` для uuid5 |
|---|---|
| `calendars` (только системные) | `system_key` |
| `tags` | `lower(name)` (обычное «простое» приведение к нижнему регистру: `str.lower()` / `toLowerCase()`) |
| `event_overrides` | `"{event_id}\|{original_start}"` (`event_id` — строчный дефисный uuid) |
| `task_tags` | `"{task_id}\|{tag_id}"` |
| `task_completions` | `"{task_id}\|{instance_date}"` |

У остальных таблиц — UUIDv7, генерирует клиент (Этап 1, 2.3). Пользовательские (не системные) календари тоже UUIDv7.

### 2.3 Мягкие ссылки на будущие сущности

`tasks.project_id` и `tasks.person_id` — колонки `uuid` **без внешнего ключа и без каскада**. Это решение «как задачам ссылаться на проекты Этапа 4 и не сломаться»:

- Сейчас (Этап 2) есть минимальные таблицы `projects` (название, цвет, архив) и `people` (имя, архив), чтобы работал быстрый ввод `#проект` и `@человек`. Этап 4 (Работа) **расширяет те же таблицы новыми необязательными колонками** (заказчик, доля, роли, контакты…) — идентификаторы проектов не меняются, миграция данных не нужна.
- Ссылка не проверяется сервером: задача может ссылаться на проект, которого ещё нет на этом устройстве (порядок доставки), или которого уже нет. Клиент показывает такую задачу «без проекта» и **не чистит** ссылку — если проект появился или восстановлен из корзины, связь вернётся сама.
- Удаление проекта не удаляет и не изменяет задачи. Поведение при архивации проекта — решение Этапа 4.
- Ссылки `event_id → project` («ссылки: проект, предмет, шаблон») добавят будущие этапы новыми nullable-колонками (сервер молча отбрасывает неизвестные колонки от более новых клиентов — Этап 1, версии протокола).

### 2.4 Напоминания (`reminders`)

Колонка `reminders` (json, необязательная): `null`/отсутствует = без напоминаний, иначе **список целых «минут до начала»**: 0…40320 (28 суток), не более 5 элементов, без повторов. Пример: `[0, 10, 1440]` — в момент начала, за 10 минут, за сутки.

- Для события/задачи **с временем** опорный момент — начало (`start_at`/`due_at`).
- Для **«весь день»/срока без времени** опорный момент — локальное время `calendar.all_day_reminder_time` (настройка `user_settings`, значение вида `"09:00"`, по умолчанию `09:00`) на дату начала. Поэтому `[0]` = «в 9:00 в этот день», `[900]` = «в 18:00 накануне».
- Локальные уведомления **планируются на клиенте** (Android: `zonedSchedule`, Windows: внутренний таймер) на 14 дней вперёд и пересчитываются при любой правке, после синхронизации и при старте (раздел 7 в `01`). Сервер только хранит определения. Для экземпляров повторений список берётся из `event_overrides.reminders`, если он не `null`, иначе из события.
- Напоминание на выполненную, отменённую или удалённую (в корзине) задачу не срабатывает; на отменённый экземпляр — тоже.

## 3. Таблицы календаря

Обозначения: «обяз.» — колонка обязательна при создании; `null` допустим только у колонок с пометкой «null». «неизм.» — неизменяема после создания (`immutable_field`). Ошибки значений — `invalid_field` (тип, длина, формат, перечисление); межполевые — `validation_failed` (Этап 1, 3.3).

### 3.1 `calendars` — слои

| Колонка | Тип | Правила |
|---|---|---|
| `name` | text | обяз., 1–100 символов, не пустая после trim |
| `color` | text, null | `#RRGGBB` (регистр любой) |
| `kind` | enum | обяз.: `user` \| `system` |
| `system_key` | text, null | неизм.; для `kind=system` — обяз., одно из `personal`, `work`, `study`, `tasks`, `holidays_ru`; для `user` — `null` |
| `visible` | bool | обяз. — галочка слоя в левой панели |
| `position` | int | обяз., 0…1 000 000 — порядок в списке |

- **Системные календари** создаёт клиент при первом запуске с **детерминированным** `id = uuid5(ns("calendars"), system_key)` (2.2): `personal` («Личное»), `work` («Работа»), `study` («Учёба»), `tasks` («Задачи»), `holidays_ru` («Праздники России»). Повторное создание с другого устройства безопасно (та же строка; название и цвет — по обычному слиянию полей).
- Системные календари **нельзя удалять** — это правило клиента (сервер удаление не запрещает). `system_key` сервер защищает сам (неизменяем), а перевод `kind` в `user` при заданном ключе — `validation_failed`. Слои `tasks` и `holidays_ru` не содержат строк `events`: `tasks` показывает задачи с датами, `holidays_ru` — праздники из встроенных данных (раздел 7). Строка нужна только для видимости, названия, цвета и порядка.
- Удаление пользовательского календаря удаляет его события (каскад, 2.1); клиент перед этим предупреждает и предлагает перенести события.

### 3.2 `events` — события

| Колонка | Тип | Правила |
|---|---|---|
| `calendar_id` | uuid → `calendars` | обяз.; каскад |
| `title` | text | обяз., 1–300, не пустое после trim |
| `description` | text, null | ≤ 10 000 |
| `location` | text, null | ≤ 500 |
| `all_day` | bool | обяз. |
| `start_at`, `end_at` | datetime, null | у события с временем — обяз. оба, `end_at ≥ start_at`, длительность ≤ 366 суток; у «весь день» — `null` |
| `tz` | text, null | у события с временем — обяз., имя IANA; у «весь день» — `null` |
| `start_date`, `end_date` | text, null | у «весь день» — обяз. оба, реальные даты, `end_date ≥ start_date`, длина ≤ 366 суток; у события с временем — `null` |
| `rrule` | text, null | тело правила из подмножества раздела 5.1; `null` — не повторяется |
| `reminders` | json, null | 2.4 |
| `source` | enum | обяз.: `manual` \| `template` \| `study` \| `ai` \| `import` |

Дополнительно: `UNTIL` в `rrule` не раньше начала серии (`start_at`/`start_date`).

**Начало серии.** `start_at`/`start_date` — это момент **первого экземпляра**, и он **обязан подходить под правило** (клиент выбирает начало сам: см. `first_date` в разделе 6). Если начало не подходит под `BYDAY`/`BYMONTHDAY`, первым экземпляром считается ближайший подходящий позже, а «лишнего» экземпляра в момент `start_at` **нет** (так ведёт себя `python-dateutil` и эталон; вектор `weekly_byday_earlier_than_start_weekday_skips_first_week`). Сервер синхронность начала и правила не проверяет.

### 3.3 `event_overrides` — переопределения одного экземпляра

Одна строка = один экземпляр повторяющегося события: «отменён» (это и есть `EXDATE`) или «изменён».

| Колонка | Тип | Правила |
|---|---|---|
| `event_id` | uuid → `events` | обяз., неизм.; каскад |
| `original_start` | text | обяз., неизм.; ключ экземпляра (раздел 1): `YYYY-MM-DDTHH:MM:SSZ` или `YYYY-MM-DD` |
| `cancelled` | bool | обяз.; `true` — экземпляра нет (остальные поля игнорируются) |
| `title`, `description`, `location` | text, null | `null` = «как в событии»; `title` не пустой после trim |
| `start_at`, `end_at` | datetime, null | новое время экземпляра; **оба или ни одного** |
| `start_date`, `end_date` | text, null | новая дата экземпляра «весь день»; оба или ни одного; `end_date` включительно |
| `reminders` | json, null | `null` = как в событии; `[]` — без напоминаний |

- `id = uuid5(ns("event_overrides"), "{event_id}|{original_start}")` (2.2): два устройства, переопределившие один экземпляр, дают одну строку.
- Нельзя одновременно задать `start_at` и `start_date`. `end ≥ start`. Таймзона экземпляра всегда `tz` события; перенос экземпляра в другую таймзону не поддерживается.
- **EXDATE в самой строке `rrule` не хранится**: список дат-исключений в одной колонке был бы одним значением для слияния по полям (два устройства, отменившие разные экземпляры, потеряли бы одно из них). Отдельные строки сливаются без потерь.
- Переопределение действует, только если его `original_start` — **настоящий** экземпляр правила (5.3); «висячие» переопределения (после смены правила или начала серии) игнорируются. Клиент при смене начала/правила серии удаляет такие строки.

## 4. Таблицы задач

### 4.1 `tasks`

| Колонка | Тип | Правила |
|---|---|---|
| `title` | text | обяз., 1–500, не пустое после trim |
| `notes` | text, null | markdown, ≤ 20 000 |
| `status` | enum | обяз.: `inbox` (Входящие) \| `todo` (К выполнению) \| `in_progress` (В работе) \| `done` (Выполнено) \| `cancelled` (Отменено) |
| `priority` | int, null | 1…5 (P1 — самый высокий), `null` — без приоритета |
| `due_date` | text, null | срок/день **без времени**, реальная дата |
| `due_at` | datetime, null | срок/начало **с временем** (UTC) |
| `due_tz` | text, null | обяз. вместе с `due_at`, иначе `null` |
| `duration_minutes` | int, null | 1…1440: длина блока в сетке (тайм-блокинг) и оценка; в UI по умолчанию 60 |
| `rrule` | text, null | раздел 5.1; требует `due_date` или `due_at` |
| `recurrence_mode` | enum, null | `schedule` (строго по расписанию) \| `after_completion` (следующий экземпляр от даты выполнения); обяз. при `rrule`, иначе `null` |
| `completed_at` | datetime, null | момент выполнения |
| `archived_at` | datetime, null | момент переноса в архив; `null` — не в архиве |
| `project_id` | uuid, null | мягкая ссылка (2.3) |
| `person_id` | uuid, null | мягкая ссылка (2.3) |
| `reminders` | json, null | 2.4; требует `due_date` или `due_at` |
| `sort_order` | int, null | 0…2^53, ручной порядок в списке |
| `source` | enum | обяз.: `manual` \| `ai` \| `telegram` \| `import` |

Межполевые проверки: `due_date` и `due_at` **взаимоисключающие**; `due_at` ⇒ `due_tz` (имя IANA), `due_tz` без `due_at` — ошибка; `rrule` ⇒ есть срок и `recurrence_mode`; `UNTIL` в тех же формах, что у событий (`YYYYMMDD` при `due_date`, момент при `due_at`) и не раньше срока.

**Три вида задач в календаре**: «с временем» (`due_at`, блок в сетке длиной `duration_minutes`), «с датой» (`due_date`, полоса «весь день» и список дня), «без даты» (оба `null`, бэклог «Без даты»).

**Статусы — правила клиента** (сервер допускает любой переход и не связывает `status` с `completed_at`, потому что слияние по полям иначе давало бы невалидные сочетания):
- Задача из быстрого ввода: `todo`, если указана дата или время, иначе `inbox`.
- Переход в `done`: клиент ставит `completed_at = now`; выход из `done` — `completed_at = null`. Оба поля уходят одной операцией.
- `cancelled` скрывается из обычных списков (фильтр «Отменённые»); `archived_at` ставится вручную или автоматически для `done`/`cancelled` старше N дней (настройка клиента); архив — отдельный экран.
- Просроченные (срок раньше «сейчас» и статус не `done`/`cancelled`) поднимаются в «Сегодня».

**Повторяющиеся задачи.** Экземпляры разворачиваются так же, как у событий (5.3): `due_date` ⇒ как «весь день», `due_at` ⇒ как событие с временем и длительностью `duration_minutes` (0, если не задана), таймзона — `due_tz`.
- `recurrence_mode = schedule`: выполнение экземпляра — строка `task_completions` (4.4), сама задача остаётся `todo`; когда экземпляров больше нет (исчерпан `COUNT`/`UNTIL`) и все выполнены — клиент переводит задачу в `done`.
- `recurrence_mode = after_completion`: при выполнении клиент **сдвигает срок** задачи на следующее значение и оставляет её `todo`. Следующее значение — первый экземпляр правила, который вычислен так, как если бы началом серии была **локальная дата выполнения** (с прежним временем суток), и у которого локальная дата **строго больше** даты выполнения (например, `FREQ=DAILY;INTERVAL=3` → через 3 дня; `FREQ=WEEKLY;BYDAY=MO` → ближайший понедельник). Строка `task_completions` пишется и здесь — для истории (`instance_date` = прежний срок).

### 4.2 `subtasks` — подзадачи (чек-лист)

Подзадача — **лёгкий пункт списка внутри задачи** (один уровень), а не полноценная задача: у неё нет срока, статуса и приоритета. Так сделано, потому что реестр Этапа 1 не поддерживает самоссылку таблицы, а карточка задачи (☰ 2/5) показывает именно прогресс пунктов.

| Колонка | Тип | Правила |
|---|---|---|
| `task_id` | uuid → `tasks` | обяз., неизм.; каскад |
| `title` | text | обяз., 1–500, не пустое |
| `done` | bool | обяз. |
| `position` | int | обяз., 0…2^53; порядок пунктов; клиент вставляет с шагом (например, 1024), при исчерпании перенумеровывает |

Если нужна «большая» подзадача со сроком — пользователь создаёт обычную задачу (и, при желании, ссылку на неё в заметках); отдельная связь «родитель–дочерняя задача» в Этапе 2 не предусмотрена (см. открытые вопросы).

### 4.3 `projects`, `people`, `tags` (минимальные)

| Таблица | Колонки | Замечания |
|---|---|---|
| `projects` | `title` (обяз., 1–200, не пустое), `color` (null, `#RRGGBB`), `archived` (bool, обяз.) | UUIDv7. Этап 4 добавит колонки |
| `people` | `name` (обяз., 1–100, не пустое), `archived` (bool, обяз.) | UUIDv7. Этап 4 добавит роли, контакты |
| `tags` | `name` (обяз., неизм., 1–50 символов **без пробельных символов и без `# @ + !`**), `color` (null, `#RRGGBB`) | `id = uuid5(ns("tags"), lower(name))` (2.2). **Переименования тегов нет**: имя неизменяемо, «переименовать» = создать новый тег и переставить связи |

Сопоставление `#проект`/`@человек` из быстрого ввода со строками таблиц — на клиенте: без учёта регистра, `_` приравнивается к пробелу; если совпадения нет, клиент предлагает создать. Тег `+тег` ищется по `lower(name)`; при отсутствии создаётся с детерминированным id.

### 4.4 `task_tags` и `task_completions`

**`task_tags`** — связь задача–тег как множество: `task_id` → `tasks` (неизм.), `tag_id` → `tags` (неизм.), `id = uuid5(ns("task_tags"), "{task_id}|{tag_id}")`. Снять тег = удалить строку (мягко); повторно поставить = восстановить ту же строку (`deleted_at: null`) или создать с тем же id. Удаление задачи или тега каскадом убирает строки связи.

**`task_completions`** — отметка экземпляра повторяющейся задачи:

| Колонка | Тип | Правила |
|---|---|---|
| `task_id` | uuid → `tasks` | обяз., неизм.; каскад |
| `instance_date` | text | обяз., неизм.; локальная дата экземпляра (в `due_tz`, для `due_date` — сама дата), реальная дата |
| `state` | enum | обяз.: `done` \| `skipped` |
| `completed_at` | datetime | обяз. |

`id = uuid5(ns("task_completions"), "{task_id}|{instance_date}")`. Ключ — дата: правила подмножества (без `BYHOUR`) дают не более одного экземпляра в сутки.

## 5. Повторения (RRULE)

### 5.1 Подмножество RFC 5545

В колонке хранится **только тело правила** (без префикса `RRULE:`, без `DTSTART`, `EXDATE`, `WKST`): `FREQ=WEEKLY;INTERVAL=2;BYDAY=TU;UNTIL=20261231T210000Z`. Части разделены `;`, имена — заглавными, каждая не более одного раза, пробелов нет, длина ≤ 200. Неподдерживаемое → `validation_failed`.

| Часть | Значения | Замечания |
|---|---|---|
| `FREQ` | `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY` | обяз. |
| `INTERVAL` | целое 1…999, без ведущих нулей | по умолчанию 1 |
| `COUNT` | целое 1…1000 | число экземпляров считается с первого; **отменённые экземпляры тоже входят в счёт**. Взаимоисключающе с `UNTIL` |
| `UNTIL` | событие/срок **с временем**: `YYYYMMDDTHHMMSSZ` (UTC-момент, **включительно**); **весь день**: `YYYYMMDD` (локальная дата, включительно) | другая форма → ошибка; не раньше начала серии |
| `BYDAY` | `WEEKLY`: `MO,TU,WE,TH,FR,SA,SU` (без порядковых номеров); `MONTHLY`: те же с необязательным порядковым номером `1…5` или `-1…-5` (`2TU`, `-1FR`) | для `DAILY` и `YEARLY` не поддерживается; без повторов; **не сочетается с `BYMONTHDAY`** |
| `BYMONTHDAY` | только `MONTHLY`: `1…31`, `-1…-31`, список через запятую | без повторов |

**Не поддерживаются** (ошибка): `BYSETPOS`, `BYMONTH`, `BYYEARDAY`, `BYWEEKNO`, `BYHOUR`/`BYMINUTE`/`BYSECOND`, `WKST`, частоты чаще суток. **Неделя — всегда с понедельника** (`WKST=MO`).

Значения по умолчанию: `WEEKLY` без `BYDAY` — день недели начала серии; `MONTHLY` без `BYDAY`/`BYMONTHDAY` — число месяца начала серии; `YEARLY` — месяц и число начала серии. **Несуществующие даты пропускаются**, а не сдвигаются: `BYMONTHDAY=31` — только в месяцах с 31 днём; ежемесячное «30-е» пропускает февраль; `5FR` — только в месяцах с пятой пятницей; ежегодное 29 февраля — только в високосные годы. «Последний день месяца» — `BYMONTHDAY=-1`, «последняя пятница» — `BYDAY=-1FR`. Векторы: `rrule_validate.json`, `rrule_expand.json`.

### 5.2 Семантика

- Правило применяется к **настенному времени `tz`**: 09:30 по Берлину остаётся 09:30 после перехода на летнее время, а UTC-момент меняется (1.1). Для «весь день» — к датам.
- Начало серии — первый экземпляр (3.2). Длительность экземпляра — `end − start` первого экземпляра (в UTC для событий с временем, в днях для «весь день»).
- `original_start` экземпляра — его UTC-момент **после** применения 1.1 (для «весь день» — дата).

### 5.3 Алгоритм развёртки (нормативный)

Вход: событие (`all_day`, `tz`, `start`, `end`, `rrule`, `title`), множество отменённых `original_start` (`cancelled = true` в `event_overrides`), переопределения (остальные строки `event_overrides`), окно `[from, to)` (полуоткрытое; моменты или даты — по типу события). Выход — экземпляры `{original_start, start, end, title}`, пересекающие окно, по возрастанию `(start, original_start)`.

1. Породить исходные экземпляры правила по возрастанию: настенные времена от начала серии (`FREQ`, `INTERVAL`, `BYDAY`, `BYMONTHDAY`, `COUNT`), затем для события с временем — в UTC по 1.1. `UNTIL` отсекает экземпляры позже него (включительно); `COUNT` отсекает по счёту до перевода в UTC. Без `rrule` — ровно один экземпляр (начало события).
2. Идти по экземплярам, пока `original_start < to`. Пропускать отменённые. Экземпляры с переопределением на этом шаге пропускаются (см. шаг 3). Остальные включать в результат, если они **пересекают окно** (ниже).
3. Для каждого неотменённого переопределения, чей `original_start` — настоящий экземпляр правила (пройден на шаге 1): взять `start/end` из переопределения (если `start_*` не `null`), иначе исходные; `title` — из переопределения, если не `null`, иначе из события; включить, если **итоговое** время пересекает окно. Так экземпляр, перенесённый в окно из далёкого прошлого/будущего, не теряется, а перенесённый из окна — исчезает. Если `cancelled` и переопределение относятся к одному ключу — побеждает `cancelled`.
4. Переопределение для несуществующего экземпляра игнорируется.

**Пересечение окна.** Событие с временем: `start < to` **и** `end > from`; экземпляр нулевой длины (`end == start`) пересекает окно, только если `from ≤ start < to`. «Весь день»: `start_date < to` **и** `end_date + 1 день > from`.

Производительность: клиент кэширует развёрнутые экземпляры на видимый диапазон; шаг 1 можно начинать не с начала серии, если реализация умеет пропускать (`INTERVAL`/`BYDAY`), лишь бы результат совпадал с векторами.

### 5.4 Правки повторяющегося события (клиент)

Диалог «Только это · Это и следующие · Все в серии» (02, 5.1.4):

- **Только это** — создать/обновить строку `event_overrides` для экземпляра; «удалить только это» — `cancelled = true`; «вернуть» — удалить строку переопределения.
- **Все в серии** — правка самого события. Если изменились начало, `tz` или правило, переопределения, чей `original_start` перестал быть экземпляром, клиент удаляет (они всё равно игнорируются).
- **Это и следующие** — разрез серии в экземпляре с ключом `K`: (1) если `K` — первый экземпляр, это правка «Все»; (2) иначе у старого события правило получает `UNTIL` = момент на секунду раньше `K` (для «весь день» — дата накануне `K`); если у старого события был `COUNT`, он заменяется на `UNTIL`, а новому достаётся `COUNT` минус число уже пройденных экземпляров; (3) создаётся **новое событие** (новый UUIDv7) с началом = (изменённый) экземпляр `K`, тем же правилом без `UNTIL` и остатком `COUNT`; (4) переопределения старого события с `original_start ≥ K` пересоздаются у нового события (новые детерминированные id), у старого — удаляются. Всё это — одна локальная транзакция.

## 6. Чередование недель (чёт/нечёт)

**Решение.** Чередование — это **обычное недельное повторение с интервалом цикла**: `FREQ=WEEKLY;INTERVAL=N;BYDAY=…`, где `N` — длина цикла (2 для чёт/нечёт), а чётность серии задаёт её **начало** (первый экземпляр). Никаких отдельных таблиц шаблонов и никакой ссылки события на «настройку недели» нет: развёртка, исключения и переопределения работают единым механизмом (5.3), события переживают смену настроек. Шаблоны расписания (`ScheduleTemplate`, `TemplateSlot`, `WeekPlanOverride` из 01) приходят в Этапе 7 и будут **компилироваться в такие же события** (`source = template`).

**Настройка цикла** — ключ `user_settings` **`calendar.week_cycle`**, значение (json):

```json
{"length": 2, "week1_start": "2026-08-31", "labels": ["Нечётная", "Чётная"],
 "shifts": [{"from": "2026-11-02", "weeks": 1}]}
```

| Поле | Правила |
|---|---|
| `length` | целое 1…8; `1` — цикл выключен |
| `week1_start` | любая дата недели №1 (нормализуется к понедельнику этой недели); в UI: «Неделя А начинается: 1 сентября 2026» |
| `labels` | необязательно; `length` непустых строк ≤ 30 символов; по умолчанию для 2 — «Нечётная», «Чётная», иначе «Неделя 1…N» |
| `shifts` | необязательно; записи «сдвинуть чётность»: с недели, содержащей `from`, номер недели цикла увеличивается на `weeks` (может быть отрицательным) |

Ключа нет ⇒ **цикл выключен** («каждую неделю одинаково», решение 04, #6). Сервер значение не проверяет (это общий json Этапа 1); проверки — на клиенте.

**Номер недели цикла** для любой даты (`shared-test-vectors/calendar/week_cycle.json`, `op: week_number`):

```
monday(d)    = d − weekday(d)                       # weekday: понедельник = 0
weeks        = floor_div(monday(d) − monday(week1_start), 7)   # в днях: делить вниз, не к нулю
weeks       += сумма shift.weeks по всем shift, у которых monday(shift.from) ≤ monday(d)
week_number  = (weeks mod length) + 1               # mod неотрицательный (для дат до опоры тоже)
```

**Как показывается.** Пилюля с названием недели рядом с периодом (`labels[week_number − 1]`); в месяце — метка у строки недели; на «Сегодня» — подзаголовок; блок серии, у которой `FREQ=WEEKLY` и `INTERVAL > 1`, помечен иконкой `repeat-2`, в деталях — «по нечётным неделям, Вт 10:40–12:10» (номер недели серии = `week_number(дата первого экземпляра)`; если `INTERVAL ≠ length`, пишем «каждые N недели» без названия).

**Создание** серии в редакторе («Нечётная / Чётная / Каждую», день недели, время): начало серии = `first_date(after, weekday, week, cycle)` (`op: first_date` в векторах): ближайшая дата ≥ выбранной, у которой день недели совпал и номер недели цикла равен выбранному; правило `FREQ=WEEKLY;INTERVAL={length};BYDAY={дни}`; при нескольких днях начало серии — самый ранний подходящий день недели. «Каждую» — обычное `FREQ=WEEKLY;BYDAY=…`.

**«Пропустить неделю»** (каникулы) для недели `W` (пн–вс): для каждой серии, имеющей экземпляр в `W`, клиент создаёт `event_overrides` с `cancelled = true` на этот экземпляр (детерминированные id — повтор с другого устройства безопасен); отмена действия — удаление этих строк.

**«Сдвинуть чётность»** с понедельника `D` (вуз объявил сдвиг): (1) в `calendar.week_cycle` добавляется запись `shifts += {from: D, weeks: 1}` (бейджи и подсказки после `D` меняются, прошлые остаются); (2) для каждой серии чередования (`INTERVAL = length`), активной на `D`: старая серия получает `UNTIL` (как в 5.4, «Это и следующие», ключ — первый экземпляр ≥ `D`), новая серия создаётся с тем же правилом и началом = (первый экземпляр старой серии ≥ `D`) + 7 суток. Векторы серий: `alt_*` в `rrule_expand.json`.

## 7. Праздники РФ

**Решение: встроенные статические данные, не синхронизируемая таблица.** Клиенту они нужны офлайн с первого запуска, меняются раз в год, а приложение личное и ставится вручную — обновление данных = обновление приложения. Слой «Праздники России» — системный календарь `holidays_ru` (3.1) только для видимости; событий-строк у него нет, клиент рисует дни из данных.

**Файл.** Канонический — `shared-data/calendar/holidays_ru.json`; клиент кладёт **байт-в-байт копию** в `app/assets/` (Dart-тест сравнивает копию с каноническим файлом; Flutter не умеет брать assets вне пакета). Формат:

```json
{"version": 1, "updated": "2026-09-30", "description": "…",
 "years": {"2026": {"status": "official", "source": "…",
                    "days": [{"date": "2026-01-01", "type": "holiday", "name": "Новогодние каникулы"}, …]}}}
```

`type`: `holiday` — праздничный день на своей дате; `transfer_off` — дополнительный выходной по переносу (всегда будний день); `working_weekend` — рабочая суббота/воскресенье (в 2026–2027 нет). Год `status`: `official` — по постановлению Правительства; `provisional` — расчёт по ст. 112 ТК РФ (праздник, выпавший на выходной, переносится на ближайший рабочий день), **подлежит замене**, когда выйдет официальное постановление.

**Правило дня** (`shared-test-vectors/calendar/holidays.json`): запись `holiday`/`transfer_off` ⇒ выходной, `working_weekend` ⇒ рабочий; даты без записи (и годы, которых нет в файле) ⇒ выходной ровно в субботу и воскресенье. Имя — из записи, иначе `null`. Данные 2026 — официальные (247 рабочих дней), **2027 — `provisional`**.

**Как обновлять** (раз в год, обычно осенью после постановления): (1) добавить/заменить блок года в `holidays_ru.json`, поставить `status: "official"`, поднять `updated`; (2) `cd backend && uv run pytest tests/test_calendar_holidays.py` — проверки согласованности (даты в своём году, без дублей, `transfer_off` только в будни, ≥ 244 рабочих дней в году); (3) пересобрать векторы `cd backend && uv run python -m tests.calendar_vectors_gen`, посмотреть диф глазами; (4) обновить копию в `app/assets/` и выпустить приложение. Сервер файла не читает.

## 8. Быстрый ввод

Разбор — **на клиенте, офлайн**; формат — одна строка. Результат — **предложение**, которое интерфейс показывает чипами (дата, время, приоритет, проект…) до сохранения; пользователь может убрать любой чип. Эталон — `backend/src/tasker/calendar/reference_quick_input.py`; векторы — `shared-test-vectors/calendar/quick_input.json` (≥ 100 случаев).

**Вход:** `text` и `now` — локальное время устройства в часовом поясе пользователя, до минуты (`YYYY-MM-DDTHH:MM`).
**Выход:** `{title, priority, project, people, tags, date, time, duration_minutes}`: `priority` — 1…5 или `null`; `project` — строка или `null`; `people`, `tags` — списки строк; `date` — `YYYY-MM-DD` или `null`; `time` — `HH:MM` или `null`; `duration_minutes` — целое или `null`. `date` без `time` — задача с датой (`due_date`), с `time` — с временем (`due_at`); `duration_minutes` ложится в `tasks.duration_minutes`.

### 8.1 Алгоритм

1. **Токены.** Разделители — только U+0020, U+0009, U+000A, U+000D, U+00A0, U+202F, U+2009 (последовательность считается одним разделителем; пустые токены отбрасываются).
2. **Метки** (по исходным токенам, регистр сохраняется). Токен целиком равен:
   - `!1`…`!5` — приоритет; **последний** побеждает; токен убирается. `!0`, `!6`, `Срочно!1`, `!` — обычные слова;
   - `#имя` — проект (**последний** побеждает); `@имя` — человек; `+имя` — тег. У имени отрезаются хвостовые символы `, . ; :`; остаток должен быть непустым, а его первый символ — буква (Unicode L*) для `@` и `+`, буква или десятичная цифра (Nd) для `#`. Иначе токен остаётся словом названия (`+1`, `#!`, `@`). Люди и теги: без повторов без учёта регистра (остаётся первое написание). Метка `_` в имени не преобразуется (сопоставление — в 4.3).
   Метки убираются, остальные токены `R` идут дальше в исходном порядке.
3. **Ключ токена** `key(t)` = `lowercase(t)`, `ё → е`, без хвостовых `, ; :` (точка остаётся: `15.10.`). Все сопоставления — по ключам, названием остаются **исходные** токены.
4. **Фразы.** Слева направо по `R`; в каждой позиции пробуются шаблоны в порядке Ф1–Ф5 (раздел 8.2), берётся **первый подошедший**. Фраза задаёт **компоненты**: дата (`date`), время (`time`), длительность (`duration`); если хоть один из её компонентов уже занят раньше, фраза **отвергается**: её токены остаются в названии, другие шаблоны в этой позиции не пробуются. Принятая фраза убирает свои токены; если она задала дату или время, то стоящий **непосредственно перед ней и не убранный** токен-предлог из `в, во, на, к, до, с` тоже убирается («сдать до 15 октября» → «сдать»). Фраза только с длительностью предлог не убирает.
5. **Голое «в N»** (после прохода 4, если время ещё не задано): пара токенов `в`, `N` (0…23, только цифры), не убранная; принимается, если **найдена дата**, либо это **последние два токена** `R`. Первая подходящая пара задаёт время `N:00`. («завтра в 15 позвонить» — время 15:00; «в 15 позвонить» без даты — обычное название; «позвонить в 15» — время.)
6. **Итоговая дата.** Если есть время, но нет даты: сегодня, если время **строго позже** `now`, иначе завтра. Только дата — время `null`.
7. **Название** — оставшиеся токены через один пробел (может быть пустым).

### 8.2 Фразы

`N` — только цифры ASCII; `«…»` — слово из списка (ключи, слова с `ё` пишутся через `е`).

**Ф1. «через»** (`сегодня` = дата `now`):

| Шаблон | Результат |
|---|---|
| `через неделю` | дата +7 суток |
| `через месяц` | +1 месяц, число сжимается до конца месяца (31 янв → 28 фев) |
| `через час`, `через полчаса` | момент `now` + 60 / 30 минут: **и дата, и время** |
| `через N {день, дня, дней}`, N 1…365 | дата +N суток |
| `через N {неделю, недели, недель}`, N 1…52 | дата +7N суток |
| `через N {месяц, месяца, месяцев}`, N 1…24 | +N месяцев (сжатие как выше) |
| `через N {минуту, минуты, минут, мин}`, N 1…1440 | `now` + N минут: дата и время |
| `через N {час, часа, часов, ч}`, N 1…72 | `now` + N часов: дата и время |

`через день` (без числа) — не фраза (по-русски это «через сутки»/«через день» неоднозначно).

**Ф2. День недели:** `[в|во] [следующий|следующую|следующее] ДЕНЬ`, где ДЕНЬ ∈ понедельник, вторник, среда, среду, четверг, пятница, пятницу, суббота, субботу, воскресенье, а также `пн вт ср чт пт сб вс`. Без «следующий» — **ближайшая дата строго после сегодня** (в среду «в среду» — через 7 суток). С «следующий…» — этот день **следующей недели пн–вс**. Предлог `в/во` входит в фразу.

**Ф3. Дата:**

| Шаблон | Результат |
|---|---|
| `сегодня`, `завтра`, `послезавтра` | +0/1/2 суток |
| `в выходные`, `на выходные`, `на выходных` | сегодня, если сегодня сб/вс, иначе ближайшая суббота |
| `ГГГГ-ММ-ДД` | эта дата (должна существовать) |
| `Д.М`, `ДД.ММ`, `Д.М.ГГ`, `ДД.ММ.ГГГГ` | дата; двузначный год = 20ГГ; без года — **эта дата этого года, если она не в прошлом, иначе следующего**; если такой даты нет ни там, ни там (29.02, 31.02) — не фраза |
| `Д МЕСЯЦ [ГГГГ]` | то же по названию месяца (родительный падеж или сокращение); год — токен `20ГГ` сразу после месяца |

Месяцы: января янв, февраля фев, марта мар, апреля апр, мая, июня июн, июля июл, августа авг, сентября сен сент, октября окт, ноября ноя нояб, декабря дек. Дата в прошлом при явном годе допустима (`15.10.2020`). **Известная неоднозначность:** `1.5` читается как дата 1 мая; интерфейс показывает чип, пользователь его убирает.

**Ф4. Время:**

| Шаблон | Результат |
|---|---|
| `с ЧЧ:ММ до ЧЧ:ММ` | время начала **и длительность** (конец строго позже начала, иначе не фраза) |
| `ЧЧ:ММ-ЧЧ:ММ` (дефис, U+2013 или U+2014 без пробелов) | то же |
| `ЧЧ:ММ` (ч 0…23, часы из одной или двух цифр, минуты из двух) | время |
| `[в\|к] N [час\|часа\|часов] {утра\|дня\|вечера}` (N 1…12) | утра: `N mod 12`; дня, вечера: `N mod 12 + 12` («в 12 утра» = 00:00, «в 12 дня» = 12:00, «в 3 часа дня» = 15:00) |
| `в\|к N {час\|часа\|часов}` (N 0…23, без периода) | `N:00` |
| `N [час\|часа\|часов] {утра\|дня\|вечера}` без предлога | как выше («9 утра») |
| `утром`, `днем` (`днём`), `вечером` | 09:00, 13:00, 19:00 |

Голое «в N» — шаг 5 раздела 8.1.

**Ф5. Длительность:** `на час` (60), `на полчаса` (30), `на полтора часа` (90), `на N {минуту, минуты, минут, мин}` (N 1…1440), `на N {час, часа, часов, ч}` (N 1…24, ×60).

### 8.3 Не поддерживается

Повторения («каждый день»), относительные даты вроде «на следующей неделе», «в конце месяца», «вчера», часовые пояса, названия месяцев в именительном падеже, кавычки в проектах (проект с пробелом пишется через `_`). Расширение — только вместе с векторами и обеими реализациями в одном изменении.

## 9. Проверки сервера и коды ответов

Все ошибки значений — обычные отказы операции (Этап 1, 3.3), тело не повторяется:

| Ситуация | `code` |
|---|---|
| тип, длина, формат (`#RRGGBB`, дата, имя тега), значение перечисления, `null` в обязательной колонке | `invalid_field` (`message` называет колонку) |
| межполевая проверка: даты и моменты (2.4, 3.2, 3.3, 4.1), `rrule`, неизвестная `tz`, пустой заголовок, `system_key` | `validation_failed` |
| попытка изменить `event_id`, `original_start`, `task_id`, `tag_id`, `instance_date`, `system_key`, `tags.name` | `immutable_field` |
| id не совпадает с правилом 2.2 или не UUIDv7 | `invalid_id` |
| родитель не существует (событие без календаря, переопределение без события…) | `parent_not_found` |
| создание без обязательных колонок или без `created_at` | `missing_fields` |

## 11. Открытые вопросы

1. **Подзадача-как-задача** (свой срок, статус, приоритет, вложенность) не поддержана: реестр Этапа 1 не умеет самоссылку таблицы. Если понадобится — отдельное решение (расширение реестра или связь «задача → задача» без каскада).
2. **Переименование тегов** отсутствует из-за детерминированного id (2.2). Альтернатива — обычный UUIDv7 и отказ от схлопывания одноимённых тегов, созданных на двух офлайн-устройствах.
3. **Праздники 2027** рассчитаны по ст. 112 ТК РФ и помечены `provisional`; заменить, когда выйдет постановление.
4. **Версия схемы клиента.** Этап 2 только добавляет таблицы; вопрос, повышать ли `min_client_schema_version`, решает оркестратор вместе с изменениями Этапа 1 (клиент Этапа 1 должен игнорировать строки неизвестных таблиц в pull).
5. **Валидация значений `user_settings`** (`calendar.week_cycle`, `calendar.all_day_reminder_time`) на сервере невозможна без правки реестра Этапа 1 (сейчас проверяется только размер JSON); проверки — на клиенте.
