# Этап 6. Спецификация: Банки (уведомления, выписки, дедупликация)

> Контракт для сервера и Flutter-клиента. Решения — `docs/briefs/stage-6.md` (при расхождении действует он). Эталон — `backend/src/tasker/banks/` (`reference.py`, `notifications.py`, `statements.py`), общие векторы — `shared-test-vectors/banks/` (раздел 9). Финансы (счета, операции, статусы, `dedup_hash`) — `docs/specs/stage5_finance.md`.

## 0. Принципы

- Легального банковского API нет. Источники операций: **уведомления Android** (на устройстве), **выписки** (разбор на сервере), **ручная сверка** (Этап 5).
- Всё, что импортируется, сначала **черновик** (`status = draft`, `needs_review`): в суммы и аналитику входит только `confirmed` (Этап 5, 4.3). Деньги — целые копейки, валюта операции хранится только как признак «не рубли → `needs_review`» (колонки валюты в v1 нет).
- **Секреты и сырьё не хранятся на сервере.** Файл выписки разбирается в памяти и сразу забывается (раздел 6). Сырой текст уведомления остаётся на устройстве (30 дней) и не синхронизируется — на сервер уходит только распознанная операция.
- **Правила — данные, не код.** Новый формат уведомления — новая запись в `shared-data/banks/notification_rules.json`; новый банк выписки — новый профиль в `statement_profiles.json`. Общий движок Python (эталон) и Dart (клиент) один и тот же по поведению: на это есть векторы.
- Все эталонные функции чистые, детерминированные, без плавающей арифметики; Dart обязан дать **побайтно тот же** результат на `shared-test-vectors/banks/`.
- Время в строках — UTC `YYYY-MM-DDTHH:MM:SSZ`; «день» — по Москве (Этап 5, 0). Время в выписках и в тексте уведомлений считается **московским** (допущение, раздел 11).
- **Все образцы в этом этапе синтетические** (помечены `"synthetic": true` в файлах правил). Реальные уведомления и выписки заказчик пришлёт позже; каждый станет тестом.

Сервер читает их из `shared-data/` репозитория; в контейнере каталог монтируется и задаётся переменной `SHARED_DATA_DIR` (образ api содержит только `backend/src`).

## 2. Правила уведомлений

### 2.1 Формат `notification_rules.json`

```json
{"version": 1, "synthetic": true, "description": "…",
 "currencies": {"₽": "RUB", "$": "USD", …},
 "banks": [{"id": "tbank", "name": "Т-Банк", "packages": ["com.idamob.tinkoff.android"],
            "rules": [ {Rule}, … ]}]}
```

Пакет Android-приложения принадлежит ровно одному банку. Слушатель уведомлений обрабатывает **только** пакеты из этого списка (белый список расширяемый). Имена пакетов в стартовом наборе синтетические и подлежат проверке на устройстве заказчика.

`Rule`:

| Поле | Значение |
|---|---|
| `id` | уникальный в файле, `<банк>.<имя>` |
| `kind` | `expense` расход, `income` доход, `ignore` — служебное/рекламное уведомление, не операция |
| `title` | `null` (любой заголовок) или список допустимых заголовков (сравнение после очистки, 2.3, точное) |
| `pattern` | регулярное выражение по тексту (2.2); ищется `search`/`firstMatch` — якоря `^ $` ставит автор правила |
| `groups` | имя поля → номер группы шаблона: `amount` (обяз. у не-`ignore`), `currency`, `merchant`, `card_last4`, `balance`, `time` |
| `currency_fixed` | необяз.: валюта правила целиком (исключает группу `currency`) |
| `merchant_fixed` | необяз.: постоянный «мерчант» (например «Зарплата») вместо группы |
| `refund` | необяз., `true`: доход — возврат покупки |
| `ignore_case` | необяз., по умолчанию `false` |
| `samples` | ≥ 1 образец `{"title", "text", "expected": {…}}`; **каждое правило проверяется на своих образцах** (`expected` — подмножество результата) |

Порядок правил внутри банка — приоритет: побеждает первое подошедшее.

### 2.2 Переносимое подмножество регулярных выражений

Python `re` и Dart `RegExp` различаются в мелочах, поэтому правила пишутся в подмножестве (`pattern_problem` его проверяет; правило вне подмножества — ошибка данных):

- разрешено: литералы, `.`, классы `[…]` (с явными диапазонами `[0-9]`), группы `( )` и `(?: )`, `| ? * + {m} {m,} {m,n}` и их ленивые формы (после квантификатора допускается один `?`), якоря `^ $`, экранирование **знаков препинания** `\. \* \+ \? \( \) \[ \] \{ \} \| \^ \$ \\ \- \/`;
- запрещено: `\d \w \s \b` и любые другие буквенные экранирования (в Python `\d` — любые Unicode-цифры, в Dart — только ASCII), look-around, именованные группы, обратные ссылки, встроенные флаги `(?i)`, притягательные (possessive) квантификаторы `a*+ a++ a?+ a{1,2}+` и повтор квантификатора (`a+*`), `{`, не образующая квантификатор (`a{,3}` — в Python квантификатор, в Dart текст; литерал пишется `\{`), вложенные и пустые классы (`[[a]`, `[]a]`).

Цифры — только `[0-9]`; пробел внутри числа — обычный пробел (2.3 приводит к нему все пробельные символы).

### 2.3 Очистка текста перед сопоставлением

Заголовок и текст уведомления очищаются: символы `U+0020 U+00A0 U+202F U+2009 U+2007 U+0009 U+000D U+000A U+2028 U+2029 U+000B U+000C` заменяются обычным пробелом, серии пробелов схлопываются, края обрезаются. Другие символы не трогаются. Нельзя использовать «умный» `trim()`/`split()` по `\s` — только эти символы. (После очистки в тексте нет переводов строк, поэтому `.` ведёт себя одинаково в Python и Dart.)

### 2.4 Результат `parse_notification(package, title, text)`

- **Пакет неизвестен:** `{"status": "ignored", "bank": null, "rule_id": null, "reason": "unknown_package"}` — не наш банк, ничего не делаем.
- **Правило `ignore`:** `{"status": "ignored", "bank", "rule_id"}`.
- **Банк известен, правила нет:** `{"status": "unrecognized", "bank", "rule_id": null, "reason": "no_rule"}` — уведомление идёт в «Требует проверки» с исходным текстом (локально); из него можно создать операцию вручную. Если правило подошло, но сумма не читается (`bad_amount`) или валюта неизвестна (`unknown_currency`) — тоже `unrecognized` с причиной.
- **Разобрано:** `{"status": "parsed", "bank", "rule_id", "kind", "refund", "amount" (копейки, int, > 0), "currency", "card_last4" | null, "merchant" | null, "balance" (копейки) | null, "time" ("HH:MM") | null, "needs_review", "review_reason"}`.
  - сумма и остаток читаются правилом денег `parse_amount` (Этап 0; векторы `money`);
  - валюта: `currency_fixed`, иначе символ из группы `currency` по таблице `currencies`, иначе `RUB`;
  - `needs_review = true` и `review_reason = "foreign_currency"`, если валюта не `RUB` (суммы в чужой валюте в рублёвые счета не вносим без проверки);
  - `time` — только если группа есть и значение — реальное время.

### 2.5 Что делает клиент с результатом

- `parsed` → операция `source = notification`, `status = draft`; счёт — по `card_last4` среди карточных счетов (`accounts.card_last4`, Этап 5); нет совпадения или `needs_review` → `status = needs_review` и выбор счёта пользователем. Время операции — время уведомления (`posted_at`), а при группе `time` — оно в тот же день.
- `balance` → точка сверки `balance_checkpoints` с `source = notification` (Этап 5, 4.4) на момент операции.
- `kind = income` с `refund = true` — возврат: обычный доход, но автокатегория берётся как у расхода того же мерчанта (клиент подставляет категорию расхода, если у возврата нет своей).
- Дедупликация и склейка — раздел 4. Две одинаковые покупки подряд — две операции (хеши различаются порядковым номером, 4.2).

## 3. Нормализация мерчанта

`normalize_merchant(text) -> string` — **общая** функция (хеши, сопоставление, правила категорий, векторы `merchants.json`).

1. Каждый символ приводится к алфавиту: `a-z`, `0-9`, `а-я` сохраняются; ASCII-заглавные `A-Z` и кириллические `А-Я` понижаются (`+32`); `ё/Ё` → `е`; **любой другой** символ (пробелы, кавычки всех видов, `* # № . , -` и т. д.) — разделитель. (Свой «безопасный» регистр, а не `toLowerCase`: он различается между средами.)
2. Строка делится на слова по разделителям.
3. Удаляются слова из `legal_forms` (в любом месте: `ооо`, `ип`, `llc` …). Если не осталось ничего — слова сохраняются.
4. С **конца** повторяются отрезания: слово из `country_codes` (`rus`, `ru`, `рф` …), слово из одних цифр (номер терминала/магазина), город из `cities` (последовательность слов, например `санкт петербург`). Цифры в начале и в середине остаются («7 эльдорадо», «магнит 5 косметик»). Если после этого не осталось ничего — берётся результат шага 3.
5. Слова соединяются одним пробелом.

Функция идемпотентна (`normalize(normalize(x)) = normalize(x)`), пустой вход даёт пустую строку.

Пример: `ООО «Пятёрочка» №1234 Москва RUS` → `пятерочка`; `PYATEROCHKA 1234 MOSKVA` → `pyaterochka`; `McDonald's` → `mcdonald s`.

Латиница и кириллица **не сопоставляются** между собой (нет транслитерации); см. раздел 11.

## 4. Дедупликация и сопоставление

### 4.1 Идентификаторы

- `external_id` — идентификатор операции, если источник его даёт (некоторые выписки).
- `dedup_hash` — когда идентификатора нет: **первые 32 hex-символа SHA-256** от UTF-8 строки `account_id|tail`, где `tail = kind|amount|minute|merchant_norm`:
  - `kind` — `expense`/`income`; `amount` — копейки десятичным целым;
  - `minute` — момент операции в UTC до минуты, `YYYY-MM-DDTHH:MM` (секунды и доли отбрасываются);
  - `merchant_norm` — `normalize_merchant(merchant)` (для пустого мерчанта — пустая строка).
  Пример: `acc|expense|123456|2026-10-03T11:30|пятерочка`. Хеш привязан к счёту (как и ключ `dedup_key`, Этап 5, 7.2).
- Строка «только дата» (выписки часто без времени) получает момент **12:00 по Москве** (`09:00Z`) этой даты и признак `date_only = true`.

### 4.2 Одинаковые операции одного пакета

Две настоящие одинаковые покупки (две чашки кофе за день по выписке только с датой) совпали бы по хешу. Поэтому внутри одной пачки кандидатов `i`-я повторная (`i ≥ 1`) получает суффикс: `tail|i` (`ordinal`). Повторный импорт той же выписки даёт те же хеши, и обе покупки находятся как дубликаты, а не схлопываются в одну.

### 4.3 `classify_candidates(account_id, candidates, existing)`

Кандидат — `{kind, amount, currency, occurred_at, date_only, merchant, external_id}`; существующая операция — строка `transactions` (`id, account_id, kind, amount, occurred_at, merchant, source, status, external_id, dedup_hash`). Учитываются **живые** операции того же счёта любых статусов (включая черновики). Результат по кандидату:

`{"index", "action": "new"|"duplicate"|"merge", "existing_id", "reason": "external_id"|"hash"|"fuzzy"|null, "similarity", "dedup_hash", "needs_review", "review_reason", ["refine"]}`.

Порядок шагов:

1. **Точно:** тот же `external_id`, затем тот же `dedup_hash` (кандидату вычисляется хеш с его порядковым номером) → `duplicate`. Две операции с **разными** `external_id` — разные операции, всегда.
2. **Нечётко** (для оставшихся): строка ещё не занята; тот же `kind`; **та же сумма до копейки**; разница моментов **≤ 48 часов** (включительно); `similarity` мерчантов ≥ **60**. Совпадения берутся от лучшего: большее сходство, затем меньшая разница времени, затем `id` строки, затем номер кандидата; каждая существующая строка обслуживает **одного** кандидата. Если у существующей `source = statement` — `duplicate`, иначе (уведомление, ручная) — **`merge`**: выписка уточняет черновик, а не создаёт вторую операцию. `refine` у `merge` — что выписка уточняет: `occurred_at` (только если у строки выписки есть время и оно отличается) и `merchant` (если выписка называет мерчанта и он отличается).
3. **Чужая валюта** (`currency ≠ RUB`): нечётко не сопоставляется, `needs_review = true`, `review_reason = "foreign_currency"`. По точному совпадению (шаг 1) всё же `duplicate`.
4. Остальное — `new`.

Близкие, но не равные суммы (`1234,50` и `1234,00`) — **не** совпадение. Возврат (другой `kind`) — не совпадает с покупкой.

### 4.4 Сходство мерчантов

`similarity(a, b)` двух нормализованных имён — целое 0…100: пустое имя → 0; равные → 100; одно имя — начало другого по **словам** → 90; иначе коэффициент Дайса по биграммам символов имён без пробелов: `2·|общие| · 100 // (|A| + |B|)` (мультимножества, вниз). `merchant_similarity` (сырые строки): если у одной из сторон имени нет, возвращает **60** («не можем сравнить» — ровно порог).

### 4.5 Переводы между своими счетами

`match_transfers(transactions, window_seconds = 600)`: пара — расход на одном счёте и доход на **другом** с той же суммой, не дальше `window_seconds` друг от друга; для строк, у которых одна из сторон `date_only`, требуется одна и та же московская дата. Не участвуют чужая валюта, операции с `debt_id` и уже существующие переводы. Каждая строка входит в одну пару, ближайшие пары первыми (разница, затем `expense_id`, затем `income_id`). Результат — `[{"expense_id", "income_id", "delta_seconds"}]` — **предложение** склеить в один `transfer` (Этап 5, 4.1); решение за пользователем.

## 5. Выписки

Форматы: **CSV**, **XLSX**, **PDF с ограниченной линиями таблицей** (pdfplumber). Реальные выписки Т-Банка и ВТБ заказчик пришлёт; до этого — каркас и синтетические образцы (`backend/tests/data/banks/`).

1. **Формат** определяется по первым байтам (`%PDF-` → pdf; `PK\x03\x04` → xlsx; иначе csv). Заданный параметром `format` должен совпасть (`statement_format_mismatch`).
2. **Таблицы.** CSV: UTF-8 (с BOM) или cp1251, разделитель — самый частый из `;`, табуляции, `,`. XLSX: каждый лист; даты Excel → `ДД.ММ.ГГГГ[ ЧЧ:ММ:СС]` (полночь = «без времени»), числа с плавающей точкой переводятся в строку без потерь. PDF: таблицы страниц; строки вне таблиц (первые 5 строк документа, «за период с … по …», «остаток на конец …») добавляются как служебные.
3. **Заголовок.** Среди первых 60 строк выбирается лучшая пара (профиль, строка) из `statement_profiles.json`: профилю нужны колонки даты и суммы (колонка суммы, либо `amount_account`, либо пара «расход/приход»); больше распознанных колонок — лучше; упоминание банка выше заголовка — небольшой плюс. Профили `tbank`, `vtb`, `generic`; параметр `bank` ограничивает выбор указанным профилем и `generic`. Заголовки сравниваются без регистра, только буквы и цифры (`ё = е`).
4. **Строка → кандидат.** Дата `ДД.ММ.ГГГГ[ ЧЧ:ММ[:СС]]`, `ДД.ММ.ГГ` или `ГГГГ-ММ-ДД[ …]`, год ≥ 2015. Сумма: сначала «сумма в валюте счёта» (`amount_account`), иначе «сумма операции»; знак `−` → расход, `+` → доход; колонки «расход»/«приход» — по колонке; `(75,00)` — отрицательное; нули пропускаются. Если у операции чужая валюта, а сумма в валюте счёта есть — берётся она, в `original_amount`/`original_currency` — исходная, `needs_review = true`. Статус: если у профиля есть `ok_statuses`, строки с другим статусом (`FAILED` и т. п.) пропускаются. Описание → `merchant` (≤ 200 символов); `MCC` (4 цифры); `card_last4` — последние 4 цифры ячейки карты; `external_id`; `balance_after`.
5. **Время.** Время в выписке — московское; `occurred_at = локальное − 3 ч`. Строка только с датой: `date_only = true`, момент 12:00 МСК.
6. **Служебное.** Период (`с ДД.ММ.ГГГГ по ДД.ММ.ГГГГ` или min/max дат кандидатов), `cards` (все `card_last4` строк) и **остаток на конец периода** (`остаток на конец [периода] <сумма>` в строках вне таблицы) → `closing_balance = {"amount", "at": конец московского дня периода}`; клиент создаёт точку сверки `source = statement` (Этап 5, 4.4).
7. **Для каждого кандидата** сервер добавляет: `index`, `row` (номер строки таблицы), `merchant_norm`, `dedup_tail` (4.1–4.2; клиент считает хеш `sha256(account_id|dedup_tail)[:32]`, когда выбрал счёт), `suggested_category` (раздел 8). Пропущенные строки — в `skipped: [{"row", "reason"}]` (причины: `status …`, `bad_date`, `no_amount`; пустые строки и «итого» без суммы пропускаются молча).
8. **Дальше клиент** (мастер): сопоставляет счёт по `cards`, считает хеши, вызывает `classify_candidates` против локальных операций (дубликаты помечены, `merge` — предложение уточнить черновик), показывает категории; подтверждённые кандидаты создаются обычными операциями `source = statement`.

## 6. Эндпоинт `POST /banks/statements/parse`

- Авторизация обычная (токен устройства + `X-Client-Schema-Version`): без токена `401`, отозванное устройство `401 device_revoked`.
- Тело запроса — **сырые байты файла** (без multipart). Query: `format` = `csv|xlsx|pdf` (необяз.), `bank` = `auto|tbank|vtb|generic` (по умолчанию `auto`).
- **Лимит размера** — `BANKS_STATEMENT_MAX_BYTES` (по умолчанию 10 МБ): по `Content-Length` заранее и при чтении потоком → `413 payload_too_large` (`details.max_bytes`). Лимиты разбора: ≤ 20 000 строк, ≤ 100 страниц PDF, XLSX ≤ 64 МБ в распакованном виде, ≤ 20 листов, ≤ 60 столбцов (дальше ячейки отбрасываются), ≤ 200 000 ячеек в сумме (пустой хвост строки не считается; заявленный в файле `<dimension>` игнорируется: подделанный `A1:XFD1048576` иначе раздувает каждую строку), общий срок разбора 20 с (поток останавливается сам, API отвечает не позже чем через 30 с) → `422 statement_too_large`.
- **Файл не хранится**: разбор идёт в памяти (в потоке, `to_thread`), на диск не пишется, в БД ничего не создаётся (сервер не создаёт операций — только возвращает кандидатов). Тест проверяет отсутствие временных файлов и новых строк.
- Ответы: `200` — `{"format", "bank", "period", "closing_balance", "cards", "candidates": […], "skipped": […]}`; `400 empty_file`; `422 statement_unrecognized` (нет таблицы с датой и суммой), `statement_unreadable` (файл повреждён), `statement_format_mismatch`, `statement_too_large`, `validation_error` (параметры).
- Правила автокатегорий пользователя (раздел 7) читаются из БД и применяются к `suggested_category`.

## 7. Таблица `merchant_category_rules` (синхронизируемая)

Служебные поля, мягкое удаление и общие правила — как у всех таблиц (Этап 1). Родителей нет.

| Колонка | Тип | Правила |
|---|---|---|
| `merchant_key` | text 1–200, **неизменяем** | уже нормализованное имя: `normalize_merchant(key) == key` (иначе `validation_failed`) |
| `match_type` | enum, **неизменяем** | `exact` — мерчант равен ключу; `contains` — слова ключа идут подряд внутри слов мерчанта |
| `kind` | enum, **неизменяем** | `expense`, `income` — вид операций, к которым правило применяется |
| `category_id` | uuid | **мягкая ссылка** на `categories`; меняется свободно (пользователь передумал) |

`id` — детерминированный: `uuid5(ns("merchant_category_rules"), kind|match_type|merchant_key)` (`ns` как в Этапе 2, 2.2); иначе `invalid_id`. Два устройства, запомнивших один мерчант, создают одну строку. Создание правила — галочка «запомнить для этого мерчанта» при подтверждении операции.

## 8. Автокатегории

`suggest_category(merchant, mcc, kind, user_rules)` → `{"source": "user"|"keyword"|"mcc"|null, "category_id", "system_key"}`:

1. **Правила пользователя** вида `kind`: `exact` с равным ключом, затем `contains` (больше слов в ключе — раньше, затем длиннее ключ, затем `id`). Даёт `category_id` правила.
2. **Ключевые слова** `category_dictionary.json` (`keywords`, порядок записей — приоритет): слово (несколько слов подряд) найдено целыми словами среди слов мерчанта; ключ категории должен быть того же вида (`expense.*`/`income.*`). `category_id` = `uuid5` предустановленной категории (Этап 5, 3.2).
3. **MCC** (`mcc`): код → ключ категории того же вида.
4. Иначе — `null` (категорию выберет пользователь).

Словарь стартовый и небольшой; пользовательские правила его перекрывают.

Векторы на эталоне; **каждое правило уведомлений** на своих образцах и валидатор правил; переносимость регулярных выражений; словари и данные нормализации; парсеры выписок (CSV разных кодировок и разделителей, XLSX, PDF, ошибки, лимиты); эндпоинт (доступ, лимит по заголовку и по потоку, файл не хранится); таблица правил через настоящий `POST /sync/push` (валидация, неизменяемость, детерминированный id, два устройства); сквозной импорт выписки без дублей (повтор, пересекающаяся выписка) и уточнение черновика уведомления; миграция `0010` туда-обратно и тест дрейфа схемы; property-based: нормализация идемпотентна, сходство симметрично.

## 11. Известные ограничения и открытые вопросы

1. **Все образцы синтетические.** Тексты уведомлений, имена пакетов Android, заголовки и вид выписок взяты по общему виду; реальные образцы заказчика заменят их и станут тестами. Профиль ВТБ и разбор PDF особенно условны (PDF — только таблицы с линиями; без линий таблица не находится, нужен тюнинг на реальной выписке).
2. **Транслитерации нет.** Уведомление «PYATEROCHKA» и строка выписки «Пятёрочка» не склеиваются нечётко (разные алфавиты); пользователь увидит дубль в мастере. Если банки так себя ведут на реальных данных — нужна таблица соответствий или транслитерация (это изменит векторы).
3. **Префиксы описаний** («Оплата товаров и услуг …») в нормализацию не входят; добавляются списком в `merchant_normalization.json` по реальным выпискам.
4. **Время в выписках — московское** (допущение; банки обычно так и пишут). Часовой пояс устройства не учитывается.
5. **Строка «только дата»** получает 12:00 МСК: окно 48 часов покрывает такие даты, но хеш такой операции никогда не совпадёт с хешем уведомления (разное время) — их связывает только нечёткое сопоставление.
6. **Операция по картам без `card_last4`** в счёте не находит счёт автоматически (`needs_review`, выбор вручную).
7. **Сумма для чужой валюты** хранится в рублях по данным выписки; курс и мультивалютность — вне v1 (Этап 5, 12.1).
8. Правила регулярных выражений уведомлений — подмножество (2.2); если реальные тексты потребуют большего, подмножество расширяется вместе с обеими реализациями и векторами.
