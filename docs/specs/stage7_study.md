# Этап 7. Спецификация: Учёба (расписание, посещаемость, предметы, долги, вложения)

> Контракт для сервера и Flutter-клиента. Решения — `docs/briefs/stage-7.md` (требования заказчика от 2026-10-02; при расхождении действует выжимка). Эталон — `backend/src/tasker/study/reference.py`, общие векторы — `shared-test-vectors/study/` (раздел 10). Календарь и праздники — `docs/specs/stage2_calendar_tasks.md` (6, 7).

## 0. Принципы

- Расписание **вычисляется**, а не хранится: «семестр + сетка звонков + пары + особые дни + изменения на дату + праздники РФ» → занятия на любую дату (раздел 3). Занятия не синхронизируются и не попадают в таблицу событий; календарь показывает их отдельным слоем «Учёба».
- Всё, что хранится, синхронизируется по правилам Этапа 1; конфликты — автоматически (поле за полем, LWW). Мягкое удаление, корзина 30 дней, служебные поля, `id` — UUIDv7 от клиента. Исключение — строки с естественным ключом (звонок, особый день, изменение на дату, отметка): их `id` **детерминированный** (`uuid5`), чтобы два устройства, сделавшие одно и то же офлайн, создали одну строку.
- Даты — `YYYY-MM-DD`, время занятий — `HH:MM` (локальное время вуза, **без часового пояса**: пара идёт в 08:30 по часам города, где вуз). День недели — `1…7`, понедельник = 1.
- Все функции расчёта чистые, на «JSON-строках» таблиц (`id` — строки). Клиент и сервер обязаны давать **побайтно одинаковый** результат на векторах; клиент передаёт **видимые** строки (живые и с живыми родителями).
- Деньги в этом модуле не участвуют.

## 1. Таблицы

Порядок регистрации в реестре (родители раньше потомков): `study_semesters`, `study_subjects`, `study_bells`, `class_slots`, `study_day_rules`, `class_overrides`, `study_attendance`, `study_debts`, `attachments`. Необязательные колонки при создании можно не посылать (читаются как `null`).

### 1.1 `study_semesters` — семестры

| Колонка | Тип | Правила |
|---|---|---|
| `name` | text 1–100, не пустое | обяз. |
| `start_date`, `end_date` | date | обяз.; `end_date ≥ start_date`, длина семестра ≤ 400 суток |
| `week1_start` | date | обяз.; **любая** дата недели №1 (нормализуется к понедельнику) — опора чередования **этого** семестра |
| `cycle_length` | int 1…8 | обяз.; `2` — чёт/нечёт, `1` — без чередования |
| `week_shifts` | json, null | «сдвинуть чётность» (как в Этапе 2, 6): список ≤ 30 записей `{"from": date, "weeks": int −8…8}` |
| `archived` | bool | обяз.; архивный семестр в расписание не входит |

**Решение: у семестра своя опора чередования, а не общая настройка `calendar.week_cycle`.** У каждого семестра своя нулевая неделя; расчёт идёт на сервере и в клиенте без чтения пользовательских настроек, а векторы самодостаточны. Формула номера недели та же, что в Этапе 2, 6 (`calendar/week_cycle.py`): `weeks = floor((monday(d) − monday(week1_start)) / 7) + Σ shift.weeks (monday(shift.from) ≤ monday(d)); week = weeks mod cycle_length + 1`. Номер 1 = «нечётная», 2 = «чётная» (названия — на клиенте). Календарь Этапа 2 по-прежнему живёт на своей настройке; клиент при создании семестра предлагает взять опору оттуда.

### 1.2 `study_subjects` — предметы

| Колонка | Тип | Правила |
|---|---|---|
| `semester_id` | uuid → `study_semesters`, **неизменяема** | обяз.; родитель, каскад |
| `name` | text 1–200, не пустое | обяз. |
| `teacher` | text ≤ 200, null | ФИО преподавателя (одно поле) |
| `building` | text ≤ 10 без пробелов, null | корпус по умолчанию («1», «2» …) |
| `room` | text ≤ 20, null | кабинет по умолчанию |
| `absence_limit` | int 1…999, null | лимит пропусков; `null` — не считать лимит |
| `note` | text ≤ 5 000, null | |
| `archived` | bool | обяз. |

Цвета нет (монохром, решение заказчика).

**Аудитория**: хранится как `building` + `room` (раздел 4), показывается и вводится как «к1 28».

### 1.3 `study_bells` — сетка звонков

Одна строка = одна пара: «номер → начало, конец».

| Колонка | Тип | Правила |
|---|---|---|
| `semester_id` | uuid → `study_semesters`, **неизменяема** | обяз.; каскад |
| `on_date` | date, null, **неизменяема** | `null` — обычная сетка семестра; дата — **звонок только на эту дату** (замена обычного) |
| `number` | int 1…12, **неизменяем** | номер пары |
| `start_time`, `end_time` | `HH:MM` | обяз.; `end_time > start_time` |

`id = uuid5(ns("study_bells"), "<semester_id>|<on_date или пусто>|<number>")` (`ns(t) = uuid5(NAMESPACE_URL, "urn:my-tasker:" + t)`, как в Этапе 2, 2.2); иначе `invalid_id`.

«Изменить для всех пар» = править обычную сетку; «только на дату» = строки с `on_date`. Для даты звонок пары берётся из строки с этой датой, если она есть, иначе из обычной сетки; замена идёт **по каждому номеру отдельно**. Задавать сетку можно вручную по паре или генератором (раздел 5): «начало первой пары, длительность пары, перемены».

### 1.4 `class_slots` — пары расписания

| Колонка | Тип | Правила |
|---|---|---|
| `semester_id` | uuid → `study_semesters`, **неизменяема** | обяз.; каскад |
| `subject_id` | uuid → `study_subjects`, null | предмет; каскад (удаление предмета убирает его пары) |
| `title` | text 1–200, null | своё название («Кружок»); нужен, если нет предмета |
| `weekday` | int 1…7 | обяз. |
| `number` | int 1…12, null | номер пары по сетке |
| `start_time`, `end_time` | `HH:MM`, null | своё время (оба или ни одного); побеждает номер |
| `kind` | enum | обяз.: `lecture` лекция, `practice` практика, `lab` лабораторная, `other` другое |
| `building`, `room` | как у предмета, null | аудитория пары; нет — берётся аудитория предмета |
| `cycle_week` | int 1…8, null | неделя цикла (1 нечётная, 2 чётная …); `null` — каждая неделя |

`validation_failed`: нужен `subject_id` или непустое `title`; нужен `number` или своё время; `end_time > start_time`.

### 1.5 `study_day_rules` — особые дни

Правило на день недели (на весь семестр) или на конкретную дату: «обычных пар нет» и/или свой набор занятий.

| Колонка | Тип | Правила |
|---|---|---|
| `semester_id` | uuid → `study_semesters`, **неизменяема** | обяз.; каскад |
| `weekday` | int 1…7, null, **неизменяем** | правило на день недели |
| `on_date` | date, null, **неизменяема** | правило на дату; ровно одно из `weekday`/`on_date` (иначе `validation_failed`) |
| `cycle_week` | int 1…8, null, **неизменяема** | только с `weekday`: правило действует лишь в эту неделю цикла |
| `title` | text 1–200 | обяз. («Подготовка к олимпиаде») |
| `hide_regular` | bool | обяз.; `true` — обычные пары этого дня скрыты |
| `items` | json | обяз.; список ≤ 12 занятий, ≤ 8 КБ |

Занятие правила: `{"key": 1–20 символов a-z 0-9 _ (уникален в правиле), "title": 1–200, "kind": как у пары, "number": 1…12 | null, "start_time"/"end_time": HH:MM | null, "building": ≤ 10 | null, "room": ≤ 20 | null, "cycle_week": 1…8 | null}`; нужен `number` или своё время. Других ключей нет.

`id = uuid5(ns("study_day_rules"), "<semester_id>|weekday:<день>:<cycle_week или пусто>")` или `…|date:<дата>`.

Занятия особого дня — не предметные: **не отмечаются в посещаемости и в пропуски не идут** (решение заказчика: четверг-подготовка к олимпиаде).

### 1.6 `class_overrides` — изменения на дату

| Колонка | Тип | Правила |
|---|---|---|
| `slot_id` | uuid → `class_slots`, **неизменяема** | обяз.; каскад |
| `date` | date, **неизменяема** | дата **по расписанию** (когда пара была бы обычно) |
| `action` | enum | обяз.: `cancel` отмена, `change` изменение, `move` перенос |
| `new_date` | date, null | только у `move`, обязательна, `≠ date` |
| `start_time`, `end_time` | `HH:MM`, null | новое время (оба или ни одного) |
| `building`, `room` | null | новая аудитория (пара целиком: заданное одно — второе берётся пустым) |
| `subject_id` | uuid, null | **мягкая ссылка**: замена предмета |
| `title` | text ≤ 200, null | замена названия |
| `lesson_kind` | enum, null | замена типа |

`id = uuid5(ns("class_overrides"), "<slot_id>|<date>")` — одно изменение на пару и дату. У `cancel` остальные поля **игнорируются** (не ошибка, чтобы слияние полей двух устройств не ломало строку). «Для всех пар» — правка самой пары или сетки звонков; «только на дату» — эта таблица.

### 1.7 `study_attendance` — посещаемость

| Колонка | Тип | Правила |
|---|---|---|
| `slot_id` | uuid → `class_slots`, **неизменяема** | обяз.; каскад |
| `date` | date, **неизменяема** | дата пары **по расписанию** (у перенесённой — исходная) |
| `status` | enum | обяз.: `present` был, `absent` пропустил, `cancelled` отменена преподавателем |
| `note` | text ≤ 500, null | |

`id = uuid5(ns("study_attendance"), "<slot_id>|<date>")`. «Не отмечено» — строки нет.

### 1.8 `study_debts` — долги (лабораторные, практические …)

| Колонка | Тип | Правила |
|---|---|---|
| `subject_id` | uuid → `study_subjects`, **неизменяема** | обяз.; каскад |
| `kind` | enum | обяз.: `lab`, `practice`, `rgr` РГР, `coursework` курсовая, `credit` зачёт, `exam` экзамен, `other` |
| `title` | text 1–200 | обяз. («ЛР 3») |
| `status` | enum | обяз.: `open` не сдана, `submitted` сдана, `credited` зачтена |
| `due_date`, `done_date` | date, null | срок; дата сдачи |
| `note` | text ≤ 5 000, null | заметка |
| `task_id` | uuid, null | **мягкая ссылка** на задачу Этапа 2 («создать задачу» по долгу): ссылка хранится на стороне долга, таблица `tasks` не менялась |

Открытый долг — `status = open`; «просрочен» — `open` и `due_date` раньше сегодняшней даты. Каждая лабораторная/практическая — отдельная строка (отдельный блок на экране предмета).

### 1.9 `attachments` — метаданные вложений

Содержимое файлов лежит **вне** синхронизации (раздел 7); здесь только описание.

| Колонка | Тип | Правила |
|---|---|---|
| `subject_id` | uuid → `study_subjects`, null, **неизменяема** | владелец — предмет |
| `debt_id` | uuid → `study_debts`, null, **неизменяема** | владелец — долг |
| `file_name` | text 1–255 | без `/`, `\` и управляющих символов; расширение должно подходить к `mime_type` |
| `mime_type` | enum, **неизменяем** | см. таблицу типов ниже |
| `size_bytes` | int 1…26 214 400 (25 МБ), **неизменяем** | |
| `sha256` | 64 hex строчными, **неизменяем** | SHA-256 содержимого |
| `upload_status` | enum | обяз.: `pending` (файл есть только на устройстве-источнике), `uploaded` (загружен на сервер; ставит клиент после успешного `PUT`) |

Ровно одно из `subject_id`/`debt_id` (`validation_failed`).

**Решение: владелец — две типизированные ссылки, а не пара «тип + id».** Каскады и корзина Этапа 1 работают по настоящим родителям; полиморфная ссылка не смогла бы убрать вложения вместе с предметом и долгом. Новый владелец в другом модуле — новая необязательная ссылка-колонка и миграция.

| `image/jpeg` | `.jpg` `.jpeg` |
| `image/png` | `.png` |
| `image/heic`, `image/heif` | `.heic` `.heif` |
| `image/webp` | `.webp` |
| `application/pdf` | `.pdf` |
| `application/msword` | `.doc` |
| `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | `.docx` |
| `application/vnd.ms-excel` | `.xls` |
| `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | `.xlsx` |
| `application/vnd.ms-powerpoint` | `.ppt` |
| `application/vnd.openxmlformats-officedocument.presentationml.presentation` | `.pptx` |
| `text/plain` | `.txt` |
| `application/zip` | `.zip` |

## 2. Связи и каскады

```
study_semesters ─┬─ study_subjects ─┬─ class_slots ─┬─ class_overrides
                 │                  │   (также от    └─ study_attendance
                 │                  │    семестра)
                 │                  ├─ study_debts ──── attachments
                 │                  └─ attachments
                 ├─ study_bells
                 ├─ class_slots
                 └─ study_day_rules
```

Каскады делает сервер, клиент шлёт одну операцию `delete` родителя (Этап 1, 3.5):

| Удаляется | В корзину каскадом |
|---|---|
| семестр | предметы, звонки, пары, особые дни и всё ниже |
| предмет | пары предмета (и их изменения и отметки), долги (и их вложения), вложения предмета |
| пара | изменения на дату и отметки посещаемости |
| долг | вложения долга |

Удаление пары стирает её историю посещаемости (счётчики пропусков пересчитаются) — клиент предупреждает; 30 дней можно восстановить. Видимость на клиенте — как в Этапе 1: строка видима, если живы она и **все** её родители.

Физическая очистка корзины (Этап 1, 3.8) вместе с строкой `attachments` **удаляет и файл** (раздел 7.4).

## 3. Развёртка расписания на дату

`expand_day(date, semesters, subjects, bells, slots, day_rules, overrides, holidays)` → день:

```json
{"date": "2026-09-10", "weekday": 4, "semester_id": "…", "cycle_week": 2,
 "day": {"kind": "special", "name": "Подготовка к олимпиаде", "rule_id": "…"},
 "lessons": [ … ]}
```

`holidays` — словарь «дата → название» нерабочих дней (`holidays_between`: из `shared-data/calendar/holidays_ru.json` берутся только записи `holiday` и `transfer_off`; обычные суббота и воскресенье — **учебные** дни, суббота у вуза бывает рабочей).

### 3.1 Что за день (`day.kind`)

1. **Семестра нет** (дата вне всех неархивных семестров; пересекаются — побеждает семестр с более поздним началом): `no_semester`, занятий нет.
2. Иначе приоритет: **правило на эту дату** → **праздник** → **правило на день недели** (с учётом `cycle_week` правила; конкретная неделя цикла побеждает «любую») → обычный день.
   - правило на дату или на день недели → `special`; `name` — `title` правила;
   - праздник (и нет правила на эту дату) → `holiday`, `name` — название праздника; правило на день недели в праздник **не действует**;
   - иначе `regular`.

### 3.2 Занятия

- **Обычные пары** (`source = "slot"`) показываются в `regular` и в `special` при `hide_regular = false`: пары семестра с нужным днём недели и `cycle_week` пары, равным неделе цикла (или `null`).
- **Занятия правила** (`source = "rule"`) — в `special`: занятия из `items`, подходящие по `cycle_week`.
- **Изменения на дату** применяются к обычным парам по ключу «пара + дата по расписанию»:
  - `cancel` — занятие остаётся в списке с `cancelled = true` (зачёркнуто в интерфейсе);
  - `change` — подставляются заданные время, аудитория, предмет, название, тип; `changed = true`;
  - `move` — в исходный день занятие остаётся с `moved_to = <new_date>` (не отмечается), а в день `new_date` появляется с `moved_from = <исходная дата>` и новыми полями; **перенесённое занятие показывается в любой день, даже в праздник и «особый»** (его перенесли явно; если пара скрыта правилом в исходный день, перенос всё равно срабатывает). Изменение для пары, которой в этот день по расписанию нет (не та неделя цикла), не показывается.
- **Время занятия:** своё время пары (`start_time`/`end_time`) → иначе звонок её номера на **день проведения** (строка сетки на эту дату, затем обычная) → иначе `null` (занятие в конце списка). Время из `change`/`move` побеждает всё.
- **Аудитория** — первая из «изменение → пара → предмет» **целиком** (корпус и кабинет вместе; заданный только кабинет не смешивается с чужим корпусом); `room_text` — «к1 28».
- **Название** — `title` изменения → `title` пары → название предмета; тип — `lesson_kind` → `kind` пары.
- **Порядок:** время начала (без времени — в конце), номер пары (нет — в конец), ключ.

Поля занятия: `key` (`slot:<slot_id>@<исходная дата>` или `rule:<rule_id>:<key>`), `source`, `slot_id`, `rule_id`, `scheduled_date`, `date`, `number`, `start`, `end`, `title`, `subject_id`, `kind`, `building`, `room`, `room_text`, `cancelled`, `changed`, `moved_from`, `moved_to`, `override_id`, `trackable`.

`trackable` — занятие можно отмечать и о нём спрашивают «Был на паре?»: пара из расписания (не занятие правила), не отменена и не перенесена в другой день. В праздник, в день, где правило убрало пару, для отменённой и для перенесённой пары вопрос **не задаётся**.

### 3.3 Примеры

Семестр с 1 сентября 2026 (вторник), неделя 1 начинается 31 августа, цикл 2. Пары: пн №1 «Мат. анализ» каждую неделю; пн №2 физика-лаба на нечётных неделях; вт №3 программирование на чётных; чт №1–3 обычные; правило на четверг — «обычных пар нет», 3 занятия «Подготовка к олимпиаде».

| Дата | Что |
|---|---|
| 2026-09-14 (пн, неделя 1) | лекция по матану + лаба по физике |
| 2026-09-07 (пн, неделя 2) | только лекция |
| 2026-09-03 и 2026-09-10 (чт) | `special`: 3 занятия «Подготовка к олимпиаде» (№1–3 по сетке), обычные пары скрыты |
| Четверг — праздник | `holiday`, правило не действует |
| Четверг с правилом **на эту дату** (экскурсия) | правило на дату побеждает правило на четверг |
| Пара отменена на 2026-09-07 | в списке с `cancelled = true`, в пропуски не идёт |
| Среда перенесена с 9 на 11 сентября, 14:00–15:30 | 9-го: `moved_to = 2026-09-11`; 11-го: `moved_from = 2026-09-09`, 14:00–15:30 |
| Звонки на 14 сентября: пара №1 с 07:50 | только в этот день; 21 сентября — обычные |

Полный набор — `shared-test-vectors/study/expand.json`.

## 4. Аудитория «к1 28»

`parse_room(text)` → `{"building", "room"}` или `null`; `format_room(building, room)` → строка.

1. Приведение: пробельные символы (`U+0020 U+00A0 U+202F U+2009 \t \r \n`) схлопываются в один пробел, края обрезаются (получается «введённый» текст). Для разбора заглавные ASCII и кириллица понижаются, `ё = е` (для всего остального — не `toLowerCase`, он различается между средами).
2. Пустая строка или длиннее 20 символов — `null`.
3. С меткой корпуса: `к`, `k` (латиница), `корп`, `корпус`, затем необязательные `.`/пробелы, **1–2 цифры корпуса**, затем **обязательный** разделитель (`пробел . , / -`, после него необязательная метка `к/каб/кабинет/ауд/аудитория` и точка) **или** метка кабинета без разделителя, затем кабинет `цифры[буква]`: `к1 28`, `К2 101`, `к 1 28`, `к1-28`, `к1.28`, `корп. 2 каб. 101`, `Корпус 1 ауд. 305`, `к1 каб28`, `к2 101а` → корпус `1`/`2`, кабинет `28`/`101`/`101а`. Слитно `к128` не делится (корпус не угадывается) — как произвольный текст.
4. Пара цифр: `1-28`, `2 101`, `1/28` → корпус и кабинет.
5. Всё остальное — кабинет без корпуса **как введено** (с обрезкой пробелов, регистр сохраняется): `28`, `305а`, `Спортзал`. У распознанной пары буквы кабинета приводятся к нижнему регистру (`28Б` → `28б`).

`format_room`: корпус и кабинет → `к{корпус} {кабинет}`; только корпус → `к{корпус}`; только кабинет → он; пусто → `""`.

## 5. Генератор сетки звонков

`generate_bells(first_start, duration, breaks, count)`: пара `i` начинается в `first_start` + Σ (длительность + перемена) предыдущих и длится `duration` минут; `breaks` — одно число для всех перемен или список (`breaks[i]` — после пары `i + 1`; лишние отбрасываются). Результат — список `{number, start_time, end_time}` или **ошибка**, если: время начала не `HH:MM`, `count` не 1…12, `duration` не 1…300, перемена не 0…240, перемен меньше `count − 1`, последняя пара заканчивается позже 23:59. В UI поля редактируются по паре; генератор — быстрый способ первой настройки и «сдвинуть всё».

## 6. Посещаемость и пропуски

`attendance_summary(through, semesters, subjects, bells, slots, day_rules, overrides, holidays, attendance)` → по каждому предмету (в порядке входа):

```json
{"subject_id", "present", "absent", "cancelled", "unmarked", "limit", "left", "state"}
```

Считаются занятия предмета с начала семестра по дату `through` включительно:

- считаются только **пары из расписания** (`source = slot`), не перенесённые в другой день; занятия особых дней, праздники и скрытые правилом пары — не занятия вовсе;
- пара, **отменённая изменением** или отмеченная `cancelled`, — `cancelled` (пропуском не является, даже если стоит `absent`);
- отметка `present`/`absent` ищется по «пара + дата **по расписанию**» (у перенесённой — исходная); нет отметки — `unmarked`;
- у пары с заменённым предметом занятие идёт на предмет-замену;
- отметка на несуществующее занятие (не та неделя, праздник) игнорируется.

`left = limit − absent` (`null` без лимита, может быть отрицательным). `state`: `no_limit`; иначе `over` (`absent > limit`), `reached` (`=`), `near` (`absent × 4 ≥ limit × 3`, «приближается»), `ok`. Целочисленно, без деления. Клиент сам решает, какую `through` передать (сегодня или вчера — до конца пары «не отмечено» не пропуск); локальное уведомление «Был на паре?» приходит после окончания занятия с `trackable = true` и очищается, когда отметка поставлена.

## 7. Вложения: хранилище и эндпоинты файлов

### 7.1 Хранилище

Содержимое лежит **на диске сервера** в каталоге `FILES_DIR` (в compose — отдельный том `files`), за интерфейсом хранилища (`tasker.files.store.FileStore`: `put / size / read / delete / keys`); позже подключается S3 без изменения API. Ключ файла — `id` вложения; путь `FILES_DIR/<первые 2 символа id>/<id>`. Запись — во временный файл `*.part` рядом и атомарное переименование после проверки размера и SHA-256: читатель никогда не видит недописанный файл, оборванная загрузка ничего не оставляет. Бэкап базы в S3 (Этап 1) **файлы не покрывает** — том `files` включается в бэкап сервера отдельно (известное ограничение).

### 7.2 `PUT /files/{attachment_id}`

Тело — сырые байты файла. Заголовки: обычная авторизация (токен устройства и `X-Client-Schema-Version`). Предусловие: строка `attachments` с этим `id` **уже синхронизирована** (клиент делает синхронизацию перед загрузкой; иначе `404 attachment_not_found` — повторить после синхронизации).

- Размер и хеш берутся из **метаданных** (они неизменяемы): тело должно быть ровно `size_bytes` байт с SHA-256 `sha256`. Объявленная длина (`Content-Length`) не равна размеру, тело короче или другой хеш — `422 size_mismatch` / `422 hash_mismatch`; потоковое тело длиннее размера — `413 payload_too_large`. Файл при этом не сохраняется (оборванная загрузка — частный случай «короче»; оборванное соединение ничего не оставляет).
- Лимит 25 МБ (`FILES_MAX_BYTES`): `size_bytes` вложения больше лимита — `413 payload_too_large` (`details.max_bytes`).
- Первые байты должны подходить к `mime_type` (JPEG/PNG/WebP/HEIC/PDF/Office/ZIP/текст без NUL) — иначе `415 content_type_mismatch`.
- **Идемпотентно:** файл уже сохранён — `200 {"status": "exists"}`, тело не читается; успешная первая загрузка — `201 {"status": "stored", "size": n}`. Повтор после обрыва безопасен.
- Строка скрыта (удалена или удалён родитель) — `404`. Без токена `401`; без настроенного `FILES_DIR` — `503 files_not_configured`.

Клиент после `201`/`200` ставит `upload_status = uploaded` обычной правкой.

### 7.3 `GET /files/{attachment_id}`

`200` с содержимым, `Content-Type` = `mime_type`, `Content-Length`, `ETag: "<sha256>"` (`If-None-Match` → `304`), `Content-Disposition: attachment; filename*=UTF-8''…`, `X-Content-Type-Options: nosniff`, `Cache-Control: private`. `404 attachment_not_found` — нет или скрыто; `404 file_not_uploaded` — метаданные есть, содержимого на сервере нет (ещё не загружено). **Доступ только владельцу:** единственный пользователь — владелец; запрос без токена, с отозванным устройством и к чужому (несуществующему, скрытому) `id` файла не получает.

### 7.4 Удаление

Строка `attachments` уходит в корзину вместе с владельцем (каскад) и физически удаляется воркером через 30 дней (Этап 1, 3.8). В той же операции очистки воркер **удаляет файл** из хранилища; затем сметает «осиротевшие» файлы (ключ без строки в БД — например, после сбоя между удалением строки и файла) и временные `*.part` старше часа.

## 8. Инструменты ИИ (читающие, агент «Учёба»)

Регистрация — `backend/src/tasker/study/tools.py` (реестр Этапа 3, 6.1); встроенный профиль `study` получает их автоматически. Читают только **видимые** строки; результат — JSON ≤ 20 000 символов (`truncated` при обрезке).

- **`get_study_schedule`**: `from_date`, `to_date` (обяз., `YYYY-MM-DD`, не более 31 дня). Ответ `{"period", "count", "truncated", "days": [{"date", "weekday", "cycle_week", "kind", "name", "lessons": [{"number", "start", "end", "title", "kind", "room", "teacher", "cancelled", "changed", "moved_from", "moved_to"}]}]}`; дни без занятий и без особого статуса пропускаются.
- **`get_study_absences`**: `subject_id` (необяз.), `through_date` (по умолчанию сегодня, московская). Ответ — счётчики из раздела 6 по предметам неархивных семестров с названием и преподавателем.
- **`get_study_debts`**: `subject_id`, `status` (`open` по умолчанию | `submitted` | `credited` | `all`), `limit` (1…100). Ответ — долги с предметом, типом, названием, статусом, сроком, `overdue`, заметкой (до 300 символов) и числом вложений; порядок — по сроку (без срока в конце), затем предмет и `id`.

## 12. Известные ограничения и открытые вопросы

1. **Время без часового пояса.** Пара «08:30» — местное время вуза; при поездках в другой пояс клиент показывает его как записано.
2. **Праздники и учёба.** Учебными считаются все дни, кроме `holiday`/`transfer_off` из файла Этапа 2. Перенесённые рабочие субботы (`working_weekend`) расписание **не** меняют (вуз может учить в такую субботу по расписанию другого дня — это можно задать правилом или изменением на дату). Каникулы — правило на дату или конец семестра.
3. **Удаление пары стирает её отметки** (каскад). Вместо удаления пары в конце семестра лучше архивировать семестр.
4. **Файлы вне бэкапа базы.** Том `files` нужно сохранять отдельно; до появления S3 потеря тома = потеря содержимого вложений (метаданные останутся).
5. **Проверка файла — по первым байтам**, не антивирус; клиент открывает документы системным просмотрщиком.
6. **Конфликт «пара скрыта, а перенос из неё»** трактуется в пользу переноса (раздел 3.2).
7. **Одно изменение на пару и дату**; чтобы «перенести и ещё сменить аудиторию», задаётся `move` с нужными полями.
8. **Ограничения размера:** ≤ 12 занятий в особом дне и ≤ 12 пар в сетке — по виду реального расписания; расширяется миграцией.
