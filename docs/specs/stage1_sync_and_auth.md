# Этап 1. Спецификация: вход, устройства, синхронизация, корзина

> Контракт между бэкендом (`backend/`) и клиентом (`app/`). Клиент реализуется по этому документу. Уточняет разделы 4 и 8 из `01_ARCHITECTURE_PLAN.md`; при расхождении с ним действует этот документ, при расхождении с `04_DECISIONS_AND_ROADMAP.md` — 04 (корзина **30 дней**, конфликты **только автоматически**).
> Идентификаторы, поля JSON и коды ошибок — на английском. Тестовые векторы: `shared-test-vectors/sync/*.json` (описание в конце).

## 0. Общие соглашения

- Транспорт: HTTPS, JSON UTF-8. Адрес сервера настраивается в клиенте (см. 1.5 в 04).
- Заголовки запроса:
  - `Authorization: Bearer <access_token>` — на всех эндпоинтах кроме `/auth/login`, `/auth/refresh`, `/version`, `/health/*`.
  - `X-Client-Schema-Version: <int>` — **обязателен** для `/auth/login`, `/auth/refresh`, `/sync/*`, `/events`. Текущая версия схемы клиента на этом этапе: `1`.
  - `X-Request-ID` (необязателен) — эхом возвращается в ответе.
- **Ошибки** — всегда одна форма, с нужным HTTP-статусом:
  ```json
  {"error": {"code": "invalid_credentials", "message": "человекочитаемо, по-английски", "details": {}}}
  ```
  Клиент ветвится **только по `code`**. `details` необязателен. Тела запросов в ошибках не повторяются.
- Типы значений: `uuid` — строчный дефисный (`0195f2a0-...`); `datetime` — ISO 8601 UTC с `Z`; в ответах дробная часть секунд бывает из 0, 3 или 6 цифр, клиент разбирает любую; `hlc` — раздел 2; `int` — целое до 2^63-1.
- Константы протокола: `BATCH_MAX=500` операций в push, `PULL_MAX=1000` строк в pull, `TRASH_DAYS=30`, `ACCESS_TTL=900 с`, `REFRESH_TTL=90 дней` (скользящий), `REFRESH_GRACE=60 с` (1.3), `MAX_FUTURE_DRIFT=600 с`.
- Допустимые значения (сервер проверяет их у каждой операции; нарушение — `rejected` `invalid_field` для этой операции, пачка не страдает; те же правила полезно проверять на клиенте до отправки, вектор `sync/validation.json`):
  - строки (`text`, `enum`, а также **все** строки внутри `json`, включая ключи объектов) не содержат символ NUL (U+0000) и непарные суррогаты (в JSON: `"\ud800"`; пара `"\ud83d\ude00"` допустима);
  - `datetime` (колонки и `created_at`) — ISO 8601 **с часовым поясом**, после перевода в UTC лежит в диапазоне **[1970-01-01T00:00:00Z, 2200-01-01T00:00:00Z)**; значения без пояса и с датой, не представимой в UTC (`0001-01-01T00:00:00+14:00`), отклоняются. Сервер хранит и возвращает такие значения в UTC (`Z`);
  - `json` — не глубже **64** вложенных контейнеров, размер по колонке (например 16 КБ), без `NaN`/`Infinity`.

### Версии протокола

- Сервер отдаёт публичный `GET /version` → `{"app_version","api_schema_version","min_client_schema_version","server_epoch"}` (`server_epoch` — 3.10; при недоступной БД `503 database_unavailable`).
- Если `X-Client-Schema-Version` < `min_client_schema_version`, любой из перечисленных выше эндпоинтов отвечает **`426`, `code: "client_too_old"`**, `details: {"min_client_schema_version": n, "api_schema_version": m}`. Клиент показывает баннер «нужно обновить приложение», продолжает работать офлайн, синхронизацию не пытается, пока не обновится.
- Заголовок отсутствует или не число → `400 schema_version_required`.
- Клиент новее сервера — допустимо: неизвестные **колонки** внутри операции сервер молча отбрасывает (клиент узнаёт по тому, что в pull колонка не вернулась); неизвестная **таблица** → операция отклоняется с `unknown_table`.
- Миграции БД только «добавить, потом использовать»: старые клиенты продолжают работать в пределах `min_client_schema_version`.

## 1. Аккаунт, вход, устройства

Один владелец, публичной регистрации нет. Пользователя создаёт администратор командой на сервере (не API):

```
python -m tasker.cli user create    # пароль запрашивается интерактивно (или из stdin с --password-stdin)
python -m tasker.cli user reset     # новый пароль и новый TOTP-секрет, все устройства отзываются, блокировки входа снимаются
python -m tasker.cli user unlock    # снять все блокировки входа и обнулить счётчики неудач (1.1)
python -m tasker.cli epoch show     # текущая эпоха сервера (3.10)
python -m tasker.cli epoch rotate   # новая эпоха: обязательный шаг после восстановления из дампа (3.10)
```
`user create|reset` один раз печатает `otpauth://totp/My%20Tasker:owner?secret=...&issuer=My%20Tasker` (добавляется в приложение-аутентификатор); с флагом `--json` печатает одну строку `{"otpauth_uri": "...", "totp_secret": "BASE32"}` для скриптов и CI. Пароль **12–256 символов** (границы одинаковы в CLI и в API, чтобы заданный пароль всегда можно было ввести), без NUL и непарных суррогатов; хранится как Argon2id, при входе пересчитывается, если параметры стоимости выросли (`check_needs_rehash`). TOTP: RFC 6238, SHA-1, 6 цифр, шаг 30 с, окно ±1 шаг; один и тот же шаг повторно не принимается (защита от повтора).

### 1.1 `POST /auth/login`

```json
{"password": "…", "totp_code": "123456",
 "device": {"name": "Galaxy A55", "platform": "android", "app_version": "0.3.1"}}
```
`platform` ∈ `android|windows|linux|macos|ios|web|other`; `name` 1–64 символов; `app_version` необязательно, ≤ 32.
`200`:
```json
{"device_id": "uuid", "token_type": "Bearer",
 "access_token": "…", "access_expires_at": "datetime",
 "refresh_token": "…", "refresh_expires_at": "datetime",
 "server_epoch": "uuid"}
```
`server_epoch` — эпоха сервера (3.10). Каждый успешный вход **создаёт новое устройство** (новый `device_id`). `device_id` клиент сохраняет: он входит в HLC.
Ошибки: `401 invalid_credentials` (неверен пароль **или** код — не различаются; пользователя нет — тот же код), `429 too_many_attempts` (+ заголовок `Retry-After`, `details.retry_after_seconds`), `426 client_too_old`, `422 validation_error`, `409 owner_secret_unreadable` (пароль верен, но `APP_SECRET_KEY` сервера изменился и секрет TOTP не расшифровать; владельцу нужно выполнить на сервере `user reset`; клиент показывает сообщение из `message`, повторять не нужно). Пароль или имя устройства с NUL/суррогатом — `422 validation_error`.

**Защита от перебора** (хранится в PostgreSQL): счётчики неудач по IP клиента и глобальный. Порог по IP — 5 неудач, глобальный — 20; после порога вход блокируется на `30 с × 2^(n−порог)`; максимум — **15 минут по IP и 5 минут глобально**; блокировка действует и при верных данных (успешный вход её не обходит).
- Попытка **засчитывается до проверки пароля**: проверка блокировок и увеличение счётчиков — одна короткая транзакция под блокировкой строк счётчиков, поэтому параллельный залп не проходит проверку чаще порога (например, 40 параллельных неверных входов дают не более 5 ответов `401`, остальные `429`). Повтор уже использованного кода TOTP считается неудачей.
- Успешный вход сбрасывает счётчик **только своего IP** и возвращает глобальному счётчику свою попытку (сама успешная попытка блокировку не создаёт). Счётчики забываются через 1 час без неудач.
- Распределённый перебор с многих адресов может лишь притормозить вход: глобальная блокировка не длиннее 5 минут, а администратор снимает любые блокировки командой `user unlock` (`user reset` тоже снимает их). Запереть владельца навсегда нельзя.

### 1.2 Токены

- **access_token** — непрозрачная для клиента строка, живёт 15 минут. Клиент шлёт его в `Authorization`. Просрочен → `401 token_expired` (клиент делает refresh и повторяет запрос один раз).
- **refresh_token** — непрозрачная строка, хранится клиентом в защищённом хранилище ОС. Сервер хранит только хеш.
- Ключ `APP_SECRET_KEY` подписывает access-токены и шифрует секрет TOTP. После его смены access-токены прежней подписи дают `401 invalid_token` (клиент делает refresh: refresh-токены от ключа не зависят), а новый вход невозможен (`409 owner_secret_unreadable`) до `user reset`.

### 1.3 `POST /auth/refresh`

`{"refresh_token": "…"}` → `200` тот же объект, что у login, включая `server_epoch` (**новый** access и **новый** refresh, `device_id` прежний). **Старый refresh перестаёт действовать сразу** — с единственным исключением, льготой ниже. Клиент обязан сохранить новый refresh **до** использования новых токенов.

**Льгота 60 с (`REFRESH_GRACE`) на потерянный ответ.** Токен, замененный **последней** ротацией, принимается ещё 60 с от этой ротации, пока его преемник **не использован**. Преемник считается использованным, если его предъявили к `/auth/refresh` или если пришёл запрос с access-токеном, выпущенным после ротации. Тогда сервер выдаёт **свежую пару** (новые access и refresh, `device_id` прежний), а неиспользованный преемник перестаёт действовать; устройство **не отзывается**. Окно считается от первой ротации: повторы в его пределах не продлевают его. Клиент при потере ответа повторяет тот же запрос с тем же refresh и сохраняет пару из последнего полученного ответа.

Ошибки (все `401`): `invalid_refresh_token` (формат или неизвестный), `refresh_expired`, `device_revoked`, **`refresh_reuse_detected`** — предъявлен уже использованный refresh вне льготы (токен «на два поколения назад», токен старше 60 с после ротации, токен, чей преемник уже использован, или сам неиспользованный преемник, погашенный льготой): сервер **отзывает устройство целиком**, клиент переходит в состояние «вышел, нужен вход». Клиент не должен слать refresh параллельно (один общий mutex); льгота страхует только от потери ответа, а не от гонки клиента.

### 1.4 Остальное

| Метод и путь | Описание | Ответ |
|---|---|---|
| `POST /auth/logout` | отозвать **текущее** устройство | `204` |
| `GET /auth/devices` | список устройств; `?include_revoked=true` добавляет отозванные | `200 {"devices":[Device]}` |
| `DELETE /auth/devices/{id}` | отозвать устройство (можно и текущее), идемпотентно | `204`; `404 device_not_found` |

`Device`: `{"id","name","platform","app_version","created_at","last_seen_at","last_pulled_version","revoked_at","is_current"}`.

**Отозванное устройство**: любой запрос с его access-токеном → `401 device_revoked` (в том числе `/events` и `/sync/*`), refresh → `401 device_revoked`. Клиент стирает токены и показывает экран входа; локальные данные остаются (решение UX, не протокола).
Прочие `401` на защищённых эндпоинтах: `not_authenticated` (нет заголовка), `invalid_token` (подпись/формат), `token_expired`.

## 2. HLC и идентификаторы

### 2.1 Формат HLC

Строка `"{ms:015d}-{counter:05d}-{device_id}"`: `ms` — миллисекунды Unix UTC, ровно 15 цифр с ведущими нулями; `counter` — 5 цифр (0…99999); `device_id` — uuid устройства, строчный. Пример: `001790000000123-00002-0195f2a0-7b1c-7a3e-8f10-0123456789ab`. Длина всегда 58.
**Порядок = обычное сравнение строк** (побайтово, ASCII): сравнивается `ms`, затем `counter`, затем `device_id`. Два разных устройства никогда не дают равных HLC.

### 2.2 Алгоритм часов клиента (`shared-test-vectors/sync/hlc.json`)

Состояние `(l, c)` (последние `ms` и `counter`), хранится в локальной БД, начальное `(0, 0)`.
- `send(now_ms)` (новая локальная правка): `if now_ms > l: l=now_ms; c=0 else: c=c+1`. Возвращает HLC `(l, c, device_id)`. Если `c` переполнился (> 99999) — `l=l+1; c=0`.
- `receive(remote, now_ms)` (для каждого `updated_at` строки, пришедшей в pull): `l' = max(l, remote.ms, now_ms)`; если `l' == l == remote.ms`: `c = max(c, remote.counter) + 1`; иначе если `l' == l`: `c = c + 1`; иначе если `l' == remote.ms`: `c = remote.counter + 1`; иначе `c = 0`; `l = l'`. Если `c` переполнился (> 99999) — `l=l+1; c=0`.
После `receive` любая новая правка клиента получает HLC строго больше всего увиденного.

Сервер отклоняет операцию, у которой `ms` больше серверного времени более чем на `MAX_FUTURE_DRIFT` (`hlc_in_future`, см. 3.3), чтобы часы «из будущего» не выигрывали LWW навсегда. Операции «из прошлого» (офлайн 3 дня) допустимы без ограничений.

### 2.3 Идентификаторы

Все `id` строк — **UUIDv7** (версия 7, вариант RFC 4122), генерирует клиент. Сервер проверяет версию; иначе `invalid_id`. `op_id` тоже UUIDv7. Исключение — `user_settings` (см. 4.1). `device_id` выдаёт сервер (UUIDv7).

## 3. Синхронизация

### 3.1 Модель данных синхронизируемой строки

Служебные поля (есть у каждой синхронизируемой таблицы, клиент хранит их локально):

| Поле | Тип | Кто задаёт |
|---|---|---|
| `id` | uuid | клиент при создании |
| `created_at` | datetime | клиент при создании; неизменно |
| `updated_at` | hlc | сервер: наибольший HLC применённых правок строки |
| `deleted_at` | datetime \| null | сервер: момент удаления = **наибольшее из** времени HLC операции удаления и времени, когда сервер её получил (3.8); `null` — строка жива |
| `server_version` | int | сервер: номер последнего принятого изменения строки из **одной глобальной** последовательности (выдаётся под блокировкой в порядке фиксации транзакций) |
| `origin_device_id` | uuid | сервер: устройство последней принятой правки |

Плюс прикладные колонки таблицы (у каждой таблицы свои, объявлены модулем на сервере). Сервер дополнительно хранит **карту версий полей**: для каждой прикладной колонки и для `deleted_at` пару `(server_version, hlc)` последнего её изменения. Клиенту она не отправляется.

`server_version` строки уникален: две строки никогда не имеют одинакового номера, поэтому порядок pull полный.

### 3.2 Формат операции outbox

```json
{"op_id": "uuid-v7", "table": "user_settings", "id": "uuid",
 "type": "upsert", "fields": {"value": {"x": 1}}, "base_version": 12,
 "hlc": "001790000000123-00002-<device_id>"}
```
- `type: "upsert"` — `fields` содержит **только изменённые прикладные колонки** (для создания — все обязательные колонки и `created_at`, `base_version: 0`). Служебные ключи в `fields` игнорируются, кроме двух: `created_at` (только при создании) и `deleted_at`, у которого допустимо **только** значение `null` — это **восстановление из корзины**.
- `type: "delete"` — `fields` отсутствует или пуст. Удаление мягкое: сервер ставит `deleted_at`.
- `base_version` — `server_version` строки, которую клиент **видел** при правке (значение локальной строки в момент правки); `0` для новой строки.
- `hlc` — одна метка на всю операцию, сгенерированная `send()` в момент правки. `device_id` в ней **обязан** совпадать с устройством из токена (`hlc_device_mismatch`).
- Неизвестные ключи верхнего уровня операции игнорируются.

### 3.3 `POST /sync/push`

Запрос: `{"ops": [Op, …]}`, 1…`BATCH_MAX` операций **в порядке создания**. Больше → `413 batch_too_large`; пусто/не массив → `422 validation_error`. Пачка обрабатывается в **одной транзакции**, последовательно; невалидная операция отклоняется, остальные применяются.

`200`:
```json
{"results": [{"op_id": "uuid", "status": "applied", "code": null, "message": null,
              "server_version": 57, "conflicts": 0, "duplicate": false}],
 "head_version": 60, "server_epoch": "uuid", "server_time": "datetime"}
```
`results` — в том же порядке и количестве. `status` ∈ `applied` | `rejected`.
- `applied`: операция обработана (в том числе «ничего не изменилось» и «проиграла по LWW» — это не ошибка, сходимость даст pull). `server_version` — новый номер строки (`null`, если строки нет: удаление несуществующей). `conflicts` — сколько записей добавлено в журнал конфликтов этой операцией.
- `rejected`: `code` и `message`; операция не применена. Клиент оставляет её в outbox со статусом `rejected` (бейдж «не синхронизировано», очередь не блокируется, повторно автоматически не отправляется).
- `duplicate: true` — `op_id` уже обработан ранее; возвращён **прежний** результат (идемпотентность). Повтор всей пачки после обрыва безопасен.

Коды `rejected`:

| code | Причина |
|---|---|
| `invalid_op` | не объект, нет обязательных ключей, неверные типы, неверный `type` |
| `invalid_id` | `id`/`op_id` не uuid, не UUIDv7 (или не совпал с правилом таблицы) |
| `invalid_hlc` | формат HLC нарушен |
| `hlc_device_mismatch` | устройство в HLC ≠ устройство токена |
| `hlc_in_future` | `ms` > серверное время + `MAX_FUTURE_DRIFT`. **Не запоминается** в журнале: клиент может отправить ту же операцию позже |
| `unknown_table` | таблицы нет в реестре сервера (клиент новее сервера) |
| `missing_fields` | создание без обязательных колонок или без `created_at`; правка несуществующей строки |
| `invalid_field` | значение колонки не проходит тип/ограничения (`message` называет колонку) |
| `immutable_field` | попытка изменить неизменяемую колонку |
| `parent_not_found` | внешний ключ указывает на несуществующую (в том числе удалённую физически) строку |
| `validation_failed` | нарушен доменный инвариант таблицы |
| `op_failed` | страховочный код: операцию не удалось применить по причине, которую не предвидели валидаторы (например, база отвергла значение). Операция откатывается целиком (в том числе её версии), остальные операции пачки применяются как обычно. Запоминается в журнале, как прочие отказы; исправить — новой операцией. Клиент показывает как «не синхронизировано» (5.2) |

Отклонённые операции (кроме `hlc_in_future`) тоже запоминаются: повтор даст тот же ответ. Чтобы исправить ошибку, клиент создаёт **новую** операцию (новый `op_id`, свежий HLC).
**Ни одна операция не может провалить пачку**: значения, которые база не сохранит (NUL, непарные суррогаты, даты вне диапазона, см. раздел 0), отклоняются валидаторами как `invalid_field`, а всё, что они пропустили, ловится на уровне операции (`op_failed`). Ответ `200` приходит, если запрос вообще разобран; `5xx` означает сбой сервера, и клиент повторяет всю пачку (безопасно, см. `duplicate`).
Ограничение размера: тело запроса ≤ 10 МБ (Caddy).

### 3.4 Слияние на сервере

Обозначения: операция `op` с `hlc h`, `base_version b`, устройство `d = device(h)`. Для поля `f` строки хранится `(v, h_f)`. Поле **конкурентно**, если `v > b` **и** `device(h_f) ≠ d`. (Собственные предыдущие записи того же устройства конфликтом не считаются — это защита от повтора после потери ответа.) `deleted_at` считается полем как остальные, но с правилами ниже.

**Новый `server_version`.** Сервер под блокировкой берёт `head+1` для **каждой принятой операции над существующей строкой** — даже если ничего не изменилось или операция проиграла. Так строка гарантированно вернётся в следующем pull, и клиент, чьё локальное состояние (собственные `updated_at`, `deleted_at`) отличается от серверного, сойдётся с сервером. Удаление несуществующей строки версию не расходует.

**`upsert` для существующей строки, по каждому полю `f` из `fields`:**
1. значение равно текущему → значение не меняется, журнал не пишется; но если `h` больше метки поля `h_f`, метка поля обновляется на `(v_new, h)` (иначе более старая конкурентная запись позже выиграла бы у этой), а `updated_at` строки поднимается до `max(updated_at, h)` и `origin_device_id` становится устройством операции: клиент, получивший строку в pull, должен увидеть эту метку в `updated_at` (`receive`, 2.2), иначе его следующая правка получила бы HLC меньше метки поля и проиграла бы ей;
2. поле не конкурентно → применить, `(v_new, h)`;
3. поле конкурентно: если `h > h_f` — **побеждает операция**: применить и записать конфликт `kind=field` (проигравшее = прежнее значение); иначе **побеждает сервер**: не применять и записать конфликт `kind=field` (проигравшее = значение операции).

**Удаление против правки** (по правилу «побеждает более новая метка»):
- `upsert` данных в **удалённую** строку, при этом удаление конкурентно (`deleted_at.v > b`, чужое устройство): если `h > h_deleted` — строка **воскрешается** (`deleted_at = null`, дети — см. 3.5), конфликт `kind=resurrected` (проигравшее: `{"deleted_at": "<iso>"}`); иначе строка остаётся в корзине, поля всё равно сливаются, конфликт `kind=edit_vs_delete` (проигравшее: значения полей операции). Если правка не конкурентна удалению (клиент видел удаление) — просто сливается, строка остаётся удалённой.
- `delete`: строки нет → `applied`, `server_version: null`. Строка уже удалена → `applied`, значения не меняются (версия строки растёт, как для любой операции; если `h` больше метки `deleted_at`, метка обновляется, и `updated_at` строки поднимается до `max(updated_at, h)`, как при «touch» выше). Иначе ищутся конкурентные чужие правки полей (`v > b`, чужое устройство). Есть правка с `h_f > h` → **удаление проигрывает**: строка остаётся живой, конфликт `kind=resurrected` (проигравшее: `{"deleted_at": "<iso из h>"}`). Иначе строка удаляется (`deleted_at` = время из `h`), а если конкурентные правки были — конфликт `kind=edit_vs_delete` (проигравшее: их значения).
- **Восстановление** (`fields.deleted_at = null`): строка жива → ничего. Иначе: если удаление не конкурентно или `h > h_deleted` — восстановить (при конкурентном удалении — конфликт `kind=resurrected`); иначе восстановление проиграло, конфликт `kind=edit_vs_delete` (проигравшее: `{"deleted_at": null}`).

**Создание** (`upsert` для строки, которой нет): нужны все обязательные колонки и `created_at`; строка получает `(v, h)` для каждого переданного поля.

Любое значение, проигравшее по LWW, попадает в журнал конфликтов — потерь без следа нет. Журнал хранит: таблицу, `row_id`, поле, вид, проигравшее и победившее значения, оба устройства, обе HLC, `op_id`, время.

### 3.5 Каскады родитель–потомок (на сервере)

Модуль объявляет связь «дочерняя таблица → колонка → родительская таблица».
- **Удаление родителя** сервер каскадом удаляет всех **живых** потомков (тот же HLC и тот же `deleted_at`, у каждого свой `server_version`, метка «удалён каскадом от родителя»). Потомки, уже лежавшие в корзине, не трогаются.
- **Явное удаление потомка, уже лежащего в корзине по каскаду** (клиент не видел удаления родителя), делает его **собственным** удалением: метка «удалён каскадом» снимается, метка времени удаления не уменьшается. Восстановление родителя такого потомка не вернёт — он остаётся в корзине, пока пользователь не восстановит его сам.
- **Восстановление родителя** (в том числе воскрешение) восстанавливает потомков, удалённых каскадом от **этого** родителя; потомки, удалённые сами по себе (в том числе явным удалением поверх каскада), остаются в корзине.
- Операция над потомком (создание, правка колонки-внешнего ключа), если родитель удалён: строка уходит в корзину каскадом, конфликт `kind=parent_deleted`. Если родителя не существует физически — `parent_not_found`.
- Физическая очистка (3.8): родитель не удаляется, пока остались потомки.

**Клиент каскадов не выполняет**: при удалении родителя он отправляет **одну** операцию `delete` для родителя. Локально потомки считаются скрытыми через видимость: строка «видима», если её `deleted_at = null` **и** все её родители видимы. Корзина показывает только «корневые» удалённые строки (родитель не удалён). Каскадные изменения потомков приходят обычным pull.

### 3.6 `GET /sync/pull?since=<int>&limit=<int>`

`since` ≥ 0 — курсор (`next_since` предыдущего ответа, `0` для нового устройства), `limit` 1…`PULL_MAX` (по умолчанию 500). `since` **не может быть больше `head_version`** (см. ниже).
`200`:
```json
{"changes": [{"table": "user_settings", "id": "uuid", "server_version": 58,
              "row": {"id": "…", "created_at": "…", "updated_at": "hlc", "deleted_at": null,
                      "server_version": 58, "origin_device_id": "uuid", "key": "ui.theme", "value": "dark"}}],
 "next_since": 58, "has_more": false, "head_version": 60,
 "purge_watermark": 0, "server_epoch": "uuid", "server_time": "datetime"}
```
- `changes` упорядочены по `server_version` по возрастанию (сквозной порядок по всем таблицам), включают **надгробия** (`deleted_at` не `null`), содержат **полную строку**.
- `has_more: true` — есть ещё; `next_since` — версия последней возвращённой строки. При `has_more: false` `next_since = head_version` на момент чтения (курсор можно сдвигать и без строк).
- Чтение — согласованный снимок. Каждый успешный pull сервер запоминает `since` как **курсор устройства** (`last_pulled_version`); курсор устройства и `next_since` **никогда не превышают `head_version`**.
- **Полная пересинхронизация:** если `0 < since < purge_watermark`, где `purge_watermark` — наибольшая версия физически очищенного надгробия, → **`410 Gone`, `code: "resync_required"`**, `details: {"purge_watermark": n, "head_version": h, "reason": "purged"}`. Тот же ответ (`"reason": "cursor_ahead"`) возвращается, если **`since > head_version`**: курсор клиента опережает сервер, то есть сервер восстановлен из более старого дампа (3.10); курсор при этом не сохраняется. Клиент в обоих случаях обязан выполнить полную пересинхронизацию (5.3). `since = 0` разрешён всегда.
- Собственные операции клиента возвращаются в pull как обычные строки — их надо применять так же (см. 5.2).

### 3.7 Что видит клиент при конфликте

Клиент не разбирает конфликты сам: сервер решает, клиент получает итоговую строку в pull. Номер строки увеличивается после каждой принятой операции (3.4), поэтому итоговая строка **обязательно** придёт в следующем pull.

### 3.8 Корзина и физическая очистка

- Корзина = строки с `deleted_at ≠ null`. Клиент показывает те, что удалены не более `TRASH_DAYS` (30) дней назад и не имеют удалённого родителя.
- **Срок корзины считается от получения удаления сервером.** `deleted_at` (3.1) = наибольшее из времени HLC операции и времени приёма на сервере. Удаление, сделанное офлайн 35 дней назад и дошедшее до сервера сегодня, получает `deleted_at` = сегодня и лежит в корзине ещё 30 дней; клиент, ориентируясь на `deleted_at` из pull, увидит его в корзине, а не потеряет сразу. Время из HLC, опережающее серверное (в пределах `MAX_FUTURE_DRIFT`), сохраняется как есть. Так же ведёт себя каскад: потомки получают то же `deleted_at`, что родитель. До первой синхронизации локальный `deleted_at` клиента — время его собственной правки (5.1). Восстановление — операция `upsert` с `fields: {"deleted_at": null}`.
- Воркер сервера раз в час физически удаляет надгробие, если **одновременно**: (а) `deleted_at` старше 30 дней (по определению выше, то есть от получения сервером); (б) `server_version` надгробия ≤ курсора **каждого активного устройства**; (в) нет потомков. **Активное устройство** = не отозвано и `last_seen_at` не старше 30 дней. Отозванные и молчащие > 30 дней устройства очистку не задерживают.
- Очищая, сервер поднимает `purge_watermark` до наибольшей очищенной версии.
- Устройство, отставшее от очищенной версии, получает `410 resync_required` (3.6). Так реализовано решение «офлайн дольше 30 дней → полная пересинхронизация».
- Клиент локально удаляет надгробия старше 30 дней (если по строке нет неотправленных операций) — сервер их, скорее всего, тоже уже удалил.
- Журнал обработанных операций хранится 60 дней, журнал конфликтов — 180 дней (чистит воркер).

### 3.9 Журнал конфликтов

`GET /sync/conflicts?reverted=<true|false|all>&limit=<1..200, по умолчанию 50>&before=<conflict id>` → `{"conflicts": [Conflict], "next_before": "id"|null}`, новейшие первыми. По умолчанию `reverted=all`.
`Conflict`:
```json
{"id": "uuid-v7", "created_at": "datetime", "table": "…", "row_id": "uuid", "field": "value",
 "kind": "field|resurrected|edit_vs_delete|parent_deleted",
 "losing_value": …, "winning_value": …,
 "losing_device_id": "uuid|null", "winning_device_id": "uuid|null",
 "losing_hlc": "hlc|null", "winning_hlc": "hlc|null",
 "reverted_at": "datetime|null"}
```
`field` — имя колонки, а для видов кроме `field` — `"deleted_at"`. Значения — JSON как есть (для `resurrected`/`edit_vs_delete` — объекты из 3.4).

**«Вернуть моё»:** `POST /sync/conflicts/{id}/revert` (тело пустое). Сервер применяет проигравшее значение **как новую операцию** от текущего устройства: свежая метка HLC (больше всех существующих меток строки), `base_version` = текущий `server_version` строки, поэтому она выигрывает без нового конфликта. Действие по виду:

| kind | что применяется |
|---|---|
| `field` | `fields = {field: losing_value}` |
| `resurrected` | удаление строки (проигравшим было удаление) |
| `edit_vs_delete` | восстановление строки из корзины; если проигравшим были поля — они уже влиты |
| `parent_deleted` | не поддерживается (`409 not_revertable`) |

`200`: `{"conflict": Conflict, "change": {"table","id","server_version","row": {…}}}` — `change` клиент применяет так же, как строку из pull. Ошибки: `404 conflict_not_found`, `409 conflict_already_reverted`, `409 row_not_found` (строка уже физически удалена), `409 not_revertable`, `422 revert_rejected` (значение теперь не проходит валидацию).

### 3.10 Эпоха сервера (`server_epoch`)

`server_epoch` — случайный uuid, идентифицирующий «историю» базы данных. Он хранится в `app_meta` (создаётся миграцией) и возвращается в ответах `login`, `refresh`, `GET /sync/pull`, `POST /sync/push` и `GET /version`. Пока база живёт непрерывно, эпоха не меняется. Она меняется, когда содержимое БД могло **откатиться назад во времени**, то есть после восстановления из дампа: тогда номера `server_version`, курсоры устройств и `base_version` операций уже не соответствуют серверу.

**Правило клиента.** Клиент хранит `server_epoch`, полученный при последней успешной синхронизации (`null` — ещё не было). Для каждого ответа с эпохой (`shared-test-vectors/sync/epoch.json`):
- сохранённой нет (`null`; пустая строка — обычное значение, а не «нет») → запомнить (при первой загрузке — вместе с курсором);
- совпала (сравнение точное, по строке, регистр важен) → ничего;
- **отличается → полная пересинхронизация с сохранением outbox (5.3)**, затем запомнить новую эпоху. В ответе `push` результаты операций обрабатываются как обычно (они применены уже к восстановленной базе), после чего вместо обычного pull выполняется 5.3. Страница `pull` с чужой эпохой отбрасывается. Если эпоха сменилась в середине полной пересинхронизации, её нужно начать заново.

**Как сервер меняет эпоху:**
1. **Явно** — `python -m tasker.cli epoch rotate`. Это обязательный шаг **процедуры восстановления из дампа** (`deploy/README.md`): после `pg_restore` и запуска миграций выполнить `docker compose exec api python -m tasker.cli epoch rotate`, затем перезапустить `api`.
2. **Автоматически** — сервис `migrate` при каждом запуске сравнивает «отпечаток базы» (идентификатор кластера PostgreSQL `system_identifier` и OID базы данных), сохранённый в `app_meta`, с текущим. Дамп, восстановленный в другой кластер или в заново созданную базу, несёт старый отпечаток, поэтому эпоха меняется сама. Если роль БД не может читать `pg_control_system()`, используется один OID.
3. **Страховка на стороне протокола**: клиент, чей курсор больше `head_version` (дамп старее клиента), получает `410 resync_required` с `reason: cursor_ahead` (3.6).

Что не обнаруживается автоматически: откат внутри того же кластера и той же базы (PITR, `pg_restore --clean` поверх), когда курсоры клиентов не опережают сервер. Для него единственный механизм — явный `epoch rotate`.

Ограничение: данные, которые сервер подтвердил клиентам после снятия дампа, при восстановлении теряются; полная пересинхронизация убирает у клиента строки, которых нет на сервере (кроме тех, что ещё в outbox).

## 4. Синхронизируемые таблицы

Реестр на сервере: модуль объявляет таблицу (колонки с типами, ограничениями, `required`/`immutable`), правила `id`, связи с родителями и доменные валидаторы. Типы значений в JSON: `text`, `int`, `bool`, `uuid`, `datetime`, `json` (любое JSON-значение), `enum`; ограничения на строки, даты и глубину `json` — в разделе 0. `null` допустим только у колонок, объявленных nullable. Колонки-ссылки (`uuid` родителя) и `uuid`-колонки сравниваются **по значению**: повторная отправка того же uuid не считается изменением ни для неизменяемой колонки, ни для конфликта.

### 4.1 `user_settings` (первая реальная таблица)

Настройки «ключ → значение», общие для устройств.

| Колонка | Тип | Правила |
|---|---|---|
| `key` | text | обязательна, неизменна; 1–100 символов, `^[a-z0-9][a-z0-9_.-]*$` |
| `value` | json | обязательна; любое JSON-значение, сериализованное ≤ 16 КБ |

`id` = **`uuid5(NS, key)`**, где `NS = 11fae5eb-de4a-5a92-88e3-5c86a8c454f4` (`uuid5(NAMESPACE_URL, "urn:my-tasker:user_settings")`). Так два устройства, создавшие один ключ офлайн, порождают **одну** строку, а не дубли (вектор: `sync/settings_id.json`). Сервер отклоняет несовпадение с `invalid_id`. Пример: ключ `ui.theme` → `826e9351-d34d-5a3d-99d0-d20367415629`.

## 5. Алгоритм клиента (эталонная реализация — `backend/tests/sync_sim/client.py`)

### 5.1 Локальная запись

В **одной** локальной транзакции: обновить строку (`updated_at` = новый HLC из `send(now)`; для создания — все поля, `created_at`, `base_version = 0`), добавить/схлопнуть операцию в outbox. Удаление: `deleted_at` = время из HLC, операция `delete`. Восстановление: `deleted_at = null`, операция `upsert {deleted_at: null}`. `base_version` операции = `server_version` локальной строки в момент правки.

Состояния операции outbox: `pending` (ещё ни разу не отправлялась), `in_flight` (отправлена хотя бы раз, подтверждения нет; результат на сервере **неизвестен**), `rejected` (сервер отклонил). Подтверждённая операция удаляется.

**Схлопывание** (только при добавлении новой операции к `pending` того же `(table, id)`; `in_flight` **неизменны навсегда** — иначе сервер, уже обработавший её `op_id`, проигнорировал бы новые поля как повтор; новая правка создаёт новую операцию):
1. `upsert` + `upsert` → один `upsert`: `fields` объединены (поздние значения затирают), `hlc` — более поздний, `base_version` — **ранний**, `op_id` — ранний.
2. `upsert` (правка, `base_version > 0`) + `delete` → один `delete` (`hlc` поздний, `base_version` ранний, `op_id` ранний). Создание (`base_version = 0`) + `delete` **не схлопывается**: обе операции уходят на сервер (иначе потомки, ссылающиеся на созданную строку, получили бы `parent_not_found`).
3. Всё остальное не схлопывается: если последняя операция строки — `delete`, `in_flight` или `rejected`, новая операция добавляется отдельно. Схлопывание идёт в позицию ранней операции (порядок outbox сохраняется).
(`shared-test-vectors/sync/outbox.json`.)

### 5.2 Цикл синхронизации (один за раз, под общим mutex)

`push`, затем `pull`. Запуск: старт приложения, появление сети, 2–5 с после правки, сигнал SSE, периодически (WorkManager ≈ 15 мин, таймер на Windows).
0. Любой ответ с `server_epoch` проверяется по правилу 3.10.
1. **Push.** Взять `pending` и `in_flight` в порядке создания, пачками ≤ 500, пометить все `in_flight`, отправить. По ответу: `applied` → удалить операцию; `rejected` → статус `rejected` с кодом (в том числе `op_failed`). **`base_version` оставшихся операций не менять.** Обрыв/таймаут → операции **остаются `in_flight`** с теми же `op_id` и содержимым (повтор безопасен, сервер вернёт `duplicate`), цикл прерывается; pull не выполняется. `401 token_expired` → refresh, повторить; `426` → баннер; `429` → пауза.
2. **Pull** страницами до `has_more = false`. Каждую страницу — в одной локальной транзакции:
   - `receive(remote_hlc)` для каждого `updated_at`;
   - для каждой строки: если по `(table, id)` есть операции не в статусе `rejected` — **rebase**: локальная строка = серверная строка, поверх неё по порядку накладываются поля этих операций (`upsert`: `fields`; `delete`: `deleted_at` = время из HLC операции в формате `YYYY-MM-DDTHH:MM:SS.mmmZ`); `base_version` операций **не меняется**, поэтому конфликт разрешится на сервере при следующем push честно по HLC; иначе локальная строка = серверная целиком;
   - сдвинуть курсор `last_pulled_version = next_since` **в той же транзакции**.
   - `server_epoch` страницы отличается от сохранённого (3.10) → страницу отбросить и выполнить 5.3.
3. Строки других устройств и свои собственные эхо-строки применяются одинаково.
4. Если после pull в outbox остались `pending` (правки во время цикла) — повторить цикл.

`rejected` операции при rebase не накладываются; UI предлагает «повторить» (новая операция от текущей строки) или «отбросить».

### 5.3 Первичная загрузка и полная пересинхронизация

- Новое устройство: pull с `since = 0`, постранично, с прогрессом.
- **Полная пересинхронизация** (по `410 resync_required` или кнопке «Полная пересинхронизация»): outbox сохраняется целиком. Клиент тянет все страницы с `since = 0` во временное хранилище, затем в одной транзакции: удаляет все локальные синхронизируемые строки, записывает серверные, накладывает операции не в статусе `rejected` (как в rebase), ставит курсор и `server_epoch`. Строки, которых нет на сервере, исчезают (очищены как надгробия). Операции без строки на сервере, не содержащие всех обязательных полей, сервер отклонит с `missing_fields`.

### 5.4 Что делает клиент при статусах

| Ситуация | Действие |
|---|---|
| `426 client_too_old` | баннер, работа офлайн, синхронизации нет |
| `401 device_revoked` / `refresh_reuse_detected` | стереть токены, экран входа |
| `410 resync_required` (`purged` или `cursor_ahead`) | 5.3 |
| `server_epoch` ответа ≠ сохранённому | 5.3 с сохранением outbox, затем запомнить новую эпоху (3.10) |
| `409 owner_secret_unreadable` (только при входе) | показать сообщение: владельцу нужен `user reset` на сервере |
| `hlc_in_future` | оставить операцию в outbox (сервер её не запомнил), повторить позже; показать предупреждение «проверьте время на устройстве» |
| прочие `rejected` | 5.2 |

## 6. SSE `GET /events`

Заголовок `Authorization`. Ответ `200`, `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`; соединение долгоживущее (Caddy: `flush_interval -1`). События (формат SSE, `data` — JSON в одну строку):

| event | data | когда |
|---|---|---|
| `hello` | `{"head_version": n}` | сразу при подключении |
| `changes` | `{"head_version": n}` | после фиксации транзакции push/revert **с другого устройства**; коалесцируются, если приходят чаще, чем клиент читает |
| `ping` | `{}` | каждые 20 с |
| `revoked` | `{}` | устройство отозвано; сервер закрывает поток |

Клиент: на `hello` и `changes` сравнить `head_version` со своим курсором и, если больше, запустить цикл синхронизации; при отсутствии любых событий 60 с — считать соединение мёртвым и переподключиться; переподключение с backoff 1→60 с. Просроченный access-токен проверяется только при подключении; отзыв устройства сервер проверяет на каждом `ping`. События «своих» коммитов устройство не получает. `503`/обрыв не влияют на офлайн-работу — синхронизация тогда идёт по таймеру.
