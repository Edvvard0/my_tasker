# Этап 9. Спецификация: Серверы — мониторинг и Telegram

> Контракт для сервера и Flutter-клиента. Решения — `docs/briefs/stage-9.md` (при расхождении действует выжимка; над ней — `docs/04_DECISIONS_AND_ROADMAP.md`). Эталон — `backend/src/tasker/monitoring/` (`targets.py`, `alerts.py`, `stats.py`), общие векторы — `shared-test-vectors/monitoring/` (раздел 11). Макет экрана — `docs/02_DESIGN_SYSTEM.md` §5.5.

## 0. Принципы

- Приложение серверами **не управляет**: нет «Выключить», «Перезапустить», запуска чужих команд. Оно наблюдает и сообщает.
- **Данные заказчика** (серверы, проекты, проверки) — обычные синхронизируемые таблицы Этапа 1: поля сливаются по одному, мягкое удаление, корзина 30 дней, служебные поля, `id` — UUIDv7 от клиента. **Измеренное** (результаты проверок, состояние, инциденты, очередь Telegram) — серверные таблицы, **не синхронизируются**: клиент читает их через API (раздел 8).
- **Секреты.** `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` существуют только в окружении сервера: в репозитории — только пустые строки в `deploy/.env.example`; не попадают в логи (редактор логов знает их значения), ответы API, конфигурацию движка, тексты ошибок (раздел 7). В контейнер движка они не передаются.
- Время — UTC; в сообщениях Telegram — часы пояса `MONITOR_TIMEZONE`. Деньги в модуле не участвуют. Расчёты целочисленные (доступность — базисные пункты вниз).

## 1. Движок проверок: Gatus (решение, которое можно поменять)

`04` требует «готовый движок (Uptime Kuma или Gatus) рядом с бэкендом», `01` (§6.6.1) — «свой движок»; **действует `04`**. Выбран **Gatus** (`twinproduct/gatus`, Apache-2.0):

| Критерий | Gatus | Uptime Kuma |
|---|---|---|
| Конфигурация | один YAML-файл — **генерируется нашим worker из данных заказчика**, без секретов | в собственной БД, управляется через socket.io (нестабильный, `01` 6.6.1) |
| Ресурсы | один маленький контейнер без БД-сервера (sqlite) | Node.js + БД, тяжелее |
| API статусов | JSON `/api/v1/endpoints/statuses` | нет стабильного API |
| Проверки | HTTP, TCP, DNS, SSL (срок сертификата) — нужные четыре | шире, но нам не нужно |
| Алерты | есть, но **мы их не используем** (антиспам и Telegram — свои) | то же |

**Как заменить:** `tasker/monitoring/engine.py` (протокол `EngineClient.fetch()` → список `EngineResult`), `config_gen.py` (из проверок — файл конфигурации движка), сервис в `deploy/docker-compose.yml`. Остальной код движка не знает.

Ограничения выбора (принять или поменять движок):
1. Gatus прогоняет проверки **по своему расписанию**: «Проверить сейчас» (раздел 8) обновляет то, что известно (читает движок немедленно), но не заставляет движок запустить проверку вне очереди. Настоящий внеочередной прогон потребует своего исполнителя проверок (то, что `01` называл «свой движок»).
2. Формат ответа Gatus (раздел 4.4) записан по документации, в тестах — рукописная запись в его форме; **сверить с живым Gatus** в фазе сборки. Длительность читается как наносекунды (`time.Duration`).
3. Подхват изменённой конфигурации работающим Gatus (перечитывание файла при изменении) нужно проверить на живом экземпляре; если не подхватывает — сервис перезапускается (`docker compose restart gatus`) или добавляется отдельный шаг.

## 2. Таблицы данных заказчика

Порядок регистрации: `monitor_servers`, `monitor_services`, `monitor_checks`. Необязательные колонки при создании можно не посылать.

### 2.1 `monitor_servers` — серверы

| Колонка | Тип | Правила |
|---|---|---|
| `name` | text 1–100 | обяз., не пустое |
| `host` | text 1–253 | обяз.; имя или публичный IP — **те же правила, что у целей проверок (раздел 5)**; адрес из внутренней сети нельзя внести |
| `provider` | text ≤ 100, null | |
| `note` | text ≤ 2 000, null | |

### 2.2 `monitor_services` — проекты/сервисы на сервере (карточки «Пульса»)

| Колонка | Тип | Правила |
|---|---|---|
| `server_id` | uuid → `monitor_servers`, **неизменяема** | обяз.; каскад |
| `name` | text 1–100 | обяз., не пустое |
| `work_project_id` | uuid, null | **мягкая ссылка** на проект Работы (Этап 4), без внешнего ключа |
| `critical` | bool | обяз.; критичный сервис не подчиняется тихим часам (раздел 6) |
| `note` | text ≤ 2 000, null | |

Паузы и «Выключить» нет (`04` 1.1 №3). Сервис, который больше не нужен, удаляется в корзину; его проверки выходят из конфигурации движка и из «Пульса».

### 2.3 `monitor_checks` — проверки

| Колонка | Тип | Правила |
|---|---|---|
| `service_id` | uuid → `monitor_services`, **неизменяема** | обяз.; каскад |
| `kind` | enum, **неизменяем** | обяз.: `http`, `tcp`, `dns`, `ssl` (сменить вид = удалить и создать) |
| `name` | text 1–100 | обяз., не пустое («Главная», «База») |
| `url` | text ≤ 2 000, null | только `http` (обяз.): `http(s)`-адрес по разделу 5 |
| `host` | text ≤ 253, null | `tcp`, `ssl` (обяз.), `dns` (обяз., имя запроса); по разделу 5 |
| `port` | int 1…65535, null | `tcp` (обяз.), `ssl` (необяз., 443 по умолчанию) |
| `dns_record_type` | enum, null | `dns` (обяз.): `A`, `AAAA`, `CNAME`, `MX`, `NS`, `TXT` |
| `expected_value` | text ≤ 253, null | `dns`: ожидаемое значение; один «токен» `[A-Za-z0-9._:/-]` |
| `expected_status` | int 100…599, null | `http`: ожидаемый код; `null` — любой код < 400 (редиректы не выполняются, 301/302 считаются «жив») |
| `keyword` | text ≤ 100, null | `http`: слово, которое должно быть в теле ответа; одним токеном — без пробелов, `* ( ) [ ] ' " \ < > = ! $ \`` |
| `ssl_min_days` | int 1…365, null | `ssl`: минимум дней до конца сертификата; `null` — 14 |
| `interval_seconds` | int 10…3 600 | обяз.; рекомендуемое значение клиента — 20 |
| `timeout_seconds` | int 1…30 | обяз.; **строго меньше** `interval_seconds` |

Межполевые правила (`validation_failed`): колонки, не относящиеся к виду, должны быть `null` (`url` — только у `http`, `host` — не у `http`, `port` — только у `tcp` и `ssl`, `keyword` и `expected_status` — только у `http` и т. д.); обязательные для вида — заданы; цель проходит раздел 5; `timeout < interval`.

### 2.4 Каскады

Сервер → сервисы → проверки. Удаление сервера (сервиса) — одна операция `delete` родителя (Этап 1, 3.5), каскад на сервере; восстановление — `deleted_at: null` у родителя. Серверные данные проверки (результаты, инциденты) при этом не удаляются сразу: результаты стареют по раздела 3, инциденты остаются в журнале.

## 4. Движок: конфигурация и опрос

### 4.1 Конфигурация

Задача `monitor_config` (раз в минуту) собирает из **живых** проверок (живые сами, сервис и сервер) файл `MONITOR_CONFIG_PATH` (`/monitor/config.yaml`; том `monitor_config`, у `gatus` — только чтение). Запись атомарная (`*.part` + переименование), только если содержимое изменилось. Порядок — по `id` проверки, поэтому файл детерминирован. В файле **нет секретов**: только цели заказчика и служебные настройки (sqlite-хранилище движка в `/data`, порт 8080).

Каждая проверка → endpoint движка: `name` = id проверки, `group` = id сервиса, `interval`, `client.timeout`, **`client.ignore-redirect: true`** (редиректы не выполняются — раздел 5). Условия:

| Вид | Адрес | Условия |
|---|---|---|
| `http` | `url` | `[STATUS] == N` (или `[STATUS] < 400`), при `keyword` — `[BODY] == pat(*слово*)` |
| `tcp` | `tcp://host:port` (IPv6 в скобках) | `[CONNECTED] == true` |
| `dns` | резолвер `MONITOR_DNS_RESOLVER` (по умолчанию `1.1.1.1:53`) | `dns: {query-name, query-type}`; `[DNS_RCODE] == NOERROR`, при `expected_value` — `[BODY] == pat(*значение*)` |
| `ssl` | `https://host:port` | `[CONNECTED] == true`, `[CERTIFICATE_EXPIRATION] > {дни×24}h` |

Строки пишутся как заключённые в кавычки скалярные значения (JSON-экранирование): значение не может стать ничем, кроме текста. Движок отказывается стартовать без единой проверки, поэтому в файл всегда добавлена служебная проверка `engine-self` (собственная страница здоровья движка); её имя не uuid, поэтому ингест её пропускает.

### 4.2 Повторная проверка целей

При генерации каждая проверка **судится заново** (строка могла появиться до ужесточения правил, а имя — начать указывать на внутренний адрес): синтаксис (раздел 5) и разрешение имени (`getaddrinfo`, до 10 одновременно, таймаут 3 с). Нарушившие правила **не попадают в конфигурацию** и перечисляются в отчёте `{check_id, reason}` — `target_<причина>` или `resolves_to_non_global` (самопроверка показывает их заказчику). Имя, которое сейчас не разрешается, остаётся в конфигурации — движок сообщит «лежит». Для `dns`-проверки имя запроса задаётся публичному резолверу и не разрешается нами.

### 4.3 Цикл опроса

Задача `monitor_poll` (каждые 10 с) и «Проверить сейчас» выполняют один и тот же `poll_cycle`, **в одной транзакции** и под рекомендательной блокировкой PostgreSQL (два цикла не идут одновременно; второй пропускается):

1. Прочитать результаты движка. Ошибка движка не создаёт ни падений, ни восстановлений: **тишина — не авария сервисов** (`monitor.last_error`).
2. Сохранить только **новые** результаты живых проверок (позже уже сохранённого) и добавить их в почасовые итоги.
3. По каждому живому сервису продвинуть автомат алертов (раздел 6) и записать состояние; состояние исчезнувших сервисов удалить.
4. Записать открытие и закрытие инцидентов; положить сообщения в очередь (`ON CONFLICT DO NOTHING` по `dedup_key` — одно и то же сообщение не ставится дважды).
5. **Страж движка:** если у живых проверок нет ни одного результата дольше 300 с (отсчёт — от последнего результата, но не раньше момента, когда появилась первая живая проверка: только что добавленная проверка не делает движок «мёртвым»), ставится ОДНО сообщение «мониторинг не отвечает» и, когда результаты вернулись, ОДНО «восстановлен».

Время срабатывания: худший случай от начала простоя до сообщения = интервал + (порог−1)·интервал + таймаут + задержка склейки + шаг опроса. При интервале 20 с, пороге 3, таймауте 5 с, склейке 10 с и опросе 10 с — **≈ 85 с** (`≤ 2 минуты` из приёмки `04`); при интервале 30 с — ≈ 115 с.

### 4.4 Формат ответа Gatus

`GET {MONITOR_ENGINE_URL}/api/v1/endpoints/statuses?page=N&pageSize=100` — массив `{name, group, key, results: [{status, hostname, duration (нс), errors: [текст], conditionResults: [{condition, success}], success, timestamp}]}`; читаются страницы, пока не придёт неполная. Результат без булева `success` или с непонятным временем пропускается. Текст неудачи: первая ошибка движка (до 200 символов), иначе первое невыполненное условие с кодом ответа, иначе «HTTP N».

## 5. Политика SSRF

Проверки исполняет наш VPS; цель, введённая заказчиком (или злоумышленником с украденным токеном), не должна дотянуться до внутренней сети сервера. Эталон — `targets.py`, векторы — `targets.json` (одни и те же правила на сервере и в форме клиента).

Уровни защиты:
1. **Запись** (`validation_failed` при синхронизации): `check_host` / `check_url` для `monitor_servers.host` и целей проверок.
2. **Генерация конфигурации** (раздел 4.2): повторный суд + разрешение имён.
3. **Сеть:** движок — в отдельной сети `monitor`, без доступа к PostgreSQL и api, без опубликованных портов; рекомендация для VPS — правило `DOCKER-USER` против адресов хоста и `169.254.169.254` (`deploy/README.md`).
4. **Редиректы не выполняются** (`ignore-redirect`): публичный сайт не может перенаправить проверку внутрь.
5. **Поля** с символами, имеющими смысл для движка (`keyword`, `expected_value`), ограничены одним безопасным «токеном».

Правила `check_host(host)` → `{valid, host}` или `{valid: false, reason}`:
- пусто → `empty`; длина > 253 → `too_long`; пробелы, управляющие, `/ \ @ ? # %` → `bad_chars`;
- **IP-адрес** (IPv6 можно в скобках): допустим только **публичный** — не loopback, не private, не link-local (`169.254/16` с metadata, `fe80::/10`), не CGNAT `100.64/10`, не unspecified, не multicast, не reserved, не документационные диапазоны; адрес IPv4 внутри IPv6 (`::ffff:a.b.c.d`) судится по IPv4; иначе `non_global_ip`. Возвращаемый `host` — как введён, строчными и без скобок (без канонизации IPv6: Dart её не обязан повторять);
- **имя:** только ASCII (IDN — в punycode `xn--`), после снятия одной конечной точки и приведения к нижнему регистру: хотя бы две метки (`single_label` — `localhost`, `postgres`, `api`, `gatus`), метки `[a-z0-9-]`, 1–63, без дефиса по краям (`bad_label`), **последняя метка — буквы 2–63 или `xn--…`** (`bad_tld`: так отсекаются `127.1`, `0x7f.0.0.1`, `0177.0.0.1`, `example.c`; десятичная форма `2130706433` — `single_label`); имена, оканчивающиеся на `localhost`, `local`, `localdomain`, `internal`, `intranet`, `lan`, `home`, `corp`, `home.arpa`, `invalid`, `test`, `example`, `onion` → `reserved_name`;
- `check_url(url)`: длина ≤ 2 000, без пробелов, управляющих и `\` (`bad_chars`), схема `http`/`https` (`scheme`), без логина и пароля (`userinfo`), без фрагмента (`fragment`), порт 1…65535 (`bad_port`), непустой хост (`no_host`), далее `check_host`;
- `check_addresses(адреса)` (после разрешения имени): пусто → `no_address`; любой непубличный → `resolves_to_non_global`.

**Остаточный риск** (принят): имя может разрешиться во внутренний адрес **между** двумя генерациями (подмена DNS, «DNS rebinding»); его закрывают сетевая изоляция (уровень 3) и редиректы-без-следования. Адреса внутренних сетей, которые заказчик *хочет* мониторить, — вне задачи (мониторинг идёт с VPS, до них он не дотянется).

## 6. Алерты и антиспам

Эталон — `alerts.py` (чистые функции, целые секунды), векторы — `alerts.json`, `quiet.json`.

### 6.1 Правила

Параметры (`Policy`, по умолчанию): подтверждение падения проверки `fail_threshold = 3` неудач подряд; подтверждение восстановления `recover_threshold = 2` успехов подряд; склейка `group_delay = 10` с; флаппинг `flap_changes = 4` смены статуса за `flap_window = 1 800` с; напоминания `reminder_first = 3 600` с, затем `reminder_every = 14 400` с; склейка сообщений от `group_min = 2` сервисов, подозрение на мониторинг от `mass_failure = 3`.

1. Статус **проверки**: `unknown` → `up` по первому успеху; `down` после 3 неудач подряд; `down` → `up` после 2 успехов подряд. Статус **сервиса** — `down`, пока лежит хотя бы одна его проверка; иначе `up`, если есть хоть одна `up`.
2. Подтверждённое падение сервиса открывает **инцидент** (`n` растёт у сервиса; начало — время первой неудачи серии). Через `group_delay` с (если сервис всё ещё лежит) уходит ОДНО сообщение `down` (сервис, с какого времени, причины по проверкам). **Если сервис восстановился раньше — тишина.** Повторное падение, которое не подтвердило ни одно сообщение, нового сообщения не рождает.
3. **Восстановление:** ОДНО сообщение `recovered` (длительность простоя) — только по инциденту, о котором было сообщение `down`. Не откладывается тихими часами.
4. **Напоминания** `reminder`, пока лежит: через час после сообщения о падении, дальше каждые 4 часа.
5. **Флаппинг:** 4 подтверждённые смены статуса сервиса (в обе стороны) за 30 минут → ОДНО сообщение `flapping` и тишина (ни `down`, ни `recovered`, ни `reminder`); когда 30 минут без смен — ОДНО `stable` с текущим статусом; если сервис при этом лежит, сообщение `stable` засчитывается как сообщение о падении, напоминания возобновляются.
6. **Одновременные:** `down` (и `recovered`) нескольких сервисов в одном цикле склеиваются в `down_group` (`recovered_group`); от 3 сервисов — `suspect_monitor` («возможна проблема на стороне мониторинга»).
7. **Тихие часы** (`MONITOR_QUIET_START`/`END`, `HH:MM`, окно `[начало, конец)`, может переходить через полночь; нет одного из концов или они равны — тихих часов нет): для **некритичного** сервиса `down`, `reminder` и `flapping` ждут конца окна (`down` уйдёт, если сервис к тому времени всё ещё лежит; короткий простой внутри окна не даёт ни одного сообщения; `flapping`, пришедшийся на окно, и его `stable` — не отправляются). **Критичный** сервис и `recovered` не удерживаются. Поясной суточный сдвиг (летнее время) учитывается: окно считается по часам `MONITOR_TIMEZONE`.
8. **Тишина — не восстановление:** отсутствие новых результатов ничего не меняет в состоянии сервиса (раздел 4.3, шаг 1 и страж движка).

### 6.2 Состояние сервиса (JSON в `monitor_state`)

`{status, checks: {id: {status, fails, oks, fail_since, reason}}, seq, incident: {n, started_at, confirmed_at, alert: pending|sent|suppressed, alerted_at, next_reminder} | null, recover_pending, flips: [t…], flapping, flap_notice: null|pending|sent|suppressed}`.

### 6.3 Гарантия «ровно один раз»

На уровне логики: `down` и `recovered` на инцидент рождаются автоматом не более одного раза (свойство проверяется случайными сценариями); очередь не принимает второго сообщения с тем же `dedup_key` (`<вид>:<сервис>#<n>`, для `flapping`/`stable` — `<сервис>@<время>`; для группы — перечень). Транспорт — **«не менее одного раза»**: если процесс упал между ответом Telegram и пометкой `sent_at`, сообщение уйдёт ещё раз (Telegram не даёт идемпотентности); окно такого сбоя — доли секунды.

### 6.4 Доставка

Задача `monitor_deliver` (каждые 5 с): сообщения в порядке очереди, **около одного в секунду**; успех → `sent_at`. Ответ `429` — все неотправленные ждут `retry_after` (попытка не засчитывается); сеть и 5xx — повтор через `min(300, 5·2^попытка)` с; **неисправимое** (неверный токен, бот заблокирован, чат не найден, сообщение отклонено) — повтор раз в 10 минут (исправленный `.env` лечит очередь сам), остановка пачки; после 20 попыток — отказ. Сообщение старше 6 часов не отправляется (устаревшее «лежит» после починки только путает). Без `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` очередь копится, `last_error = not_configured`.

## 7. Telegram за интерфейсом

`Notifier` (`configured`, `send(text) → SendResult{ok, error, retry_after, permanent}`): `TelegramNotifier` (`POST {TELEGRAM_API_BASE}/bot<токен>/sendMessage`, `chat_id`, текст ≤ 4 096, без предпросмотра ссылок, таймаут 10 с) и `NullNotifier`. Исключения `httpx` (в тексте — адрес с токеном) **не пропускаются дальше**: отображаются в код `network`. Коды: `not_configured`, `network`, `rate_limited`, `server_error`, `unauthorized` (401/403), `chat_not_found`, `bad_request`, `bad_response`. В CI настоящий Telegram не вызывается: тесты — на записанных ответах (`backend/tests/data/monitoring/telegram_responses.json`, в документированной форме Bot API; **заменить записями живого бота** в фазе сборки) и на подделках.

Тексты — обычные, без разметки и без ссылок: «ЛЕЖИТ: Сайт (VPS)», «С 14:32», строки «- Проверка: причина»; «РАБОТАЕТ …/Простой: 12 мин»; «ВСЁ ЕЩЁ ЛЕЖИТ …»; «НЕСТАБИЛЕН …»; «УСПОКОИЛСЯ …»; «ЛЕЖАТ (3): …», «РАБОТАЮТ (3): …»; «МОНИТОРИНГ НЕ ОТВЕЧАЕТ / ВОССТАНОВЛЕН»; «Проверка связи …». Причина — короткая (≤ 120 символов, без управляющих).

## 8. API «Пульс» (все эндпоинты — по токену устройства и `X-Client-Schema-Version`)

| Метод и путь | Ответ |
|---|---|
| `GET /monitoring/pulse` | **снимок целиком** (ниже), заголовки `ETag` и `Cache-Control: private, no-cache`; `If-None-Match` с тем же тегом → `304` без тела |
| `POST /monitoring/refresh` | «Проверить сейчас»: прочитать движок (не чаще раза в 5 с) и вернуть новый снимок; `503 monitoring_not_configured` без `MONITOR_ENGINE_URL` |
| `GET /monitoring/incidents?limit=1..100&before=<момент>&service_id=` | `{incidents: [{id, service_id, service_name, started_at, ended_at, duration_seconds, reason, check_ids}], next_before}`, новые первыми |
| `GET /monitoring/self-check` | `{engine: {configured, last_poll_at, lag_seconds, error}, config: {synced_at, checks_active, checks_rejected: [{check_id, reason}]}, telegram: {configured, last_success_at, last_error, queued}}` |
| `POST /monitoring/telegram/test` | `{ok, error}` — только код ошибки |

Снимок: `{generated_at, engine: {configured, last_poll_at, healthy, error, telegram_configured}, summary: {services, down, up, unknown}, services: [{id, server_id, name, server, critical, status, down_since, availability: {h24, d7, d30}, response_ms, open_incident, checks: [{id, kind, name, status, last_at, response_ms, availability, spark}]}]}`. Порядок: упавшие первыми, затем неизвестные, затем работающие, внутри — по имени. `spark` — последние до 30 результатов проверки, от старых к новым: миллисекунды или `-1` для неудачи. `engine.healthy` — опрос был не позже 60 с назад и без ошибки. Моменты — `YYYY-MM-DDTHH:MM:SSZ`.

**Офлайн-кэш (клиент).** Клиент хранит последний снимок целиком и его `generated_at`; без сети экран показывает его с подписью «Данные на HH:MM · нет сети», кнопки «Проверить» неактивны. `ETag` не зависит от `generated_at`: неизменный «Пульс» отвечает `304`. Серверы, сервисы и проверки доступны офлайн как обычные синхронизируемые данные (их можно править без сети; изменения уходят при синхронизации и попадают в конфигурацию движка в течение минуты).

## 9. Метрики

- **Доступность** `availability_bp(buckets, now, hours)`: сумма `ok` на сумму `total` часовых итогов окна, в базисных пунктах вниз (`10 000 = 100 %`), `null` без проверок. Окно — `hours` корзин, считая от корзины момента `now` включительно (24 часа — 24 корзины, текущая неполная среди них): `h24` = 24, `d7` = 168, `d30` = 720. Доступность сервиса — по всем его проверкам вместе. Внеочередных пауз и окон обслуживания нет.
- **Отклик** проверки — длительность её **последнего результата**, если он успешен (иначе `null`); сервиса — среднее таких значений по проверкам, вниз.
- Подсветка порогов (`доступность < 99 %`, `отклик > 500 мс`, «лежит» при `< 95 %` или `> 2 000 мс` — `02` §5.5) — решение клиента; сервер отдаёт числа и статус автомата.

## 10. Конфигурация (переменные окружения)

`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (секреты; пусто = не настроено), `TELEGRAM_API_BASE` (по умолчанию `https://api.telegram.org`; локальный Bot API), `MONITOR_ENGINE_URL` (`http://gatus:8080`; пусто — движка нет), `MONITOR_CONFIG_PATH` (`/monitor/config.yaml`), `MONITOR_DNS_RESOLVER` (`1.1.1.1:53`), `MONITOR_TIMEZONE` (`Europe/Moscow`), `MONITOR_QUIET_START`/`MONITOR_QUIET_END` (`HH:MM`, оба или ни одного). Пустое значение в compose = «по умолчанию»/«не настроено». Значения секретов добавляются в список редактора логов (`Settings.secret_values`) и в API, и в worker.

`deploy/docker-compose.yml`: сервис `gatus` (`twinproduct/gatus`, образ `GATUS_IMAGE`; закрепить версию в фазе сборки) в **собственной сети `monitor`**, `read_only`, `cap_drop: ALL`, без портов; тома `monitor_config` (конфигурация: worker пишет, gatus читает) и `gatus_data` (sqlite движка); `api` и `worker` присоединены и к `internal`, и к `monitor`. История «Пульса» (результаты, итоги, инциденты) — в PostgreSQL и в его ежедневный дамп; том `gatus_data` в бэкап не входит.

## 13. Что нельзя проверить без Docker и без живых сервисов (фаза сборки)

1. `docker compose config -q` и запуск стека не выполнялись (Docker недоступен): compose-файл проверен YAML-парсером и тестом на изоляцию сети; `gatus` не запускался.
2. Живой Gatus: формат `/api/v1/endpoints/statuses` (в частности единицы `duration`), подхват изменённого файла конфигурации, имена условий `[CERTIFICATE_EXPIRATION]`, `[DNS_RCODE]`, `pat()`, отказ от пустого списка endpoint'ов.
3. Живой Telegram: записи ответов — рукописные в документированной форме; реальный бот, лимиты, `retry_after`.
4. Приёмка «алерт ≤ 2 минуты» на тестовом сервисе.
