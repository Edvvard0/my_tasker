# Этап 3. Спецификация: ИИ-чат (онлайн)

> Контракт между бэкендом (`backend/src/tasker/ai/`) и клиентом (`app/`). Клиент реализуется по этому документу. Опирается на `stage1_sync_and_auth.md` (синхронизация, SSE, ошибки) и `stage2_calendar_tasks.md` (задачи, события); уточняет §5.7 и §6.1 из `01_ARCHITECTURE_PLAN.md`. При расхождении с 01 действует этот документ, при расхождении с `04_DECISIONS_AND_ROADMAP.md` — 04.
> Идентификаторы, поля JSON и коды ошибок — на английском. Ключ polza.ai существует только на сервере и нигде не появляется (раздел 9).

## 0. Принципы

- **Сервер — прокси и исполнитель инструментов.** Клиент собирает контекст локально и шлёт запрос; сервер добавляет системную часть, обращается к polza.ai (OpenAI-совместимый API), ретранслирует поток клиенту по SSE, исполняет **читающие** инструменты над данными в своей БД, а **пишущий** `create_task` превращает в **предложение** (`ai_tool_proposals`). Задачу создаёт клиент (обычная синхронизация).
- **Серверные записи — обычные синхронизируемые строки.** Сообщение ассистента и предложения сервер пишет через тот же движок, что и `POST /sync/push`, от имени виртуального устройства `SERVER_DEVICE_ID = 00000000-0000-7000-8000-000000000a11` (в HLC и в `origin_device_id`). Все устройства получают строки обычным `pull`, а сигнал `changes` на `/events` — **все** устройства, включая то, что запросило ответ.
- Новых «синхронизационных» эндпоинтов нет. Все HTTP-эндпоинты ниже требуют `Authorization` и `X-Client-Schema-Version` (как в Этапе 1). Ошибки — единая форма Этапа 1: `{"error": {"code", "message", "details"}}`; клиент ветвится только по `code`.
- Деньги — целые копейки (`*_kopecks`), везде. Токены — целые.
- Время — как в Этапе 1/2 (UTC + IANA).

## 1. Синхронизируемые таблицы

Служебные поля — как в Этапе 1 (3.1). «неизм.» = неизменяема после создания (`immutable_field`). Реестр: родители вперёд (`backend/src/tasker/ai/tables.py`, `AI_TABLES`):

```
ai_agent_profiles ── ai_prompt_versions
ai_context_presets      ai_model_favorites
ai_conversations ── ai_messages ── ai_tool_proposals
```

Каскады как в Этапе 1 (3.5): удаление профиля убирает его версии промтов; удаление чата — сообщения, а с ними предложения; восстановление родителя возвращает каскадно удалённых детей. Колонки `*_id` без внешнего ключа — мягкие ссылки (как `tasks.project_id`, Этап 2, 2.3).

### 1.1 `ai_agent_profiles`

| Колонка | Тип | Правила |
|---|---|---|
| `seed_key` | text, null | неизм.; один из `general`, `calendar_tasks`, `work`, `finance`, `study`, `sleep` для предустановленных, `null` для пользовательских |
| `name` | text | обяз., 1–100, не пустое после trim |
| `topic` | enum | обяз.: `general` \| `calendar_tasks` \| `work` \| `finance` \| `study` \| `sleep` \| `custom` |
| `system_prompt` | text | обяз., 1–20 000, не пустое после trim |
| `prompt_version` | int | обяз., 1…1 000 000; номер текущей версии промта |
| `default_model` | text, null | ≤ 200; id модели из каталога (не проверяется) |
| `enabled_tools` | json | обяз.: список имён инструментов (раздел 6), ≤ 32 элементов, каждое 1–64 символа |
| `default_context_preset_id` | uuid, null | мягкая ссылка на `ai_context_presets` |
| `position` | int | обяз., 0…1000 |

`id`: для предустановленных — `uuid5(ns("ai_agent_profiles"), seed_key)`, где `ns(table) = uuid5(NAMESPACE_URL, "urn:my-tasker:<table>")` (как в Этапе 2, 2.2); для пользовательских — UUIDv7 клиента. Предустановленные профили создаёт сервер (раздел 7), клиент их **не создаёт и не удаляет** (правило клиента; сервер удаление не запрещает).

### 1.2 `ai_prompt_versions`

История правок системного промта. Строка = одна версия.

| Колонка | Тип | Правила |
|---|---|---|
| `profile_id` | uuid → `ai_agent_profiles` | обяз., неизм.; каскад |
| `version` | int | обяз., неизм.; 1…1 000 000 |
| `text` | text | обяз., 1–20 000 |
| `source` | enum | обяз.: `seed` \| `user` \| `reset` \| `rollback` |

`id = uuid5(ns("ai_prompt_versions"), "{profile_id}|{version}")` — две правки одного номера на разных устройствах дают одну строку (слияние по полям, проигравшее — в журнале конфликтов).
**Правка промта на клиенте** (одна локальная транзакция, одна пачка): `version = profile.prompt_version + 1`; создать строку версии (`source = user`), обновить профиль (`system_prompt`, `prompt_version`). **Откат** к версии `K`: то же, но `text` берётся из версии `K`, `source = rollback`, номер — новый (история не переписывается). Серверные версии создаёт `reset` (раздел 7).

### 1.3 `ai_context_presets`

| Колонка | Тип | Правила |
|---|---|---|
| `name` | text | обяз., 1–100, не пустое |
| `sources` | json | обяз.: список объектов `{"source": str, "filter": any, "token_limit": int}` — произвольная форма для клиента, ≤ 32 элемента, всего ≤ 16 КБ |
| `sensitive` | bool | обяз.: «не отправлять в облако» |

Пресет с `sensitive = true` **нельзя** использовать в облачном чате (раздел 5.2).

### 1.4 `ai_model_favorites`

`model_id` (text, обяз., неизм., 1–200), `display_name` (text, обяз., 1–200), `position` (int, 0…1000), `supports_tools` (bool). `id = uuid5(ns("ai_model_favorites"), model_id)`. Id модели сверяется с каталогом (раздел 4): отсутствующие в каталоге клиент помечает «недоступна».

### 1.5 `ai_conversations`

| Колонка | Тип | Правила |
|---|---|---|
| `title` | text | обяз., 0–200 (пусто, пока нет заголовка) |
| `topic` | enum | обяз., как у профиля |
| `agent_id` | uuid, null | мягкая ссылка на профиль |
| `model` | text, null | ≤ 200 |
| `context_preset_id` | uuid, null | мягкая ссылка |
| `pinned`, `archived` | bool | обяз. |
| `mode` | enum | обяз.: `cloud` \| `local`. Сервер отвечает только в `cloud`-беседах; в `local` (Этап 10, ответы офлайн-моделью на телефоне) строки пишет клиент (раздел 1.8). Клиент может менять режим беседы (при переходе в `cloud` локальная `model` вида `local/…` сбрасывается) |

UUIDv7 клиента. **Беседу клиент создаёт локально и должен успеть отправить её на сервер (push) до первого запроса completion**, иначе `404 conversation_not_found` (раздел 5.4).

### 1.6 `ai_messages`

| Колонка | Тип | Правила |
|---|---|---|
| `conversation_id` | uuid → `ai_conversations` | обяз., неизм.; каскад |
| `role` | enum | обяз., неизм.: `user` \| `assistant` \| `tool` \| `system` |
| `text` | text | обяз., 0–400 000: плоский текст (склейка текстовых частей) для списка и поиска |
| `parts` | json | обяз.: список частей (ниже), ≤ 400 элементов, ≤ 1 МБ |
| `status` | enum | обяз.: `streaming` \| `done` \| `error` \| `cancelled`. Сервер в Этапе 3 пишет только `done`, `error`, `cancelled` (запись создаётся один раз, в конечном состоянии); `streaming` зарезервирован |
| `model` | text, null | ≤ 200 |
| `agent_id` | uuid, null | профиль, по которому собран ответ |
| `prompt_version` | int, null | версия промта профиля на момент ответа |
| `prompt_tokens`, `completion_tokens` | int, null | ≥ 0, сумма по всем обращениям к модели в этом ответе |
| `cost_kopecks` | int, null | ≥ 0 |
| `latency_ms` | int, null | ≥ 0: от получения запроса до конца |
| `finish_reason` | text, null | ≤ 64: `stop`, `length`, `tool_calls`, `content_filter`, `awaiting_approval` |
| `error_code` | text, null | ≤ 64: код раздела 8 при `status = error` |

UUIDv7: сообщения пользователя создаёт клиент (`role = user`, `status = done`), сообщение ассистента — id присылает клиент в запросе, строку пишет сервер.

**Части (`parts`)** — объекты с полем `type`:

```json
{"type": "text", "text": "Привет"}
{"type": "tool_call", "id": "call_1", "name": "get_tasks", "arguments": {"status": ["todo"]}}
{"type": "tool_result", "tool_call_id": "call_1", "name": "get_tasks", "content": "{\"count\":3,...}", "is_error": false}
{"type": "proposal", "proposal_id": "uuid", "tool_call_id": "call_2", "tool": "create_task"}
```

`arguments` — разобранный объект (`null` для вызова с невалидным JSON; сырая строка в таком случае хранится в поле `raw_arguments`). Порядок частей = порядок событий. Содержимое `tool_result` обрезается до 20 000 символов.

### 1.7 `ai_tool_proposals`

Предложение пишущего инструмента. В `cloud`-беседах его создаёт **сервер** вместе с сообщением (одна транзакция), в `local`-беседах — клиент (раздел 1.8); клиент меняет поля решения.

| Колонка | Тип | Правила |
|---|---|---|
| `message_id` | uuid → `ai_messages` | обяз., неизм.; каскад |
| `tool_call_id` | text | обяз., неизм., 1–128: id вызова от модели |
| `tool` | text | обяз., неизм., 1–64 (`create_task`) |
| `entity_type` | text | обяз., неизм.: что создаётся (`task`) |
| `entity_id` | uuid | обяз., неизм.: **id, который клиент обязан дать создаваемой сущности** (UUIDv7, назначает сервер) |
| `original_arguments` | json | обяз., неизм.: объект, как предложила модель (после проверки схемы) |
| `arguments` | json | обяз.: объект; пользователь правит его в карточке; изначально равен `original_arguments` |
| `status` | enum | обяз.: `pending` \| `approved` \| `rejected` \| `edited_approved` |
| `reject_reason` | text, null | ≤ 1000 |
| `decided_at` | datetime, null | момент решения |

`id` — UUIDv7 сервера. Межполевые проверки (`validation_failed`): `arguments` и `original_arguments` — объекты; `pending` ⇒ `decided_at = null`; `approved`, `rejected`, `edited_approved` ⇒ `decided_at` задан.

### 1.8 Беседы `mode = local` (Этап 10)

Офлайн-модель на телефоне отвечает без сервера, поэтому **клиент** пишет строки ответа обычным `POST /sync/push` (сервер ничего не создаёт и не вызывает polza.ai). Облачные правила не меняются: в `cloud`-беседах ответ по-прежнему пишет сервер.

- **Сообщения.** Клиент вправе создавать `role = assistant` и `role = tool` (кроме `user`), в том числе со `status = streaming` с последующей правкой `text`/`status`; серверные проверки формы те же (раздел 1.6). Модель локального ответа — `model = "local/<id>"` (например `local/gemma-4-e2b-it`), `cost_kopecks = 0`, `prompt_tokens`/`completion_tokens` — оценка или метрики рантайма. Лимит polza.ai и таблица `ai_spend` к таким сообщениям не относятся. Клиент Этапа 10 пишет сообщение ассистента один раз, в конечном состоянии (`done`, `error`, `cancelled`); результат инструмента — частью `tool_result` в `parts` (строки `role = tool` допустимы, но не обязательны).
- **Предложения.** Клиент создаёт `ai_tool_proposals` для `local`-беседы сам: `entity_id` — **новый UUIDv7 клиента** (неизменяем, как и у серверных), `status = pending`, `original_arguments = arguments`. Строка пишется в одной пачке с сообщением (сначала сообщение). Одобрение, отклонение и защита от двойного одобрения — раздел 2 без изменений: задача создаётся с `id = entity_id`, поэтому при любом числе одобрений существует одна строка `tasks`.
- **Контракт сервера** (проверено тестами `backend/tests/ai/test_local_conversations.py`): клиентские строки `assistant`/`tool` и предложения принимаются без изменения кода; неизменяемость `entity_id`, `message_id`, `tool_call_id`, `tool`, `entity_type`, `original_arguments` действует и для них (`immutable_field`).
- **Формат ответа модели для `create_task`** (клиентская сторона, для справки): JSON `{"tool":"create_task","arguments":{…}}` с теми же полями и проверками, что в 6.3; невалидный JSON — один повтор с подсказкой, затем обычный текст без карточки.

## 2. Жизненный цикл предложения и идемпотентное одобрение

1. Модель вызывает `create_task`. Сервер проверяет аргументы по схеме (раздел 6.3); при ошибке предложения **нет**, модели возвращается результат-ошибка (она может исправиться в следующем обращении, пока не исчерпан лимит шагов). При успехе сервер создаёт `ai_tool_proposals` со `status = pending`, новым `entity_id` и шлёт SSE-событие `proposal`. Результат вызова для модели — «предложение создано, ждёт одобрения пользователя».
2. Клиент показывает карточку (поля из `arguments`: заголовок, дата и время или «без времени», приоритет, проект, заметки, теги). Пользователь правит поля → клиент пишет новый `arguments` (локально, обычная правка строки).
3. **Одобрить.** Клиент в **одной локальной транзакции и одной пачке outbox** (порядок операций: сначала задача, потом предложение):
   1. создаёт задачу (`tasks`, Этап 2) **с `id = proposal.entity_id`**, `source = "ai"`, полями из `arguments` (отображение — 6.3), `status = todo` при наличии даты или времени, иначе `inbox` (4.1 Этапа 2);
   2. обновляет предложение: `status = approved` (если `arguments` равны `original_arguments`, иначе `edited_approved`), `decided_at = now`, актуальный `arguments`.
4. **Отклонить:** `status = rejected`, `reject_reason` (необязательно), `decided_at = now`. Задача не создаётся.
5. **Защита от двойного одобрения.** `entity_id` назначен сервером один раз и неизменяем, а клиент создаёт задачу ровно с этим id. Поэтому при любом числе одобрений (двойное нажатие, два устройства, повтор после потери ответа) существует **не более одной** строки `tasks` с этим id: повторное создание — это обычный `upsert` той же строки (Этап 1, 3.4), а равные значения не порождают конфликтов. Клиент перед одобрением проверяет локально: если задача с `id = entity_id` уже есть — создание пропускает и только ставит статус предложения. Предложение с `status ≠ pending` клиент не позволяет менять в интерфейсе.
6. **Решения «одобрить» и «отклонить» с двух устройств одновременно** разрешаются по полям (LWW, Этап 1, 3.4); сервер отклоняет операции, дающие несогласованную строку (раздел 1.7), но не знает, что задача создана. Возможный исход: предложение `rejected`, а задача существует (устройство, создавшее её, «проиграло»). Дубля задачи нет; пользователь видит задачу и может её удалить. Это принятое поведение для личного приложения.
7. **Итог для модели.** При сборке истории для следующего запроса клиент добавляет к assistant-сообщению с вызовом инструмента сообщение `tool` (раздел 5.1): `pending` — «awaiting user approval»; `approved`/`edited_approved` — «task created: <entity_id>» (при правках — также итоговые аргументы); `rejected` — «user rejected: <reason>».

## 4. Каталог моделей — `GET /ai/models`

Сервер кэширует `GET {POLZA_BASE_URL}/models` (запрос без ключа) на `POLZA_MODELS_TTL_SECONDS` (по умолчанию 3600 с), нормализует, оставляет чат-модели. Параметры: `refresh=true` — игнорировать кэш; `q` — подстрока в id/имени без учёта регистра; `tools=true` — только с инструментами.

`200`:
```json
{"models": [{"id": "openai/gpt-4o", "name": "GPT-4o", "context_length": 128000,
             "max_completion_tokens": 16384, "supports_tools": true,
             "price_input_kopecks_per_mtok": 25000, "price_output_kopecks_per_mtok": 100000}],
 "fetched_at": "datetime", "stale": false}
```
- Цены — в копейках за 1 млн токенов (целые, для показа; сервер считает по точным десятичным значениям); `null`, если провайдер цену не отдал. Имена полей провайдера для цен и признака инструментов (`supported_parameters` содержит `tools`) разбираются устойчиво.
- Если обновление не удалось, а в кэше есть устаревшие данные — они отдаются с `"stale": true`; если кэша нет — `502 upstream_error` (или `504 upstream_timeout`).
- Id моделей в коде не зашиты: избранное хранит id, клиент сверяет его с этим списком.

## 5. Ответ чата — `POST /ai/chat/completions`

### 5.1 Запрос

```json
{
  "conversation_id": "uuid",
  "assistant_message_id": "uuid-v7",
  "model": "openai/gpt-4o",
  "agent_id": "uuid | null",
  "context": {"text": "…собранный клиентом контекст…", "preset_id": "uuid | null", "contains_sensitive": false},
  "messages": [{"role": "user", "content": "…"},
               {"role": "assistant", "content": "…", "tool_calls": [{"id": "call_1", "type": "function", "function": {"name": "create_task", "arguments": "{…}"}}]},
               {"role": "tool", "tool_call_id": "call_1", "content": "task created: …"}],
  "tools": ["get_tasks", "get_events", "create_task"],
  "timezone": "Europe/Moscow",
  "params": {"temperature": 0.7, "max_tokens": 2000}
}
```
- `messages` — история в формате OpenAI **без** `system` (системную часть собирает сервер): роли `user`, `assistant` (`content` может быть `null` при `tool_calls`), `tool`. Клиент сам обрезает историю по бюджету токенов. ≤ 400 сообщений, `content` ≤ 100 000 символов, весь `context.text` ≤ 200 000.
- `agent_id` — профиль; необязателен. Сервер берёт из БД **текущий** `system_prompt` профиля и записывает `prompt_version` в сообщение.
- `tools` — имена включённых инструментов; `null`/нет = `enabled_tools` профиля, а без профиля — все зарегистрированные. Неизвестное имя → `422 unknown_tool`. Если каталог знает, что модель не поддерживает инструменты, они не отправляются (в `start` приходит `"tools_enabled": false`).
- `timezone` — IANA, по умолчанию `UTC`; нужна для даты/времени в системной части и для фильтров инструментов.
- `params` необязательны: `temperature` 0…2, `max_tokens` 1…32 768.

**Системная часть**, которую собирает сервер (одно `system`-сообщение): (1) `system_prompt` профиля; (2) блок «сейчас»: текущая дата, время, день недели, таймзона и чётность текущей недели (по `calendar.week_cycle` из `user_settings`, Этап 2, раздел 6; если ключа нет — строка опускается); (3) `context.text` клиента.

### 5.2 Предварительные проверки (до начала потока, обычные HTTP-ошибки)

В порядке проверки: `422 validation_error`; `503 ai_not_configured` (нет ключа); `403 sensitive_context_forbidden` (`context.contains_sensitive = true`, либо `preset_id` указывает на живой пресет с `sensitive = true`); `404 conversation_not_found`; `404 agent_not_found` (`agent_id` задан, строки нет); `422 unknown_tool`; `404 model_not_found` (каталог доступен и модели в нём нет); `409 message_exists` (строка с `assistant_message_id` уже есть или ответ с таким id сейчас идёт; `details.status`); **`402 limit_exceeded`** (раздел 5.5; `details`: `limit_kopecks`, `spent_kopecks`, `month`).

### 5.3 Поток

`200`, `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`. Формат кадра: `event: <name>\ndata: <json в одну строку>\n\n`. События:

| event | data | когда |
|---|---|---|
| `start` | `{"message_id", "model", "agent_id", "prompt_version", "tools_enabled"}` | сразу |
| `delta` | `{"text"}` | фрагмент текста ответа |
| `tool_call` | `{"id", "name", "arguments"}` | вызов собран целиком (`arguments`: объект или `null`, если JSON невалиден) |
| `tool_result` | `{"tool_call_id", "name", "is_error", "preview"}` | читающий инструмент выполнен (`preview` ≤ 200 символов) |
| `proposal` | `{"proposal_id", "tool_call_id", "tool", "entity_type", "entity_id", "arguments"}` | создано предложение |
| `usage` | `{"prompt_tokens", "completion_tokens", "cost_kopecks"}` | накопленно, после каждого обращения к модели |
| `done` | `{"message_id", "status": "done", "finish_reason", "prompt_tokens", "completion_tokens", "cost_kopecks"}` | ответ сохранён, поток закрывается |
| `error` | `{"code", "message", "retryable", "message_id"}` | сбой после начала потока; ответ сохранён со `status = error` (частичный текст сохраняется), поток закрывается |
| `ping` | `{}` | каждые `AI_SSE_PING_SECONDS` (15 с), пока нет других событий |

**Цикл инструментов.** Сервер вызывает модель; если она запросила инструменты, читающие выполняются на сервере, их результаты добавляются в разговор, и модель вызывается снова. Не более `AI_MAX_TOOL_ITERATIONS` (5) обращений к модели на ответ; последнее идёт с `tool_choice: "none"`, а вызов инструмента в нём — ошибка `tool_loop_limit`. Если в обращении запрошен `create_task` (хотя бы один успешный вызов), то после его обработки цикл **завершается**: `done` с `finish_reason = "awaiting_approval"`; читающие вызовы того же обращения выполнены и сохранены, но модель их результатов не видит до следующего запроса. Параллельные вызовы поддерживаются.

**Сохранение.** В конце (в том числе при ошибке и отмене) сервер одной транзакцией пишет строку `ai_messages` (+ строки `ai_tool_proposals`) и только потом шлёт `done`/`error`. Id сообщения известен клиенту с начала (`assistant_message_id`); строка придёт обычным `pull`, дублей нет. Если запись не удалась, приходит `error` с `code = persist_failed` и строка не создана.

### 5.4 Что клиент делает по событиям

Рисует `delta`, показывает `tool_call`/`tool_result` как шаги, `proposal` — карточкой. После `done`/`error` запускает цикл синхронизации и берёт сохранённое сообщение из БД. При обрыве соединения без `done`/`error` (сеть, рестарт сервера) ответ мог быть сохранён частично (`cancelled`) или не сохранён вовсе: клиент после синхронизации ищет сообщение по `assistant_message_id`; если его нет — предлагает повторить **с новым** `assistant_message_id`.

### 5.5 Расход и лимит

- **Стоимость обращения** в копейках: если провайдер вернул в `usage` стоимость в рублях (`cost`, затем `cost_rub`, `total_cost`) — она, округление «half up» до копейки; иначе `ceil((prompt_tokens × price_in + completion_tokens × price_out) / 1 000 000)` рублей → копейки по ценам каталога (точные десятичные значения); нет ни того ни другого (модель без цены) — 0. Если провайдер не прислал `usage` совсем, токены оцениваются как `ceil(символов / 3)` (метка `estimated` в учёте). Стоимость ответа = сумма по обращениям.
- **Учёт** — таблица `ai_spend` (не синхронизируется, переживает удаление чатов): строка на обращение (`id`, `created_at`, `message_id`, `model`, `prompt_tokens`, `completion_tokens`, `cost_kopecks`, `estimated`). Пишется сразу после каждого обращения, даже если ответ потом оборван. Обращение, от которого не пришло ни одного байта (ошибка провайдера до начала потока, отмена до первого события), не тарифицируется и строки не создаёт; оборванное после первых данных — тарифицируется (по `usage`, если он успел прийти, иначе по оценке).
- **Месяц** — календарный в таймзоне `AI_BILLING_TIMEZONE` (по умолчанию `Europe/Moscow`).
- **Лимит** — значение `ai.monthly_limit_kopecks` в `user_settings` (целое ≥ 0; ключа нет или строка удалена (так лимит снимают), неверный тип значения = лимита нет; `0` блокирует всё). Сервер проверяет `расход за месяц ≥ лимит` **перед каждым обращением к модели**: до начала потока — `402 limit_exceeded`, посреди цикла инструментов — событие `error` `limit_exceeded`. Одно обращение может превысить лимит на свою стоимость (резерва нет). Клиент предупреждает пользователя сам (например, при 80 %).

`GET /ai/usage?month=YYYY-MM` (по умолчанию текущий):
```json
{"month": "2026-10", "limit_kopecks": 50000, "spent_kopecks": 1234, "remaining_kopecks": 48766,
 "requests": 12, "prompt_tokens": 40000, "completion_tokens": 9000,
 "by_model": [{"model": "openai/gpt-4o", "requests": 12, "prompt_tokens": 40000, "completion_tokens": 9000, "cost_kopecks": 1234}]}
```
`limit_kopecks` и `remaining_kopecks` — `null`, если лимита нет; `remaining_kopecks` не меньше 0.

### 5.6 Отмена

Закрытие соединения клиентом (или `POST /ai/chat/{message_id}/cancel` → `200 {"cancelled": true}`, `false`, если такого идущего ответа нет) **прерывает запрос к polza.ai**. Сервер сохраняет накопленное как сообщение со `status = cancelled` (частичный текст, части, токены и стоимость — по полученному `usage`; если `usage` не пришёл, расход обращения оценивается по 5.5) и пишет `ai_spend`. Отмена после того, как сообщение уже сохранено, ничего не делает.

## 6. Инструменты

### 6.1 Реестр

`backend/src/tasker/ai/tools.py`: `ToolSpec(name, description, parameters (JSON Schema), kind = read | write, ...)`. **Как добавить инструмент в Этапах 4–8:** написать модуль с функцией-обработчиком, зарегистрировать её `TOOLS.register(ToolSpec(...))` и импортировать модуль в `ai/builtin.py`; для пишущего задать `entity_type` и проверку аргументов — карточки, предложения и одобрение работают без изменений сервера (клиент добавляет отображение карточки и создание сущности по `entity_id`). Для **предустановленных** профилей список инструментов выводится из кода (`agents.builtin_tools(seed_key)`) на каждый запрос — достаточно добавить имя туда; хранимый `enabled_tools` такого профиля — лишь снимок и игнорируется. Пользовательские профили (без `seed_key`) используют хранимый список. **Провайдеры серверной части контекста** (`CONTEXT_PROVIDERS`, `ai/context.py`) — функции `(ctx) -> str | None`, чей текст добавляется в системную часть после блока «сейчас»; Этап 3 содержит один — «сейчас». Данные разделов (финансы, сон) в облако собирает клиент в `context.text`; серверные провайдеры нужны только тому, что известно серверу.

### 6.2 Читающие инструменты (выполняются на сервере, автоматически)

Читают только живые строки (`deleted_at IS NULL`); строка с удалённым родителем (событие удалённого календаря) тоже скрыта. Результат — JSON-строка (UTF-8, без ASCII-экранирования), ≤ 20 000 символов.

- **`get_tasks`**: `status` (список из 5 статусов), `priority_min`/`priority_max` (1…5; 1 — самый высокий), `due_from`/`due_to` (`YYYY-MM-DD`, включительно; срок считается по дате `due_date` либо по локальной дате `due_at` в `timezone` запроса), `no_due_date` (bool: только без срока), `query` (подстрока в заголовке, без регистра), `include_archived` (по умолчанию `false`), `limit` (1…100, по умолчанию 50). Ответ: `{"count", "truncated", "tasks": [{"id","title","status","priority","due_date","due_time","duration_minutes","recurring","notes"}]}` (`notes` ≤ 300 символов). Сортировка: срок, приоритет, создание.
- **`get_events`**: `from_date`, `to_date` (обязательны, `YYYY-MM-DD`, включительно, не более 62 дней), `limit` (1…200, по умолчанию 50). Повторяющиеся события разворачиваются по правилам Этапа 2 (5.3, отмены и переопределения учитываются). Ответ: `{"count", "truncated", "events": [{"id","title","calendar","all_day","start","end","location","recurring"}]}`; для событий с временем `start`/`end` — локальные `YYYY-MM-DDTHH:MM` в `timezone` запроса, для «весь день» — даты.

### 6.3 Пишущий `create_task`

Аргументы (JSON Schema для модели, затем проверка pydantic; лишние ключи отбрасываются):

| Поле | Правила |
|---|---|
| `title` | обяз., 1–500, не пустое |
| `notes` | ≤ 20 000 |
| `priority` | 1…5 |
| `due_date` | `YYYY-MM-DD`, реальная дата 1970–2200 |
| `due_time` | `HH:MM`, локальное время пользователя; только вместе с `due_date` |
| `duration_minutes` | 1…1440 |
| `project` | ≤ 200: название проекта; сопоставление со строкой `projects` делает клиент (Этап 2, 4.3) |
| `tags` | ≤ 5 строк, каждая по правилам имени тега (Этап 2, 4.3) |

Отображение в `tasks` при одобрении: `title`, `notes`, `priority`, `duration_minutes`; `due_date` без `due_time` → `due_date`; с `due_time` → `due_at` (локальные дата и время в таймзоне пользователя → UTC) и `due_tz` — таймзона пользователя; `project` → `project_id` (если нашёлся); `tags` → строки `task_tags` (создаются тегами с детерминированными id, Этап 2, 2.2); `source = "ai"`.

## 7. Агенты по разделам, промты, сброс

- **Предустановленные профили** (`seed_key`): `general` «Общий», `calendar_tasks` «Календарь и задачи», `work` «Работа», `finance` «Финансы», `study` «Учёба», `sleep` «Сон». У каждого — системный промт на русском (текущая версия сида `SEED_PROMPT_VERSION = 1`), `enabled_tools = [get_tasks, get_events, create_task]` (для `work` ещё `get_projects`, `get_receivables`, `get_work_hours`; при ответе чата список предустановленного профиля всегда берётся из кода, хранимое значение игнорируется), `prompt_version = 1` и строка `ai_prompt_versions` (`source = seed`). Тексты — в `backend/src/tasker/ai/agents.py`.
- **`POST /ai/bootstrap`**: если профили ещё не заводились (метка `ai.seed.v1` в `app_meta`), создаёт все шесть серверными записями; повторный вызов ничего не меняет и не воскрешает удалённые или изменённые пользователем профили. Вызывается и неявно (первый completion, `reset`). `200`: `{"agents": [{"seed_key", "id", "name"}], "tools": [{"name", "kind", "description", "parameters"}], "seed_prompt_version": 1}`. Клиент вызывает его при первом входе в раздел ИИ и после полной пересинхронизации.
- **`POST /ai/agents/{seed_key}/reset`**: профиль получает исходный `system_prompt`, `prompt_version` = предыдущий + 1 и новую строку `ai_prompt_versions` (`source = reset`). Если профиль был удалён, он восстанавливается (`deleted_at = null`). Сервер пишет с меткой HLC, большей всех существующих на строке, поэтому сброс выигрывает у более ранних правок. `200`: `{"changes": [{"table","id","server_version","row"}, …]}` (формат `pull`; клиент применяет их как строки `pull`). `404 agent_not_found` для неизвестного `seed_key`.

## 8. Коды ошибок

HTTP (до начала потока и у остальных эндпоинтов):

| Статус | `code` | Когда |
|---|---|---|
| 402 | `limit_exceeded` | месячный лимит исчерпан |
| 403 | `sensitive_context_forbidden` | чувствительный контекст в облачном чате |
| 404 | `conversation_not_found`, `agent_not_found`, `model_not_found` | см. 5.2, 7 |
| 409 | `message_exists` | повторный `assistant_message_id` |
| 422 | `validation_error`, `unknown_tool` | форма запроса |
| 502 / 504 | `upstream_error` / `upstream_timeout` | только `GET /ai/models`, когда кэша нет |
| 503 | `ai_not_configured` | не задан `POLZA_API_KEY` |

События `error` потока (`code`, `retryable`):

| `code` | `retryable` | Причина |
|---|---|---|
| `upstream_timeout` | да | нет первого байта за `POLZA_FIRST_BYTE_TIMEOUT`, пауза в потоке дольше `POLZA_IDLE_TIMEOUT` или превышено `POLZA_TOTAL_TIMEOUT` |
| `upstream_error` | да | 5xx/сеть/обрыв потока, ответ не по протоколу; повторы уже были (только до первого байта) |
| `upstream_rate_limited` | да | 429 после повторов |
| `upstream_payment_required` | нет | 402 провайдера: у ключа нет баланса |
| `upstream_rejected` | нет | прочие 4xx провайдера (кроме 404 по модели); ключ и тело ответа клиенту не передаются |
| `model_not_found` | нет | провайдер ответил 404 на модель |
| `limit_exceeded` | нет | месячный лимит исчерпан посреди цикла |
| `tool_loop_limit` | нет | модель не закончила за `AI_MAX_TOOL_ITERATIONS` обращений |
| `persist_failed` | да | не удалось записать сообщение |
| `internal_error` | да | непредвиденный сбой сервера |

`message` — по-английски, без данных запроса, без тела ответа провайдера и без секретов.

## 9. Провайдер, переменные окружения, секреты

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `POLZA_BASE_URL` | `https://polza.ai/api/v1` | адрес OpenAI-совместимого API (в тестах — поддельный сервер) |
| `POLZA_API_KEY` | — | ключ; **только** серверное окружение; без него `ai_not_configured` |
| `POLZA_CONNECT_TIMEOUT` | 5 с | установка соединения |
| `POLZA_FIRST_BYTE_TIMEOUT` | 60 с | до первого события потока (повторы возможны только до него) |
| `POLZA_IDLE_TIMEOUT` | 60 с | пауза между событиями потока |
| `POLZA_TOTAL_TIMEOUT` | 600 с | весь ответ целиком |
| `POLZA_MAX_RETRIES` | 2 | повторы до первого байта: ошибки соединения, таймаут первого байта, 408/429/5xx (пауза `0,5 × 2ⁿ` с, `Retry-After` до 10 с) |
| `POLZA_MODELS_TTL_SECONDS` | 3600 | кэш каталога |
| `AI_MAX_TOOL_ITERATIONS` | 5 | шагов цикла инструментов |
| `AI_BILLING_TIMEZONE` | `Europe/Moscow` | граница месяца |
| `AI_SSE_PING_SECONDS` | 15 | `ping` в потоке |

Ключ хранится как `SecretStr`, уходит только в заголовок `Authorization` исходящего запроса. Его нет в: ответах (в том числе ошибках и потоке), логах (процессор structlog подменяет значение ключа, `Bearer …` и поля `authorization`/`api_key`/`token`/`password`/`secret` на `[redacted]` во всём событии, включая текст исключений), БД, исключениях. Тело ответа провайдера не передаётся клиенту и не пишется в логи (в логи — только статус и тип ошибки). Повторы и таймауты логируются без URL с параметрами.

## 10. Тесты бэкенда

Поддельный upstream (`backend/tests/ai/fake_upstream.py`) — настоящий HTTP-сервер на эфемерном порту с записанными в стиле OpenAI потоками: текст, вызовы инструментов (один, параллельные, с невалидными аргументами), 4xx/5xx, обрыв посреди потока, медленный первый байт. Проверяются: утечки ключа (ответы, поток, ошибки, логи, БД), отмена клиентом прерывает запрос к upstream, лимит блокирует до отправки, стоимость в копейках, ровно одна задача на одобрение (параллельные двойные одобрения), синхронизация сообщений и предложений на второе устройство, читающие инструменты скрывают удалённое.

## 11. Открытые вопросы

1. **Сырой формат polza.ai** (фаза 0, спайк): имена полей цен в `/models`, поле стоимости в `usage` стрима, `include_usage` в стриме, параметр фильтра по типу. Разбор устойчив к вариантам, но единицы (рубли за 1 млн токенов) надо подтвердить на живом ответе.
2. **Автогенерация заголовка чата** (дешёвой моделью после первого ответа) в Этап 3 бэкенда не входит: клиент может ставить заголовок из первых слов; вопрос — делать ли отдельный эндпоинт.
3. **Баланс polza.ai** (эндпоинт Balance v2) не реализован: показываем только свой учёт.
4. **Одновременные «одобрить» и «отклонить»** на двух устройствах могут оставить задачу при статусе `rejected` (раздел 2, п. 6).
