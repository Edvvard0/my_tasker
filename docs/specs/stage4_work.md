# Этап 4. Спецификация: Работа (проекты, оплаты, часы)

> Контракт для сервера и Flutter-клиента. Решения — `docs/briefs/stage-4.md` (при расхождении действует он). Эталонные расчёты — `backend/src/tasker/work/reference.py`, общие векторы — `shared-test-vectors/work/` (раздел 7).

## 0. Принципы

- Одна валюта — **RUB**. Деньги — целые **копейки** (`int`, 64 бит); `float`/`Decimal` нигде. Колонка валюты в v1 не заводится (см. раздел 9).
- **Копейки никогда не округляются**: суммы только складываются и вычитаются. Делений ровно **три**, и все — **с округлением вниз** (раздел 4.1).
- «Мне должны» — это неоплаченные остатки по проектам. **Рома — заказчик**, как и Елена: долей, партнёрского раздела денег и взаиморасчётов нет. Графика оплат (плана) нет.
- Время — UTC в хранилище; все «календарные» правила Работы (месяц платежа, период отчёта, день записи времени) считаются по **Москве** (раздел 4.8).
- Всё синхронизируется по правилам Этапа 1; конфликты — автоматически (поле за полем, LWW).

## 1. Таблицы

Служебные поля, `id` (UUIDv7, генерирует клиент) и мягкое удаление — как у всех синхронизируемых таблиц. Все новые колонки `projects`/`people` **необязательны**: строки Этапа 2 остаются валидными, а старые клиенты не ломаются (сервер молча отбрасывает неизвестные им колонки, id не меняются).

### 1.1 `projects` (расширение)

Были: `title`, `color`, `archived`. Добавлены:

| Колонка | Тип | Правила |
|---|---|---|
| `client_id` | uuid, null | заказчик → `people.id`. **Мягкая ссылка** (без FK и каскада, как `tasks.project_id`, Этап 2, 2.3) |
| `status` | enum, null | `lead` лид, `active` в работе, `paused` пауза, `completed` завершён, `cancelled` отменён. **`null` ≡ `active`** (проекты Этапа 2) |
| `pay_type` | enum, null | `fixed` фикс, `hourly` почасовой. `null` ≡ `fixed` |
| `base_amount` | int, null | копейки, 0…99 999 999 999 999. `null` ≡ 0 |
| `hourly_rate` | int, null | копейки за час, тот же диапазон |
| `start_date`, `deadline_date`, `completed_date` | date `YYYY-MM-DD`, null | реальные даты |
| `description` | text, null | ≤ 10 000 |
| `links` | json, null | список ≤ 20 объектов `{"url": "http(s)://…" (1–500), "title": ≤ 100 (необяз.)}`, ≤ 8 КБ |

Межполевые проверки (`validation_failed`): `archived = true` допустимо только при `status ∈ {completed, cancelled}` (при `status = null` проверка не срабатывает — это старые архивные проекты); `pay_type = hourly` требует `hourly_rate`; `status = completed` требует `completed_date`; `deadline_date` и `completed_date` не раньше `start_date`.

Ставка `hourly_rate` на расчёты не влияет — это справочная величина карточки; «сколько набежало по ставке» = `hourly_billable` (4.7).

### 1.2 `people` (расширение)

Добавлены `role` (enum, null: `client` заказчик, `other` другое; `null` ≡ `other`) и `contact` (text ≤ 500, null, свободный текст).

### 1.3 `change_requests` — доработки

| Колонка | Тип | Правила |
|---|---|---|
| `project_id` | uuid → `projects`, **неизменяема** | обяз.; родитель, каскад |
| `title` | text 1–300, не пустое | обяз. |
| `amount` | int ≥ 0 | обяз., копейки |
| `status` | enum | обяз.: `in_progress` в работе, `closed` закрыта, `cancelled` отменена |
| `closed_date` | date, null | `status = closed` требует дату (`validation_failed`); у остальных статусов дата не обязана быть пустой, но в расчётах значение имеет только у `closed` |
| `estimate_minutes` | int 0…600 000, null | оценка в **минутах** (в часы — на клиенте) |
| `note` | text ≤ 5 000, null | |

### 1.4 `payments` — факт поступления

| Колонка | Тип | Правила |
|---|---|---|
| `paid_at` | datetime | обяз.; не раньше 2015-01-01 (4.8). Месяц и день — по Москве |
| `amount` | int ≥ **1** | обяз.; нулевой платёж смысла не имеет |
| `payer_id` | uuid, null | «от кого» → `people.id`, **мягкая ссылка** |
| `comment` | text ≤ 2 000, null | |

Платёж сам к проекту не привязан — деньги к проектам относят распределения.

### 1.5 `payment_allocations` — распределение платежа

| Колонка | Тип | Правила |
|---|---|---|
| `payment_id` | uuid → `payments`, **неизменяема** | обяз.; каскад |
| `project_id` | uuid → `projects`, **неизменяема** | обяз.; каскад |
| `change_request_id` | uuid, null, **неизменяема** | доработка, которую оплачивает распределение; **мягкая ссылка**. `null` — оплата базовой суммы |
| `amount` | int ≥ **1** | обяз. |

Изменить можно только `amount`; «перенести» распределение = удалить и создать новое. Один платёж — несколько распределений (на доработки и проекты), одна доработка — несколько распределений (оплата частями).

### 1.6 `time_entries` — учёт времени

| Колонка | Тип | Правила |
|---|---|---|
| `project_id` | uuid → `projects` | обяз.; каскад (запись можно переназначить на другой проект) |
| `change_request_id` | uuid, null | мягкая ссылка |
| `task_id` | uuid, null | мягкая ссылка на `tasks` |
| `started_at` | datetime | обяз.; не раньше 2015-01-01 |
| `ended_at` | datetime, null | `null` — таймер идёт (только `source = timer`) |
| `billable` | bool | обяз.; оплачиваемое |
| `note` | text ≤ 2 000, null | |
| `source` | enum | обяз.: `timer`, `manual` |

Проверки (`validation_failed`): `ended_at` не раньше `started_at`; запись короче 14 суток (забытый таймер не должен давать абсурдные часы); `source = manual` требует `ended_at`. Что идущих таймеров на устройстве не больше одного и что после синхронизации их может оказаться два — логика клиента (сервер хранит оба).

## 2. Связи и каскады

```
projects ─┬─ change_requests
          ├─ payment_allocations ── payments
          └─ time_entries            (people, tasks — только мягкие ссылки)
```

Каскады делает сервер (Этап 1, 3.5), клиент шлёт одну операцию `delete` родителя:

| Удаляется | В корзину каскадом |
|---|---|
| `projects` | `change_requests`, `payment_allocations`, `time_entries` проекта |
| `payments` | `payment_allocations` платежа |
| `change_requests`, `people`, `tasks` | **ничего** |

Обоснование:
- **Проект → доработки** (по заданию): доработка без проекта не существует.
- **Проект → распределения и время.** Распределение и запись времени без проекта не показать нигде, а в итоги они не должны попадать «в воздух». Восстановление проекта возвращает всё, что ушло вместе с ним. Сами **платежи остаются** (платёж может делиться между проектами): его неразнесённая часть видна как «не распределено».
- **Платёж → распределения** (по заданию).
- **Доработка → ничего.** Ссылки `payment_allocations.change_request_id` и `time_entries.change_request_id` мягкие: если доработку удалили, полученные деньги не исчезают из «получено» проекта (они считаются оплатой базовой суммы, 4.3), а часы остаются в проекте. Деньги не должны пропадать из итогов от случайного удаления строки-ярлыка.
- **Заказчик (`people`) → ничего:** удаление человека не трогает проекты и платежи; клиент показывает «заказчик не указан», ссылку не чистит (как в Этапе 2, 2.3).
- Локальная видимость на клиенте — как в Этапе 1: строка видима, если `deleted_at = null` и все её родители видимы. Мягкие ссылки видимость не определяют.

Порядок регистрации в реестре: `projects`, `people` (Этап 2) → `change_requests`, `payments`, `payment_allocations`, `time_entries`.

## 3. Проверки сервера

### 3.1 Коды

Как в Этапе 2 (раздел 9): тип, длина, формат (`1.10.2026` — не дата), перечисление, `null` в обязательной колонке, сумма вне диапазона — `invalid_field`; межполевые правила 1.1–1.6 и несуществующие даты (`2026-02-30`, `2026-13-40`) — `validation_failed`; изменение неизменяемых колонок — `immutable_field`; родитель не существует — `parent_not_found`; создание без обязательных колонок — `missing_fields`; `id` не UUIDv7 — `invalid_id`.

### 3.2 Суммы

Суммы — целые числа, не булевы и не дробные: `1500.5`, `"100"`, `true` → `invalid_field`. Допустимо `0 ≤ base_amount, hourly_rate, change_requests.amount ≤ 99 999 999 999 999` и `1 ≤ payments.amount, payment_allocations.amount ≤ 99 999 999 999 999`. Отрицательные суммы запрещены везде: «возвраты» в v1 не поддержаны.

### 3.3 Чего сервер НЕ проверяет (и почему)

Правила, где участвует больше одной строки, при офлайн-синхронизации проверить построчно нельзя: два устройства законно создают по распределению к одному платежу, и каждое по отдельности корректно; отказ одной из операций потерял бы данные. Поэтому:

- «**сумма распределений платежа ≤ суммы платежа**» — проверяет клиент при вводе; сервер не отклоняет. Если после слияния сумма превысила платёж, расчёты считают распределения **как записано**, а нарушение видно в `integrity_problems` (4.9) и в предупреждениях клиента (`over_allocated`);
- «доработка принадлежит проекту распределения» — клиент гарантирует при вводе; нарушение — `change_request_mismatch` в `integrity_problems`;
- существование `client_id`, `payer_id`, `change_request_id`, `task_id` (мягкие ссылки).

## 4. Правила расчётов

Все функции — чистые, на «JSON-строках» таблиц (имена колонок как выше; id — строки; моменты — `YYYY-MM-DDTHH:MM:SSZ`, даты — `YYYY-MM-DD`). Клиент и сервер обязаны давать **побайтно одинаковый** результат на векторах. Недостающие необязательные значения читаются по умолчанию из 1.1 (`status = null` ≡ `active`, `base_amount = null` ≡ 0).

### 4.1 Округление (единственное правило)

**Округление вниз** (floor, к нулю — все величины неотрицательны) для всех трёх делений; целочисленное деление `//` (Dart: `~/` на неотрицательных). Выбрано вместо «банковского»: результат проверяется в уме и нигде не завышает заработок и долю оплаты; «банковское» дало бы 100 % у проекта, оплаченного на 99,996 %. Промежуточное произведение ≤ 10¹⁴ × 10⁴ — укладывается в 64 бита.

| Величина | Формула |
|---|---|
| доля оплаты (в сотых долях процента, `paid_bp`) | `received × 10 000 // total`; `0`, если `total ≤ 0`; при переплате > 10 000 |
| доход в час (копеек за час) | `amount × 3 600 // seconds`; **`null`**, если `seconds = 0` |
| стоимость времени по ставке | `rate × seconds // 3 600` |

Проценты для показа: `paid_bp / 100` с одним знаком после запятой, **без** дополнительного округления вверх (форматирование — усечением). Примеры: 1 из 3 → `3333` → «33,3 %»; 99 999 из 100 000 → `9999` → «99,9 %», а не «100 %»; 100 000 копеек за 3 ч → `100 000 × 3 600 // 10 800 = 33 333` коп. = 333,33 ₽/ч.

### 4.2 Сумма проекта

`total = base_amount + Σ amount доработок проекта со статусом ≠ cancelled` (в работе и закрытые — обе). Для почасового проекта формула та же.

### 4.3 Получено, остаток, оплата

- `received = Σ amount` **всех** распределений с `project_id` проекта (в том числе к отменённым доработкам и с оборванной ссылкой на доработку — деньги реально получены);
- `remaining = total − received` — **со знаком**: отрицательный остаток = переплата; `overpaid = max(0, received − total)`;
- `paid_bp` — 4.1;
- `base_received` = сумма распределений проекта, у которых `change_request_id` пуст **или** не указывает на живую доработку этого проекта; `base_remaining = base_amount − base_received` (со знаком);
- по каждой доработке: `received` = сумма распределений с её `change_request_id`; `remaining = amount − received` (со знаком), у **отменённой** `remaining = 0`.

Пример. Проект «Сайт Ромы»: база 100 000 ₽; доработки: «Корзина» 30 000 ₽ (закрыта), «Фильтры» 20 000 ₽ (в работе), «Чат» 15 000 ₽ (отменена). Платёж 70 000 ₽ распределён: 60 000 ₽ на базу, 10 000 ₽ на «Корзину»; второй платёж 20 000 ₽ — на «Корзину». Тогда `total = 100 000 + 30 000 + 20 000 = 150 000 ₽`; `received = 90 000 ₽`; `remaining = 60 000 ₽`; `paid_bp = 6000` («60 %»); `base_received = 60 000 ₽`, `base_remaining = 40 000 ₽`; «Корзина»: получено 30 000, остаток 0; «Фильтры»: остаток 20 000; «Чат»: остаток 0.

### 4.4 Дебиторка по заказчикам («мне должны»)

По каждому проекту со статусом **`active`, `paused` или `completed`** (в том числе архивные; `lead` и `cancelled` ничего не должны; `null` ≡ `active`): `debt = max(0, total − received)`. Переплата одного проекта **не гасит** долг другого. Проекты с `debt > 0` группируются по `client_id` (у проектов без заказчика `client_id = null`):

- группа: `{client_id, remaining = Σ debt, projects: [{id, remaining}]}`, проекты внутри — по `remaining` убыв., затем по `id`;
- группы — по `remaining` убыв., затем по `client_id` по возрастанию, **`null` последним**;
- заказчики без долга в список не попадают; `total` = сумма всех групп («мне должны всего»).

Пример: «Рома» — проекты A (остаток 70 000 ₽) и B (40 000 ₽), «Елена» — C (200 000 ₽), проект D отменён или лид (остаток 50 000 ₽ не считается). Результат: Елена 200 000 ₽; Рома 110 000 ₽ (A 70 000, B 40 000); всего 310 000 ₽.

### 4.5 Доход в час

Параметры: `period = {"from": date|null, "to": date|null}` (включительно, даты по Москве; `null` вместо периода — всё время; `null` граница — не ограничено) и необязательный проект.

- **Часы** проекта: сумма `entry_seconds` по записям `billable = true` с **завершённым** интервалом, у которых московская дата **начала** в периоде. Идущий таймер (`ended_at = null`) и неоплачиваемые записи не входят. `entry_seconds` = разность моментов, предварительно усечённых до целых секунд, в целых секундах (запись целиком относится к дню начала, через полночь не режется).
- **По факту** (`received`): сумма распределений проекта, у которых московская дата **платежа** в периоде (распределение без платежа в данных игнорируется).
- **По начисленному** (`accrued`): сумма доработок со статусом `closed`, у которых `closed_date` в периоде, **плюс** `base_amount` проекта, если `status = completed` и `completed_date` в периоде. Незакрытые и отменённые доработки и база незавершённого проекта не входят.
- `per_hour_fact = per_hour(received, seconds)`, `per_hour_accrued = per_hour(accrued, seconds)` — 4.1; **`null` при нуле часов**.
- Общий итог по нескольким проектам = **итоги, делённые друг на друга** (`Σ amount // Σ seconds`), а не среднее значений проектов.

Пример: за октябрь проект принёс 100 000 коп. (платёж 5 октября), отработано 3 ч 00 мин → `per_hour_fact = 33 333` коп.; по начисленному: закрытая 20 октября доработка 90 000 ₽ → `9 000 000 × 3 600 // 10 800 = 3 000 000` коп. = 30 000 ₽/ч.

### 4.6 Помесячная разбивка полученного (колонки Excel)

`monthly_received(payments, allocations, project_id?)` → список `{month: "YYYY-MM", received, unallocated}` по возрастанию месяца. Месяц — **московский** месяц `paid_at`. `received` — сумма распределений платежей месяца (с фильтром проекта — только этого проекта). `unallocated = Σ amount платежей месяца − Σ всех их распределений` (может быть < 0 при нарушении 3.3); при фильтре проекта — `null`. Месяц без распределений и без неразнесённых денег в список не попадает; месяц с платежом без распределений — попадает (`received = 0`).

Пример: платёж 30 сентября 20:59:59Z — это 30 сентября по Москве (сентябрь), в 21:00:00Z — уже 1 октября (октябрь).

### 4.7 Прочее

`hourly_billable(rate, seconds)` (4.1) — «набежало по ставке» для карточки почасового проекта; в итоги не входит.

### 4.8 Время: Москва

Для моментов с 2015-01-01 `Europe/Moscow` = **UTC+3 без перехода на летнее время**, поэтому «московская дата» = дата момента, сдвинутого на +3 часа; библиотека часовых поясов не нужна (на сервере и в Dart правило одно). Раньше 2015 валидаторы моменты Работы не принимают (`paid_at`, `started_at`).

### 4.9 Целостность

`integrity_problems(change_requests, payments, allocations)` — предупреждения о том, чего сервер не отклоняет (3.3): `{"code": "over_allocated", "id": <payment>, "excess": N}` и `{"code": "change_request_mismatch", "id": <allocation>, "excess": null}`; порядок — по `code`, затем `id`.

## 5. Трекер времени (серверная часть)

Хранится только строка `time_entries`; таймер = запись с `ended_at = null`, старт переживает перезапуск. Остановка = правка `ended_at`. Два идущих после синхронизации — предупреждение на клиенте (раздел 1.6). Платформенная часть (уведомление, трей) — клиент.

## 6. Инструменты ИИ (читающие, агент «Работа»)

Регистрация — `backend/src/tasker/work/tools.py` (реестр Этапа 3, 6.1); профиль `work` получает их автоматически (список инструментов предустановленных профилей выводится из кода). Читают только живые строки; результат — JSON ≤ 20 000 символов; суммы всегда парой `<имя>_kopecks` (int) и `<имя>_text` (`format_amount`, «1 234,56 ₽»).

- **`get_projects`**: `status` (список из 5), `include_archived` (по умолчанию `false`), `query` (подстрока названия), `project_id` (один проект с доработками), `limit` (1…100, по умолчанию 30). Ответ `{"count","truncated","projects":[{"id","title","status","archived","client_id","client","pay_type","deadline_date","total_*","received_*","remaining_*","paid_percent", ("hourly_rate_*")}]}`; сортировка — по неотрицательному остатку убыв., затем название. С `project_id` добавляются `base_received_*`, `base_remaining_*` и `change_requests: [{"id","title","status","amount_*","received_*","remaining_*"}]`.
- **`get_receivables`**: `client` (подстрока имени, необяз.). Ответ `{"currency":"RUB","total_*","count","truncated","clients":[{"client_id","client","remaining_*","projects":[{"id","title","remaining_*"}]}]}`; `total_*` — общий, **без учёта фильтра**.
- **`get_work_hours`**: `from_date`, `to_date` (обяз., `YYYY-MM-DD`, включительно, не более 366 дней), `project` (id или подстрока названия). Ответ `{"period","billable_seconds","billable_hours_text","received_*","accrued_*","per_hour_fact_*","per_hour_accrued_*" (null при нуле часов),"running_timers","count","truncated","projects":[…то же по проекту + "id","title"]}`; в `projects` — только проекты с часами или деньгами за период.

Неверные аргументы — обычная ошибка инструмента (`ToolArgumentError`, Этап 3).

## 7. Тестовые векторы (`shared-test-vectors/work/`)

Формат — как в `shared-test-vectors/README.md`; исходные входы — `backend/tests/work_vectors_gen.py`, ожидаемое — эталон `reference.py`; пересборка `cd backend && uv run python -m tests.work_vectors_gen`. Описание файлов — в README векторов (домен `work`). Dart обязан пройти все случаи; ≥ 60 случаев (сейчас 90).

## 8. Тесты бэкенда

Векторы на эталоне; валидация через настоящий `POST /sync/push`; круг синхронизации, каскады и восстановление через настоящий движок; инструменты ИИ на посеянных данных; миграция туда-обратно и тест дрейфа схемы.

## 9. Известные ограничения

1. **Валюта.** Колонки валюты нет: v1 — только RUB. Мультивалютность потребует колонки `currency` и правил для сумм разных валют.
2. **Сумма распределений ≤ платежу** не может быть отклонена построчно (3.3); контроль — на клиенте и через `integrity_problems`. Жёсткий запрет потребовал бы правки движка Этапа 1.
3. **Ставка почасового проекта** не определяет сумму проекта: сумму вводит пользователь (база и доработки). «Часы × ставка» — только справка `hourly_billable`.
4. **Лиды** в «мне должны» не входят (решение оркестратора): до перехода в «в работе» долга нет.
5. **Инструменты ИИ предустановленных профилей** берутся из кода на каждый запрос (Этап 3, 7), сброс агента для них не нужен.
