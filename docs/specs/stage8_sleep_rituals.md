# Этап 8. Спецификация: Сон и ежедневные ритуалы

> Контракт для сервера и Flutter-клиента. Решения — `docs/briefs/stage-8.md` (при расхождении действует выжимка). Эталон — `backend/src/tasker/sleep/reference.py`, общие векторы — `shared-test-vectors/sleep/` (раздел 8). Задачи — `docs/specs/stage2_calendar_tasks.md` (4.1).

## 0. Принципы

- Всё, что хранится, синхронизируется по правилам Этапа 1: поля сливаются по одному (LWW), мягкое удаление, корзина 30 дней, служебные поля. Исключение из «UUIDv7 от клиента» — **естественный ключ «дата»**: `id = uuid5(ns(таблица), "<дата>")` (`ns(t) = uuid5(NAMESPACE_URL, "urn:my-tasker:" + t)`, как в Этапе 2, 2.2). Иначе `invalid_id`. Два устройства, записавшие один день офлайн, получают **одну** строку, поля сливаются.
- **Пропущенный день — строки нет.** Ни нулевых записей, ни «заглушек».
- Даты — `YYYY-MM-DD`, моменты — UTC (`YYYY-MM-DDTHH:MM:SSZ` в расчётах, любой ISO 8601 со смещением в колонках — сервер нормализует), пояса — имена IANA.
- Расчёты — чистые функции на «JSON-строках» таблиц, **целочисленные** (раздел 4). Клиент и сервер обязаны дать **побайтно одинаковый** результат на векторах.
- Деньги в модуле не участвуют. Здоровье (Health Connect) не входит (выжимка).
- **Колонка `date` неизменяема.** Чтобы «перенести запись на другой день», клиент удаляет строку и создаёт новую (другой `id`). Правка времени, меняющая локальную дату пробуждения, — то же самое.

## 1. Таблицы

Порядок регистрации: `sleep_entries`, `daily_plans`, `evening_checkins`. Родителей нет, каскадов нет. Необязательные колонки при создании можно не посылать (читаются как `null`).

### 1.1 `sleep_entries` — сон

| Колонка | Тип | Правила |
|---|---|---|
| `date` | date, **неизменяема** | обяз.; «дата сна» = локальная дата `wake_at` в `wake_tz` (иначе `validation_failed`) |
| `bed_at` | datetime | обяз.; когда лёг (UTC-момент) |
| `wake_at` | datetime | обяз.; когда встал; строго позже `bed_at`, не позже чем через 24 часа; ни `bed_at`, ни `wake_at` не позже **часов сервера + 1 сутки** (ночь записывают после того, как она прошла; сутки — запас на расхождение часов устройства; иначе `validation_failed`) |
| `bed_tz` | text, null | зона, в которой лёг; `null` — та же, что `wake_tz` |
| `wake_tz` | text 1–64 | обяз.; зона, где проснулся; имя IANA (иначе `validation_failed`) |
| `source` | enum | обяз.: `manual` — ввод вручную; `morning_notification` — быстрый ввод из утреннего уведомления |
| `quality` | int, null | 1…5 |
| `note` | text ≤ 2 000, null | |

`id = uuid5(ns("sleep_entries"), date)`. Одна строка на дату: ночной сон в два приёма клиент записывает одной строкой (лёг — встал окончательно); дневной сон модуль не хранит.

**Длительность не хранится** — она вычисляется (раздел 3.1): так слияние полей двух устройств не может дать расхождение «время есть, длительность другая».

### 1.2 `daily_plans` — утренний план

| Колонка | Тип | Правила |
|---|---|---|
| `date` | date, **неизменяема** | обяз.; день, на который план |
| `task_ids` | json | обяз.; список ≤ 10 id задач — «главные дела дня» (канонический строчный uuid, без повторов; пустой список — можно) |
| `main_task_id` | uuid, null | выбранное «главное»; **не обязано** входить в `task_ids` (слияние полей двух устройств не должно делать строку невалидной); клиент при выборе добавляет его в список |
| `note` | text ≤ 2 000, null | |

`id = uuid5(ns("daily_plans"), date)`. Ссылки на задачи **мягкие** (как `tasks.project_id`, Этап 2, 2.3): сервер не проверяет, что задача есть; клиент показывает отсутствующую задачу как «задача удалена» и не чистит ссылку. Сон, задачи на сегодня, пары и события экран плана **вычисляет на клиенте** из уже синхронизированных данных — они в строку не копируются. Наличие строки = «утренний план сделан» (для серии).

### 1.3 `evening_checkins` — вечерний чек-ин

| Колонка | Тип | Правила |
|---|---|---|
| `date` | date, **неизменяема** | обяз.; день, который подводят |
| `rating` | int, null | оценка дня 1…5 |
| `done_task_ids` | json | обяз.; ≤ 50 id задач, отмеченных как сделанные (канонический uuid, без повторов) |
| `carry_over` | json | обяз.; ≤ 50 решений о переносе (формат ниже) |
| `note` | text ≤ 2 000, null | |

Решение о переносе: `{"task_id": uuid, "to": "tomorrow"}` или `{"task_id": uuid, "to": "date", "date": "YYYY-MM-DD"}`; других ключей нет; `date` — только при `to = date` и реальная; одна задача — одно решение (иначе `validation_failed`).

`id = uuid5(ns("evening_checkins"), date)`. Наличие строки = «чек-ин сделан». **Решения в `carry_over` — журнал намерения**, а не сам перенос: даты задач меняет клиент (раздел 6), сервер задач не трогает.

## 2. Валидация

Колонки проверяются по типам (`invalid_field`: неверный тип, диапазон, длина, перечисление), межполевые правила — `validation_failed`, чужой id — `invalid_id`, правка неизменяемой `date` — `immutable_field`. Сводка межполевых правил:

- `sleep_entries`: `date` — реальная дата; `wake_at > bed_at`; `wake_at − bed_at ≤ 24 ч`; `max(bed_at, wake_at) ≤ now_сервера + 1 сутки` (проверка зависит от часов сервера, поэтому в общих векторах её нет); обе зоны известны; `date == локальная дата wake_at в wake_tz`.
- `daily_plans`: `date` — реальная; `task_ids` — список ≤ 10 канонических uuid без повторов.
- `evening_checkins`: `date` — реальная; `done_task_ids` — как выше (≤ 50); `carry_over` — раздел 1.3.

## 3. Расчёты сна

Все функции в `reference.py`; моменты в них — строки `YYYY-MM-DDTHH:MM:SSZ`.

### 3.1 Длительность и дата

`duration_minutes(bed_at, wake_at)`: `floor((wake_at − bed_at) / 60 с)`; ошибка (`null`), если разность ≤ 0, > 24 ч или момент не разбирается. **Часовые пояса в длительности не участвуют**: это разность моментов, поэтому ночь через полночь, перелёт с другим поясом и ночь перевода часов считаются верно сами (ночь 29.03.2026 в Берлине с 00:30 до 07:30 по настенным часам длится 6 ч, не 7).

`sleep_date(wake_at, wake_tz)` — локальная дата пробуждения. `local_clock(момент, зона)` — `HH:MM` на настенных часах зоны (секунды отбрасываются). `entry_view(строка)` → `{date, minutes, bed_local, wake_local}` (отбой — в `bed_tz`, по умолчанию `wake_tz`; подъём — в `wake_tz`) или ошибка для невалидной строки.

### 3.2 Средний сон за 7 и 30 дней

`average_sleep(entries, through, days)`: окно — `days` дат, заканчивающееся датой `through` включительно. Берутся строки с `date` в окне и валидной длительностью. `days_with_data` — их число; `total_minutes` — сумма; `average_minutes = floor(total_minutes / days_with_data)`, а при `days_with_data = 0` — `null`. **Пропущенные дни не считаются нулями** — они просто выпадают из знаменателя. Клиент показывает «мало данных», если `days_with_data` мал (пороги — решение интерфейса).

### 3.3 Связь сна с выполненными задачами за неделю

`sleep_task_link(entries, tasks, through)` — окно **7 дней** до `through`. Это сравнение двух долей, **не статистика и не причинность**; интерфейс обязан так и формулировать («в дни после короткого сна вы закрывали X % задач, после нормального — Y %»).

1. Ночь **короткая**, если `minutes < 360` (6 ч), иначе **нормальная** (`SHORT_SLEEP_MINUTES = 360`).
2. День задачи: `due_date`, а для задачи с `due_at` — локальная дата `due_at` в `due_tz`; без даты задача не участвует. Не участвуют также повторяющиеся (`rrule`) и отменённые (`cancelled`) задачи, и задачи вне окна.
3. Для каждой даты окна, у которой **есть запись сна и есть задачи**, считаются `tasks` (всего) и `done` (`status = done`); дата без записи сна даёт `days_without_sleep += 1` (если в ней были задачи); дата без задач не участвует.
4. По группам `short` и `normal` суммируются дни, задачи и сделанные (**суммарная** доля, а не среднее долей: день с десятью задачами весит больше дня с одной).
5. `share_bp = floor(10 000 × done / tasks)` (базисные пункты, 10 000 = 100 %), `null` при `tasks = 0`. `difference_bp = normal.share_bp − short.share_bp` (со знаком; `null`, если одной из долей нет). `enough_data = true`, если в **каждой** группе не менее 2 дней с задачами (`MIN_GROUP_DAYS = 2`); иначе интерфейс пишет «мало данных».

Ответ: `{from, to, threshold_minutes, short: {days, tasks, done, share_bp}, normal: {…}, difference_bp, days_without_sleep, enough_data}`.

## 4. Округление

Всё целочисленное: минуты — вниз по секундам, среднее — вниз, доли — вниз в базисных пунктах. Никаких `float`/`double` в реализации и в векторах; деления на ноль нет (результат `null`).

## 5. Серии ритуалов

`streak(dates, through)` → `{current, best, last}`: из `dates` берутся реальные даты не позднее `through` (повторы считаются один раз, мусор игнорируется). `current` — число подряд идущих дней, заканчивающихся **сегодня** (`through`), а если сегодня ещё не отмечено — **вчера** (серия «жива» весь день и обрывается, лишь когда пропущен вчерашний день). `best` — самая длинная серия до `through`. `last` — последняя дата не позднее `through` или `null`.

`ritual_streaks(morning, evening, through)` → `{morning, evening, both}`: серии дней с утренним планом, с вечерним чек-ином и с обоими сразу (пересечение дат). Даты — `date` живых (не удалённых) строк `daily_plans` и `evening_checkins`.

## 6. Перенос задач из чек-ина

`plan_carry_over(checkin_date, decisions, tasks)` → по одному результату на решение, **в порядке решений**. Функция только считает: сервер ничего не пишет в `tasks`; клиент применяет результат обычными правками задач (поле за полем, в одной операции на задачу) и пишет решения в `carry_over`.

Цель: `tomorrow` — день после `checkin_date`; `date` — заданная дата, **строго позже** `checkin_date`. Результат:

| `action` | Поля | Когда |
|---|---|---|
| `set_due_date` | `due_date`, `status` | у задачи нет времени (`due_date` или совсем без даты) |
| `set_due_at` | `due_at` (UTC), `due_tz`, `status` | у задачи есть `due_at`: **то же настенное время** в её поясе `due_tz` на новую дату |
| `skip` | `reason` | иначе |

`status`: `"todo"`, если задача была `inbox` (задача с датой — «к выполнению»), иначе `null` («не менять»). Причины пропуска: `not_found` (нет такой задачи в переданных), `closed` (`done`/`cancelled`), `recurring` (задача с `rrule`: двигать экземпляр — отдельная правка, не из чек-ина), `duplicate` (задача уже встречалась в решениях), `not_in_future` (дата не позже `checkin_date` или нереальная), `unchanged` (задача уже на этой локальной дате).

**Летнее время** (`set_due_at`): настенное время, которого нет (переход вперёд), считается по смещению *до* перехода — момент сдвигается вперёд на длину пропуска (02:30 → 03:30); неоднозначное время (переход назад) — это **первое** вхождение (PEP 495 `fold = 0`, `Temporal` «compatible»). Клиент на Dart обязан дать те же моменты (векторы `carry_over.json`, случаи `…dst_gap…` и `…dst_overlap…`).

Что не делает функция: не меняет напоминания и длительность (`reminders`, `duration_minutes` остаются), не трогает подзадачи.

## 7. Инструменты ИИ (читающие, агент «Сон»)

Регистрация — `backend/src/tasker/sleep/tools.py` (реестр Этапа 3, 6.1); встроенный профиль `sleep` получает их автоматически (`SLEEP_TOOLS`); системный промт профиля дополнен упоминанием инструментов (изменение Этапа 3; у уже созданных профилей — после «сбросить промт»). Читают только живые строки; результат — JSON ≤ 20 000 символов: при превышении отбрасываются **самые старые** записи (`truncated = true`).

- **`get_sleep_stats`**: `through_date` (по умолчанию сегодня в поясе пользователя), `days` (1…60, по умолчанию 14). Ответ: `{through, count, truncated, average_7_days, average_30_days, tasks_vs_sleep_last_7_days, entries: [{date, bed, wake, minutes, quality, note}]}` — записи по возрастанию даты (`bed`/`wake` — настенное время `HH:MM`, заметка ≤ 300 символов); средние и связь считаются раздел 3.2–3.3.
- **`get_daily_rituals`**: `through_date`, `days` (1…30, по умолчанию 7). Ответ: `{through, count, truncated, streaks, plans: [{date, main_task_id, task_ids, note}], checkins: [{date, rating, done_tasks, carried_tasks, note}]}`; серии считаются по **всем** живым строкам, списки — по окну.

## 10. Известные ограничения и открытые вопросы

1. **Зона пользователя при записи.** Сон хранит зону пробуждения; если пользователь не указал её, клиент берёт зону устройства. Смена зоны в настройках не переписывает старые записи.
2. **Одна ночь на дату.** Сон «в два приёма» (проснулся в 4 и снова лёг) записывается одной строкой; детальные стадии, пробуждения и дневной сон не хранятся.
3. **Здоровье.** Импорт из Health Connect/Samsung Health (`01` §6.7) не входит: браслета нет (`04` §1.2, №10). Появится — новый источник (`source`), необязательные колонки и миграция.
4. **Порог «короткого» сна** (6 ч) — константа контракта; настройка пользователя — возможное расширение (`user_settings`).
5. **Связь сна и задач** считается по задачам со сроком в этот день; задачи без срока и повторяющиеся не участвуют. Это сознательная простота: «без статистических претензий».
6. **Перенос повторяющихся задач** из чек-ина не поддерживается (`recurring`): двигать экземпляр — отдельная правка календаря.
7. **Кто применяет перенос.** Если клиент не применил план (закрыл приложение), `carry_over` остаётся записанным намерением; повторное применение безопасно: `unchanged`/`not_in_future` отсекут уже сделанное.
