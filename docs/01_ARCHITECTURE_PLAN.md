## 1. Обзор и принципы

**Что строим.** Персональная система трекинга жизни для одного человека:
- Android-клиент (Samsung Galaxy A55) и Windows-клиент на одной кодовой базе;
- единый бэкенд на VPS пользователя;
- агенты мониторинга и бэкапов на серверах пользователя.

Модули: Календарь и задачи (главный экран), Работа (самый важный по смыслу) с подразделом «Серверы», Финансы, Учёба, Сон, Чат с ИИ-агентом.

**Принципы:**

1. **Offline-first.** Клиент работает со своей локальной БД: все экраны читают и пишут локально, а синхронизация идёт фоном. Сеть нужна только для:
   - онлайн-моделей ИИ;
   - живых данных мониторинга серверов;
   - банковских данных, которые приходят с сервера (ZenMoney);
   - Telegram.
2. **Один пользователь, несколько устройств.** Нет мультиарендности, ролей и шаринга. Зато есть реестр устройств, и каждое устройство можно отозвать. Одновременное редактирование исключено по договорённости, но синхронизация всё равно обязана корректно разбирать редкие конфликты: без потерь и с журналом.
3. **Модульность.** Каждый модуль — отдельная фича-папка на клиенте и отдельный роутер или сервис на бэкенде, со своими таблицами. Модули связаны только через явные ссылки: идентификатор проекта, контрагента, задачи. Так модули можно делать и выпускать поэтапно.
4. **Сервер — источник истины для синхронизации, клиент — источник истины для UX.** Любое изменение сначала применяется локально и попадает в outbox. Потом оно уходит на сервер, а оттуда на другие устройства.
5. **Секреты только на сервере.** Ключ polza.ai, токен Telegram, токен ZenMoney и ключи S3 никогда не попадают на клиентские устройства.
6. **Простота эксплуатации.** Всё разворачивается одним docker compose на VPS. Нет Kubernetes, Redis, Kafka и Mongo. PostgreSQL служит и БД, и очередью, и хранилищем временных рядов мониторинга.
7. **Честные деньги.** Суммы хранятся как целые числа в копейках плюс код валюты. Все производные показатели (остаток по проекту, доля оплаты, «сколько не хватает до цели», доход в час) вычисляются, а не вводятся вручную. Исключение — явные корректировки.
8. **Дизайн.** Тёмная тема, почти чёрный фон, неоново-зелёный акцент, моноширинные цифры для денег, времени и метрик. Скруглённые карточки из ref2, минималистичная календарная сетка из ref1, статус-пилюли и мини-графики из ref3 «Пульс».

**Компоненты и их ответственность:**

- **Клиент (Flutter)**:
  - UI всех модулей;
  - локальная зашифрованная БД;
  - движок синхронизации (outbox, push, pull);
  - локальные уведомления и напоминания;
  - конструктор контекста ИИ;
  - исполнение инструментов ИИ на локальных данных;
  - локальная LLM (Android);
  - слушатель банковских уведомлений (Android);
  - Health Connect (Android);
  - трей и автозапуск (Windows).
- **api**:
  - авторизация и реестр устройств;
  - эндпоинты синхронизации;
  - прокси к polza.ai со стримингом;
  - REST для модуля «Серверы» (живые данные, в синхронизацию не входят);
  - канал событий SSE: сигнал «есть изменения», обновления дашборда;
  - приём соединений агентов;
  - webhook Telegram-бота;
  - импорт файлов (Excel, CSV, OFX).
- **worker**: всё периодическое. Проверки мониторинга, открытие и закрытие инцидентов, антиспам и отправка Telegram, опрос ZenMoney, агрегация аптайма, ежедневный дайджест, очистка tombstone'ов и сырых результатов проверок, бэкап собственной БД, самопроверка.
- **Агент**: живёт на каждом наблюдаемом сервере. Держит одно исходящее WSS-соединение с api. Отправляет heartbeat, состояние контейнеров и метрики хоста. Выполняет строго типизированные команды: «сделать бэкап задания X», «перепроверить контейнеры». Произвольные команды не принимает.

**Потоки данных:**

1. **Локальная правка.** Экран пишет в локальную БД в одной транзакции с записью в outbox. Через 2–5 секунд (debounce) или при появлении сети изменения уходят на сервер (push), затем приходят чужие изменения (pull). На другом устройстве открыт SSE-канал: сервер шлёт сигнал «есть изменения», и оно сразу делает pull.
2. **Чат онлайн.** Клиент собирает контекст локально и отправляет запрос в api. Api проксирует его в polza.ai со стримингом и ретранслирует дельты клиенту через SSE. По завершении api сохраняет ответ как синхронизируемую запись.
3. **Мониторинг.** Worker проверяет сервисы снаружи (с VPS), агенты присылают состояние изнутри. Worker пишет результаты, открывает и закрывает инциденты и шлёт алерты в Telegram. Клиенты читают дашборд через REST и получают живые обновления через SSE.
4. **Бэкапы.** В назначенное время worker через WSS отдаёт агенту команду. Агент делает дамп, сжимает, шифрует и загружает в S3 и в Telegram, затем сообщает результат с размером, хешем и file_id. Если отчёт не пришёл в срок, срабатывает dead-man's switch и уходит алерт.
5. **Финансы.** Worker раз в 15–30 минут забирает изменения из ZenMoney и превращает их в транзакции и балансы, которые уходят на клиенты обычной синхронизацией. Телефон параллельно ловит push-уведомления банков и создаёт черновики транзакций, которые потом сверяются с данными ZenMoney.

**Структура репозитория (монорепо):**
- `app/` — Flutter-клиент, фича-модули;
- `backend/` — api и worker, общий пакет домена;
- `agent/` — Go-агент;
- `deploy/` — compose-файлы, примеры env без значений, скрипты установки агента;
- `docs/`;
- `shared-test-vectors/` — общие наборы тестовых данных для Dart и Python: развёртка RRULE, формулы целей и остатков, парсинг уведомлений.

## 4. Синхронизация и офлайн

### 4.1 Сравнение вариантов

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Свой протокол** (outbox, серверные версии, курсор, LWW по полям) | Нет лишних сервисов. Полный контроль: что синхронизировать, как разбирать конфликты, как класть серверные записи (ответы ИИ, транзакции ZenMoney). Легко отлаживать. Шаблон описан в документации Drift и протоколе WatermelonDB. | Корректность на нас: нужны хорошие тесты | **Выбран** |
| **PowerSync Open Edition** (self-hosted, лицензия FSL, со временем Apache 2.0) | Стабильный Flutter SDK для Android и Windows. Встроенный SQLCipher, персистентная очередь выгрузки, хранилище bucket'ов на Postgres. | Лишний контейнер. Postgres нужен с логической репликацией. Хранилище на Postgres помечалось Beta, интеграция с Drift — alpha/beta. Путь записи всё равно пишем сами, конфликты разбирает наш API. | **План Б**, если свой протокол начнёт буксовать |
| ElectricSQL 1.x | Хорош для веба | Синхронизирует только чтение, официальных Dart- и Kotlin-клиентов нет | Отклонён |
| CRDT: sqlite_crdt / crdt_sync (cachapa), cr-sqlite, Automerge | Математически гарантированная сходимость | Переусложнение для одного пользователя, навязывает схему. cr-sqlite почти заброшен. | Отклонён; берём оттуда только идею HLC |
| Realm / Atlas Device Sync | — | Закрыт в сентябре 2025 | — |
| ObjectBox Sync, Couchbase Lite | Готовая синхронизация | Проприетарные или тяжёлые, уводят с Postgres | Отклонены |
| Zero (Rocicorp), Triplit, InstantDB | — | TypeScript и веб, клиентов для Dart нет | Отклонены |

**Почему не PowerSync сразу.** Он снимает транспорт и очередь, но главное — правила применения записей и разбор конфликтов — всё равно живёт в нашем API. Для одного пользователя с редкими конфликтами собственный протокол — это несколько сотен строк на каждой стороне и ноль дополнительных сервисов. Схему БД при этом держим совместимой с PowerSync: UUID-ключи, мягкое удаление, плоские таблицы. Так переход на план Б останется дешёвым.

### 4.2 Правила данных

- **Идентификаторы.** UUIDv7 генерирует клиент при создании записи. Они уникальны глобально и сортируются по времени. Серверные сущности (ответы ИИ, транзакции из ZenMoney, инциденты) получают UUIDv7 на сервере.
- **Служебные поля каждой синхронизируемой таблицы:**
  - `id`;
  - `created_at`;
  - `updated_at` — HLC-метка последнего изменения;
  - `deleted_at` — мягкое удаление (tombstone);
  - `server_version` — монотонный номер, который сервер присваивает при каждом принятом изменении; берётся из одной глобальной последовательности;
  - `origin_device_id`.
- **Пополевые версии (только на сервере):** служебная карта «поле → server_version последнего изменения этого поля». Нужна для слияния по полям.
- **HLC** (гибридные логические часы): физическое время устройства, логический счётчик и id устройства. HLC защищает порядок событий от расхождения часов телефона и ПК. Реализацию можно взять за образец из пакета `crdt` (cachapa).
- **Мягкое удаление.** Удаление ставит `deleted_at`. Физически запись удаляется на сервере через 90 дней, и только если курсоры всех активных устройств уже прошли её версию. Каскад для дочерних записей (удаляем проект — удаляются доработки) выполняется на клиенте как набор мягких удалений в одной транзакции.
- **Что синхронизируется:** все пользовательские данные модулей Календарь, Задачи, Работа, Финансы, Учёба, Сон, а также чаты, промты, пресеты контекста и настройки.
- **Что не синхронизируется:**
  - временные ряды мониторинга и логи бэкапов — онлайн-REST, на клиенте кэшируется последний снимок дашборда для офлайн-просмотра;
  - файлы локальных моделей;
  - сырые тексты банковских уведомлений: хранятся локально 30 дней, на сервер уходит только распознанный черновик;
  - секреты.
- **Деньги:** целое число в минимальных единицах плюс ISO-код валюты.
- **Время:** момент в UTC плюс IANA-таймзона. «Весь день» и «без времени» хранятся как дата без времени. Правила повторения — строки RRULE (RFC 5545).

### 4.3 Алгоритм

**Клиент, запись.** Любое изменение сущности в одной локальной транзакции:
1. обновляет строку и её `updated_at` (HLC);
2. добавляет операцию в **outbox**. Операция содержит:
   - `op_id` (UUID);
   - таблицу и id строки;
   - тип: upsert или delete;
   - **только изменённые поля** с новыми значениями;
   - `base_version` — server_version строки, которую клиент видел;
   - HLC-метку.
3. Несколько правок одной строки до отправки схлопываются в одну операцию, изменённые поля объединяются.

**Push** (отправка пачками до ~500 операций). Сервер обрабатывает пачку в одной транзакции, по каждой операции:
1. **Идемпотентность.** Если `op_id` уже в журнале обработанных, операция пропускается, клиенту возвращается прежний результат. Это страхует от повторов при обрыве связи.
2. **Нет конфликта.** Если текущая server_version строки равна `base_version` (или строки ещё нет), изменения применяются. Строка получает новую server_version, обновляются версии изменённых полей.
3. **Конфликт.** Строка менялась на сервере после `base_version`:
   - поля, которые клиент менял, а сервер после base не трогал, применяются молча — **слияние по полям**;
   - если поле менялось с обеих сторон, побеждает большая HLC-метка (**LWW**). Проигравшее значение пишется в **журнал конфликтов**: таблица, строка, поле, оба значения, устройства, время. В UI журнал показывается в «Настройки → Синхронизация → Разрешённые конфликты» с кнопкой «вернуть моё».
4. **Удаление против правки.** Удаление побеждает, если его HLC новее. Если правка новее удаления, запись «воскрешается», и это тоже пишется в журнал конфликтов.
5. **Валидация** на сервере: схема, внешние ключи, доменные инварианты. Невалидная операция отклоняется с кодом. Клиент помечает её как ошибочную, показывает бейдж «не синхронизировано» и не блокирует очередь.
6. Ответ содержит статус по каждой операции и новые server_version. Клиент удаляет подтверждённые операции из outbox.

**Pull.**
1. Клиент хранит `last_pulled_version` и запрашивает изменения с server_version больше курсора. Ответ упорядочен по версии, пачками до ~1000 строк, включая tombstone'ы.
2. Клиент применяет пачку в транзакции:
   - если по строке нет неотправленных операций в outbox, она перезаписывается;
   - если есть, серверная версия ложится как база, а локальные неотправленные поля накладываются поверх (**rebase**). `base_version` операции обновляется, и её конфликт разрешится при следующем push.
3. Курсор сдвигается только после успешного применения пачки.

**Порядок и триггеры:**
- цикл всегда «push, затем pull»;
- запускается при старте приложения, при появлении сети, через 2–5 секунд после локальной правки, по сигналу из SSE-канала (устройство онлайн) и периодически: WorkManager на Android каждые ~15 минут, таймер на Windows, пока приложение в трее.

**Первичная загрузка** нового устройства — это pull с нулевого курсора, постранично, с прогресс-баром.

**Версионирование протокола.** Клиент передаёт версию схемы:
- если клиент старше минимально поддерживаемой версии, сервер отвечает «нужно обновление», а клиент показывает баннер и продолжает работать офлайн;
- новые поля старые клиенты игнорируют: неизвестные колонки отбрасываются при применении.

**Серверные записи** (ответы ИИ, импорт ZenMoney, созданные ботом сущности) пишутся на сервере с новой server_version и приходят на клиенты обычным pull.

**Мониторинг здоровья синхронизации** — экран в настройках: размер outbox, время последнего успешного push и pull, ошибки операций, конфликты, кнопка «полная пересинхронизация» (сброс курсора с сохранением outbox).

### 4.4 Тестирование синхронизации

- Property-based тесты на сервере (Hypothesis). Два-три симулированных клиента выполняют случайные последовательности правок и удалений с произвольными обрывами сети и повторами. Затем проверяется, что все реплики совпадают с сервером и потерянные значения есть в журнале конфликтов.
- Интеграционный тест «телефон офлайн 3 дня, ПК онлайн, потом встреча».
- Тест идемпотентности: повтор той же пачки.

### 4.5 Готовые решения и референсы
- **Drift, раздел «server sync»** (simolus3/drift): рекомендованный шаблон с триггерами и outbox.
- **WatermelonDB sync protocol** (Nozbe/WatermelonDB): классический pull/push с метками. Берём структуру эндпоинтов.
- **cachapa/crdt** и **cachapa/sqlite_crdt**: реализация HLC на Dart — образец.
- **Actual Budget** (actualbudget/actual): local-first финансовое приложение с синхронизацией. Идеи по журналу изменений.
- **PowerSync** (powersync-ja/powersync.dart, powersync-service): план Б, держим схему совместимой.

**Вычисляемые показатели** (не хранятся, считаются в доменном слое одинаково на клиенте и сервере):
- **Сумма проекта** = базовая сумма + сумма доработок (без отменённых).
- **Получено** = сумма распределений платежей.
- **Доля оплаты** = получено / сумма. Это колонка «Оплата (0..1)» из Excel.
- **Остаток** = сумма − получено.
- **Моя часть** = сумма × моя доля.
- **Ожидаемые поступления** по месяцам = план со статусами «план» и «просрочено». Это помесячные колонки Excel.
- **Доход в час по проекту** = (получено или заработано) × моя доля / часы по проекту. Показываются оба варианта: «по факту денег» и «по начисленному».

**Проверка формулы на Excel заказчика.** «Есть 329 600» раскладывается ровно:
- счета: 54 000 + 174 000 + 8 000;
- долги мне: 7 500 + 2 600 + 3 000;
- «Рома»: 20 000 + 60 500.

«Осталось −54 600» = 400 000 − 329 600 − 125 000. Значит, в таблице кредитка **прибавляется** к ресурсам как доступный лимит, а не вычитается как долг. Отсюда настраиваемый режим учёта кредитки в Goal (открытый вопрос в разделе 11).

### 5.9 Связи между модулями

- **Задача ↔ Проект / Доработка.** Задачи проекта и доработки видны в карточке проекта и в общем списке задач. Прогресс доработки считается по её задачам.
- **Задача ↔ Календарь.** Задача с датой-временем или тайм-блоком видна в сетке календаря как отдельный слой. Задача без времени видна в списке «Сегодня» и в строке «весь день».
- **Проект ↔ Заказчик ↔ Партнёр (Person).** Экран контрагента показывает все проекты, суммы, долги и платежи.
- **Проект → График оплат → Ожидаемые поступления → Финансы.** Ожидаемые поступления попадают в прогноз денежного потока и (по настройке) в «Есть» у целей.
- **Платёж по проекту ↔ Транзакция (доход).** При отметке «получено» создаётся или связывается доходная транзакция на выбранном счёте. Обратное тоже работает: входящий перевод из ZenMoney можно «привязать к платежу проекта» (подсказка по сумме и плательщику).
- **Партнёр (Рома) ↔ Взаиморасчёты ↔ Долги.** Деньги, прошедшие через партнёра, — это дебиторка «Рома», как в «Финансовой таблице».
- **TimeEntry ↔ Проект ↔ Задача.** Доход в час, часы по задачам, продуктивность дня.
- **Сон ↔ Продуктивность.** DailyMetrics объединяет сон (SleepEntry), выполненные задачи, часы трекера, посещаемость и DailyReview.
- **Пары ↔ Календарь.** Слоты расписания пар — это события слоя «Учёба». Посещаемость отмечается из события и из уведомления «Был на паре?».
- **Учебный долг ↔ Задачи.** Долг порождает задачи с дедлайном.
- **Серверы ↔ Проекты Работы.** Карточка проекта показывает статус его сервисов и последний бэкап. Инцидент может автоматически создать задачу «разобраться с падением X» (по настройке).
- **Чат ↔ всё.** Контекст собирается из любого модуля. Инструменты создают задачи (а позже траты, записи времени, долги) через карточку одобрения.

## 6. Модули

### 6.1 Чат с ИИ-агентом

**Функционал:**
- Список чатов с фильтром по теме: финансы, работа, учёба, календарь и задачи, сон, общий. Создание чата, автогенерация заголовка, закрепление, архив, поиск по истории.
- Быстрый выбор модели прямо в поле ввода: 3–5 избранных моделей. Отдельный переключатель «Облако / На устройстве»; на устройстве — только Android.
- Стриминг ответа с кнопкой «Стоп», повтор, редактирование последнего сообщения, копирование, markdown и таблицы в ответах.
- **Настройки:**
  - управление избранными моделями: поиск по каталогу polza.ai с ценой и контекстом, отметка «умеет инструменты»;
  - редактор системных промтов агентов с историей версий и откатом;
  - **конструктор контекста**.
- **Карточка задачи от агента.** Агент предлагает задачу, в ленте появляется карточка с полями: заголовок, дата и время или «без времени», приоритет, проект, заметки. Поля редактируются прямо в карточке, дальше «Одобрить» или «Отклонить».
- Расход: стоимость каждого ответа в ₽, сумма за месяц, баланс polza.ai.
- Позже: голосовой ввод через транскрипцию polza.ai на Whisper-моделях.

**polza.ai (проверено на 2026-09-30):**
- **API OpenAI-совместимый.** Базовый адрес — `https://polza.ai/api/v1`, эндпоинт чата — `/chat/completions`, авторизация — `Authorization: Bearer`. Документация сама показывает официальный OpenAI SDK с подменой base_url. Отдельный SDK не нужен.
- **Стриминг.** Параметр stream даёт SSE с дельтами в OpenAI-формате. Значения finish_reason: stop, length, tool_calls, content_filter. В ответе есть usage со стоимостью в рублях. Не проверены точный сырой формат чанков, маркер завершения и передача usage в стриме: проверяем на спайке (фаза 0).
- **Список моделей.** `GET /api/v1/models` работает без авторизации. Фильтр по типу: chat, embedding, audio, stt и т. д. У каждой модели есть:
  - id в формате «провайдер/модель»;
  - имя;
  - context_length и max_completion_tokens;
  - цены в ₽ за 1M токенов;
  - supported_parameters — по нему определяем поддержку tools и response_format.

  Имена полей цен в документации и в живом ответе расходятся, поэтому парсим устойчиво. Моделей в каталоге 400+.
- **Tool/function calling.** Поддерживаются tools с JSON Schema, tool_choice (auto, required, none, конкретная функция) и параллельные вызовы. Structured output — через response_format с json_schema. Всё это зависит от конкретной модели.
- **Ошибки и лимиты:**
  - 402 — нет баланса. Запрос резервирует входные токены + max_tokens, поэтому параллельные запросы могут получить 402 даже при положительном балансе;
  - 429 — rate limit, с заголовком Retry-After;
  - 408, 502, 503 — транзиентные ошибки;
  - таймаут запроса — 600 секунд;
  - неуспешные запросы не тарифицируются.
- **Баланс.** Устаревший эндпоинт баланса ещё работает, есть Balance v2. Точный путь v2 уточняем на спайке.
- **Идентификаторы моделей.** «GPT-4o», «5 sol» и «5 nano» из брифа сопоставляются так:
  - `openai/gpt-4o`;
  - «sol» — линейка OpenAI с суффиксами sol, luna, terra, astra: например `openai/gpt-5.6-sol` или `openai/gpt-6-sol`;
  - `openai/gpt-5-nano`.

  Старые id (gpt-5, gpt-5-mini, gpt-5-nano) есть в каталоге на сайте, но в выгрузке /models могли просто не попасть в обрезанный фрагмент. Поэтому в коде id **никогда не хардкодим**: избранное хранит id, который при старте сверяется с живым каталогом, а недоступные модели помечаются. Точный набор избранного подтверждает заказчик.

**Решение: LLM через прокси бэкенда, а не напрямую с клиента.**

Почему:
1. Ключ `POLZA_API_KEY` не лежит в APK или на ПК: декомпиляция и потеря телефона ничего не дают.
2. Единый учёт расходов и лимиты: например, месячный потолок в ₽ с предупреждением.
3. Каталог моделей кэшируется и нормализуется в одном месте.
4. Провайдера можно сменить без обновления клиентов.
5. Ответ сохраняется на сервере, даже если клиент потерял связь посреди стрима: клиент потом заберёт его синхронизацией.
6. Сервер добавляет системную информацию: текущие дату, время и таймзону.

Минус: +1 хоп (~десятки мс) и зависимость от доступности VPS. Для онлайн-режима это приемлемо.

**Как реализуем:**

*Сборка контекста* — на клиенте. У клиента полная локальная БД, и одна реализация работает и для облака, и для локальной модели. ContextPreset задаёт источники. Каждый источник сериализуется в компактный текст: списки и таблицы в markdown, суммы в ₽, даты — относительно «сегодня». Для каждого источника есть оценка токенов и превью «что увидит модель». Флаг «чувствительное» (например, операции по счетам) исключает источник при отправке в облако.

*Инструменты двух классов*, исполнение на клиенте:
- **Читающие** (get_tasks за диапазон, get_project_summary, get_finance_summary, get_sleep_stats и т. п.). Выполняются автоматически. Модель запрашивает данные сама, вместо того чтобы получать весь контекст в промт.
- **Пишущие** (create_task; позже update_task, add_expense, log_time, add_debt). **Никогда не выполняются без одобрения**: в ленте появляется ToolProposal-карточка.

*Поток онлайн-ответа:*
1. Клиент создаёт локально сообщение пользователя.
2. Клиент вызывает api «начать стрим». Передаёт: id чата, модель, собранные сообщения (системный промт профиля + контекст + история, обрезанная по бюджету токенов), список доступных инструментов.
3. Api открывает стрим к polza.ai и ретранслирует события по SSE:
   - начало ответа (id сообщения ассистента);
   - дельта текста;
   - вызов инструмента (имя, аргументы, id вызова);
   - usage и стоимость;
   - конец;
   - ошибка.
4. При вызове **читающего** инструмента клиент выполняет его локально и отправляет результат в api «продолжить с результатом инструмента». Стрим продолжается. Лимит — 5 шагов на один ответ.
5. При вызове **пишущего** инструмента стрим завершается карточкой. Пользователь правит поля, затем:
   - «Одобрить»: задача создаётся локально (outbox → синхронизация), статус карточки становится «одобрено», в историю пишется результат инструмента «создана задача #id»;
   - «Отклонить»: результат «пользователь отклонил, причина…».

   Модель видит итог при следующем сообщении.
6. Api сохраняет финальное сообщение ассистента с токенами и стоимостью как синхронизируемую запись. Клиент получает его тем же id, дублей нет.
7. Отмена: клиент закрывает стрим, api прерывает запрос к провайдеру и сохраняет частичный ответ со статусом «отменено».

*Разбор дат.* Системная часть промта всегда содержит текущие дату, время, день недели, таймзону и **чётность текущей недели**. Аргументы create_task валидируются по JSON-схеме. Относительные даты («в следующий вторник») модель переводит в ISO. Клиент дополнительно проверяет результат и подсвечивает сомнительное: дата в прошлом, конфликт с расписанием.

*Генерация заголовка чата* — дешёвой моделью, например gpt-5-nano, после первого ответа.

**Офлайн-модель на Android.**

*Контекст и ограничения.* Galaxy A55: Exynos 1480, CPU 4×Cortex-A78 + 4×A55, GPU Xclipse 530, 8 ГБ ОЗУ.
- В трекере LiteRT-LM открыта issue #2611: Gemma 4 E2B на **GPU именно Galaxy A55** выдаёт мусор, при этом CPU работает корректно. На других Exynos GPU-движок тоже падает. **Значит, планируем только CPU-инференс.**
- MediaPipe LLM Inference API переведён в режим поддержки; Google рекомендует LiteRT-LM.
- Публичного NPU-пути для Exynos 1480 нет.

*Рекомендация (основной вариант):*
- **Gemma 4 E2B-it** в формате .litertlm (~2,6 ГБ, смешанные 2/4/8 бит) на **LiteRT-LM, бэкенд CPU**;
- интеграция через Flutter-пакет **flutter_gemma** (DenisovAV/flutter_gemma), он поддерживает LiteRT-LM и function calling;
- почему: у Gemma 4 нативный function calling, структурированный JSON-вывод и 140+ языков (русский приемлем для кратких ответов);
- ожидаемая скорость на A55 **ориентировочно 8–15 токенов/с** на генерации. Это экстраполяция: на флагмане S26 Ultra CPU даёт ~47 т/с. Сколько на самом деле — покажет замер;
- RAM ~2–3 ГБ.

*Запасной вариант:*
- **llama.cpp** через **llamadart** (один пакет покрывает GGUF и .litertlm, умеет парсить tool calls, выдавать JSON по схеме и работать с GBNF-грамматиками) или через **fllama** (Telosnex/fllama);
- модель **Qwen3.5-4B** (ориентирована на агентов и tool calling, 201 язык) или **Qwen3-4B-Instruct-2507**, квантование **Q4_0** — на ARM это самый быстрый формат благодаря repacking;
- если скорость недостаточна, переходим на **Qwen3.5-2B**;
- **tool calling делаем грамматикой**: JSON-схема create_task превращается в GBNF-грамматику. Модель физически не может выдать невалидный JSON, поэтому нативная поддержка инструментов не обязательна;
- Vulkan-бэкенд на Xclipse считаем экспериментальным.

*Что не берём:*
- модели меньше 2B (Llama 3.2 1B, Gemma 3 1B, Qwen2.5 1.5B) — заметно слабы в русском;
- Phi-4-mini — ориентирована на английский;
- E4B-модели на 8 ГБ — рискованно из-за фоновой нагрузки One UI.

*Ограничения офлайн-режима:*
- контекст 4–8 тыс. токенов, поэтому конструктор контекста применяет «лёгкий» пресет;
- инструменты: create_task плюс 2–3 читающих;
- стриминг есть (токены генерируются локально);
- модель скачивается один раз с нашего сервера или с Hugging Face по Wi-Fi, с проверкой хеша;
- выгружается из памяти через ~2 минуты простоя;
- чат, начатый офлайн, помечается «локальная модель» и синхронизируется как обычный.

*Спайк в фазе 0* (обязателен до реализации):
1. Прогнать на реальном A55 AI Edge Gallery (CPU, Gemma 4 E2B), встроенный бенчмарк PocketPal AI (GGUF Qwen3.5-2B/4B, Gemma 4 E2B в Q4_0) и MNN Chat для сравнения.
2. Замерить: скорость генерации, время обработки промта на 2 тыс. токенов, пиковую RAM, нагрев и троттлинг за 5 минут.
3. Прогнать 20 русских фраз «создай задачу…» и посчитать долю корректного JSON и дат.

**API-эндпоинты (словами):**
- получить каталог моделей: кэш polza /models, нормализованный — id, имя, контекст, цены, поддержка tools и vision;
- начать стриминговый ответ (SSE);
- продолжить с результатом инструмента (SSE);
- отменить генерацию;
- сгенерировать заголовок чата;
- получить расход по дням и моделям, баланс polza.ai;
- (позже) транскрибировать голос;
- чаты, сообщения, профили, промты, пресеты, избранные модели — через общую синхронизацию, отдельных CRUD-эндпоинтов нет.

**Библиотеки:**
- сервер: `openai` (Python SDK с base_url), `sse-starlette` (sysid/sse-starlette), `tiktoken` для приблизительной оценки токенов;
- клиент: потоковый HTTP-клиент с разбором SSE, `flutter_chat_ui` (flyerhq/flutter_chat_ui) как основа ленты либо своя лента, `flutter_markdown_plus` / `markdown_widget` для рендера, flutter_gemma, llamadart.

**Сложности и риски:**
- разные модели по-разному поддерживают tools; UI скрывает инструменты для моделей без поддержки;
- 402 при параллельных запросах;
- ретрансляция SSE через Caddy: отключаем буферизацию, ставим keep-alive;
- обрывы мобильной сети посреди стрима: ответ сохраняется на сервере, клиент его подтягивает;
- приватность: данные уходят провайдерам моделей через polza.ai (заявлено соответствие 152-ФЗ, но конечные провайдеры зарубежные), поэтому нужен флаг «чувствительное» и локальный режим;
- качество русского у локальной модели;
- нагрев телефона.

**Готовые решения и референсы:**
- **Open WebUI** (open-webui/open-webui) и **LibreChat** (danny-avila/LibreChat): UX пресетов, промтов, выбора моделей и истории;
- **LobeChat** (lobehub/lobe-chat): конструктор агентов и плагинов;
- паттерн «human-in-the-loop tool approval» из Vercel AI SDK: схема карточек одобрения;
- **google-ai-edge/gallery**: эталон работы с LiteRT-LM;
- **a-ghorbani/pocketpal-ai**, **Mobile-Artificial-Intelligence/maid**, **shubham0204/SmolChat-Android**: примеры локального чата и бенчмарк;
- **ggml-org/llama.cpp**, **grammars/json-schema-to-grammar**: ограничение вывода.

### 6.2 Календарь и таск-трекер (главный модуль)

**Функционал:**
- **Виды:** день, 3 дня, неделя, месяц, «расписание» (лента). Слева — мини-календарь и список слоёв с чекбоксами, как в Google Calendar (ref1). На телефоне — день или неделя с вертикальной шкалой и нижняя панель «Задачи на сегодня».
- **События:** создание тапом или перетягиванием по сетке, drag-and-drop для переноса, изменение длительности, повторения, напоминания.
- **Задачи:**
  - создание, редактирование, удаление, подзадачи;
  - **с временем** (попадают в сетку), **с датой без времени** (строка «весь день» и список дня), **без даты** («Входящие»);
  - приоритеты P1–P4 с цветовой меткой;
  - теги, проект, доработка;
  - быстрый ввод одной строкой с разбором («завтра 15:00 позвонить Роме !p1 #работа»);
  - перетаскивание задачи из списка в сетку — тайм-блокинг;
  - повторяющиеся задачи;
  - просроченные поднимаются в «Сегодня».
- **Чередующееся расписание:**
  - шаблоны с циклом N недель: «чёт/нечёт», «A/B», трёхнедельные циклы;
  - в шапке недели — бейдж «нечётная» или «неделя A»;
  - редактор шаблона: сетка-неделя с вкладками «Неделя 1 | Неделя 2», слоты перетаскиваются;
  - кнопки: «Пропустить неделю» (каникулы), «Сдвинуть чётность» (если вуз объявил сдвиг), «Применить шаблон к конкретной неделе» (разовое копирование в события);
  - шаблонов может быть несколько одновременно: учёба и работа.
- **Праздники РФ и производственный календарь:** слой «Праздники России», переносы рабочих дней, подсветка выходных.
- **Поиск и фильтры:** по слоям, проекту, приоритету, статусу.

**Как реализуем чередование (ключевое решение):**
- Слот шаблона компилируется в правило повторения RFC 5545: частота «еженедельно», интервал равен длине цикла, день недели = день слота. Начало серии = опорная дата + (номер недели в цикле − 1) × 7 дней + смещение дня. Окончание серии = конец периода шаблона.
- В итоге чётные и нечётные недели — это просто два набора серий с интервалом 2, сдвинутые на неделю. Развёртка, исключения и переопределения работают единым механизмом с обычными повторяющимися событиями.
- «Пропустить неделю» добавляет даты-исключения всем сериям шаблона в эту неделю.
- «Сдвинуть чётность» перегенерирует серии от выбранной даты: старые серии получают дату окончания, новые начинаются со сдвинутой опорой.
- Номер недели цикла для любой даты = ((дата − опорная дата) в неделях) mod N. Он же выводится в бейдже и передаётся в промт ИИ.

**Повторяющиеся задачи:**
- тоже хранят RRULE;
- экземпляры разворачиваются на лету, отметка выполнения — в TaskCompletion;
- режимы «следующий экземпляр от даты выполнения» (как в Tasks.org) и «строго по расписанию».

**Развёртка RRULE:**
- клиент: Dart-пакет **rrule** (JonasWanke/rrule). Он работает только в UTC и только с неделей от понедельника. Для РФ это подходит: хранится локальное «настенное» время плюс таймзона, развёртка идёт в UTC-представлении настенного времени;
- сервер (дайджесты и напоминания в Telegram): **python-dateutil rrule**;
- расхождения ловят **общие тестовые векторы** в `shared-test-vectors/`: одинаковые входы и ожидаемые даты для обеих реализаций.

**Напоминания:** локальные уведомления планируются на ближайшие 14 дней вперёд и пересчитываются при каждом изменении и при старте (подробно в разделе 7).

**UI-компоненты:**
- **kalender** (werner-scholtz/kalender): виды день, несколько дней, месяц и расписание, drag, resize, таймзоны, своя модель событий. Основной кандидат. Пакет до 1.0, поэтому фиксируем версию;
- запасной вариант — **calendar_view** (SimformSolutionsPvtLtd/flutter_calendar_view);
- **table_calendar** — мини-календарь;
- syncfusion_flutter_calendar мощный, но лицензия community ограничена. Не берём, чтобы не зависеть от лицензии.

**Производственный календарь:** API **isdayoff.ru** (рабочий или выходной день по дате, с кэшем) или JSON **d10xa/holidays-calendar**. Раз в месяц сервер обновляет слой «Праздники России» и отдаёт его как системный календарь через синхронизацию.

**API-эндпоинты:** всё идёт через синхронизацию. Дополнительно:
- импорт ICS (например, расписание вуза или старый Google Calendar);
- экспорт ICS-ленты «только чтение» по секретной ссылке — опционально, чтобы видеть расписание в Google Calendar;
- производственный календарь на год.

**Сложности и риски:**
- производительность развёртки на месячном виде: кэшируем развёрнутые экземпляры в памяти на видимый диапазон;
- правка «только этот экземпляр» против «этот и следующие» (разрез серии);
- таймзоны при поездках: всё хранится с IANA-таймзоной;
- удобство сетки на маленьком экране и drag на тач-экране.

**Готовые решения и референсы:**
- **tasks/tasks** (Tasks.org, Android): зрелая логика повторений и напоминаний задач;
- **johannesjo/super-productivity**: задачи, тайм-блокинг, трекинг времени, интеграция задач с календарём. Близкий по духу продукт;
- **go-vikunja/vikunja**: модель задач, повторений, приоритетов;
- **Etar-Group/Etar-Calendar**: работа с повторяющимися событиями на Android.

### 6.3 Финансы

**Функционал:**
- **Главный экран:**
  - крупная цифра «Всего»;
  - карточки счетов: наличные, Т-Банк, ВТБ, кредитка с долгом и доступным лимитом;
  - «Мне должны», «Я должен»;
  - «Ожидается от проектов» (с разбивкой «через Рому» и «напрямую»);
  - цели с прогресс-баром и строкой «не хватает N ₽».
- **Операции:** лента с фильтрами, быстрый ввод траты за 2 тапа (сумма, категория), переводы между счетами, погашение кредитки.
- **Аналитика:** доходы и расходы по месяцам (столбики), расходы по категориям (donut), динамика капитала, прогноз денежного потока на 3 месяца с учётом графика оплат проектов.
- **Долги:** кто сколько должен, частичные погашения, напоминания о сроках.
- **Цели:** несколько целей, настраиваемая формула «Есть», режим учёта кредитки, история прогресса, прогноз даты достижения по среднему накоплению.
- **Кредитки:** лимит, задолженность, дата платежа, напоминание за 3 дня.
- **Черновики** из уведомлений банков: подтвердить, изменить категорию или отклонить.
- **Сверка баланса:** «в приложении банка 174 000, у нас 173 200 → создать корректировку».

**Получение банковских данных (исследование на 2026-09-30):**

|---|---|---|---|

**Рекомендуемая комбинация:**
1. **ZenMoney как агрегатор.** Работает на сервере: worker раз в 15–30 минут вызывает diff с последней меткой. Токен хранится на сервере, зашифрованный в БД. Маппинг:
   - счёт ZenMoney → Account (по внешнему id);
   - транзакция → Transaction с источником «ZenMoney»;
   - тег → Category по таблице соответствий, которую пользователь настраивает один раз.

   В режиме «только чтение» в ZenMoney ничего не пишем. Баланс счёта из ZenMoney — это BalanceCheckpoint.
2. **Уведомления банков на телефоне:**
   - белый список пакетов Т-Банка, ВТБ, Сбера и т. д.;
   - парсер — чистая функция «пакет, заголовок, текст, время → распознанная операция или ничего», покрытая тестами на реальных обезличенных текстах;
   - результат — черновик транзакции, остаток из текста — BalanceCheckpoint;
   - черновик подтверждается автоматически, когда из ZenMoney приходит та же операция: совпадают счёт (по последним 4 цифрам карты), сумма, время ±15 минут и мерчант.
3. **Импорт CSV/OFX:**
   - мастер импорта на десктопе с сопоставлением колонок и сохранением «профиля банка»;
   - дедупликация по хешу (счёт, дата, сумма, описание);
   - разбор на сервере: ofxparse, стандартный CSV, pdfplumber — только как крайний вариант для PDF.
4. **Ручной ввод** для наличных и корректировок.

Если заказчик **не** пользуется ZenMoney, основой становятся пункты 2–4, а балансы держатся на точках сверки.

**Дедупликация и приоритет источников:** ZenMoney или выписка > подтверждённый вручную черновик > черновик из уведомления. Операции с внешним id не дублируются никогда.

**Как реализуем расчёты:**
- доменный модуль «money» с одинаковой логикой на Dart и Python, покрытый общими тестовыми векторами. Балансы, «Есть» по цели и прогноз считаются из транзакций, точек сверки и графика оплат;
- «Ожидается от проектов» берётся напрямую из модуля Работа, двойного ввода нет.

**API-эндпоинты:**
- данные — через синхронизацию;
- подключить ZenMoney: сохранить токен на сервере, первичная загрузка, статус последней синхронизации, отключить;
- ручной запуск синхронизации ZenMoney;
- загрузить выписку и получить предпросмотр распознанных операций, подтвердить импорт;
- сопоставление категорий ZenMoney.

**Библиотеки:**
- клиент: `notification_listener_service` (pub.dev), при нестабильности — свой нативный Kotlin-сервис с foreground-режимом; `fl_chart` для графиков;
- сервер: клиент ZenMoney на httpx (протокол простой; за основу — python-zenmoney, zenmoney-py), ofxparse, pdfplumber.

**Сложности и риски:**
- зависимость от неофициального по сути ZenMoney API и его подписки;
- сбои синхронизации ВТБ в ZenMoney;
- изменение текстов пушей;
- Samsung убивает фоновые сервисы: нужна инструкция «не оптимизировать батарею»;
- переводы между своими счетами выглядят как расход плюс доход: правило склейки по сумме и времени;
- кредитки: знак баланса и «доступно» против «долга».

**Готовые решения и референсы:**
- **zenmoney/ZenPlugins** (wiki «ZenMoney API»): протокол diff. Код плагинов под GPL-3.0 — не копируем, только читаем протокол;
- **ardov/zerro**: веб-клиент ZenMoney, идеи UI бюджета и получения токена;

### 6.4 Учёба

**Функционал:**
- Семестр: даты, опорная неделя чётности, сессия.
- Предметы: преподаватель, форма контроля, лимит пропусков.
- **Расписание пар** — шаблон с циклом чёт/нечёт (механизм из 6.2). Пары видны в календаре слоем «Учёба». Экран «Сегодня/завтра»: пары с аудиториями и бейджем чётности.
- **Посещаемость:**
  - через 10 минут после начала пары приходит уведомление «Был на паре?» с кнопками «Был» / «Пропустил» / «Уважительная»;
  - отметить можно и из события;
  - статистика пропусков по предметам (сколько и каких: лекции, практики, лабы);
  - предупреждение при приближении к лимиту.
- **Долги:** список по предметам с дедлайнами. Долг порождает задачи. Счётчик «закрыть до сессии».
- Импорт расписания: ICS, если вуз даёт, или ручной ввод в редакторе-сетке.

**Как реализуем:** всё на общих сущностях календаря. ClassSlot — это TemplateSlot типа «пара» со ссылкой на Subject. Attendance ссылается на экземпляр пары: предмет + дата-время начала.

**API-эндпоинты:** через синхронизацию. Импорт ICS — общий с календарём.

**Библиотеки:** Dart-пакет **icalendar_parser** для ICS или разбор на сервере через `icalendar` (Python).

**Риски:** переносы пар и замены — EventOverride; изменение чётности посреди семестра — «Сдвинуть чётность»; формат расписания конкретного вуза (открытый вопрос).

**Референсы:** у многих российских вузов есть JSON-API расписания (семейство «ruz»). Конкретику выясняем у заказчика.

### 6.5 Работа (самый важный модуль)

**Функционал:**
- **Дашборд Работы:**
  - «В работе» (проекты с прогрессом);
  - «Мне должны по проектам» (остаток, сгруппированный по заказчику и партнёру);
  - «Ожидается в этом и следующем месяце» — как колонки «Оплата в сентябре» и «в октябре»;
  - доход за месяц;
  - часы за неделю;
  - **доход в час** по проектам (рейтинг);
  - плитка «Серверы: 1 лежит из 9» — вход в подраздел.
- **Проекты:**
  - карточка проекта: заказчик, партнёр, моя доля, сумма, получено, остаток, доля оплаты;
  - вкладки «Доработки» (дерево «проект → доработки» как в Excel, у каждой своя сумма и статус), «Задачи», «График оплат», «Платежи», «Время», «Серверы»;
  - вид «таблица как в Excel»: проект и доработки строками, месяцы оплат колонками, итоги. Привычный вид для заказчика.
- **Заказчики и партнёры:** экран человека со всеми проектами, суммами и взаиморасчётами.
- **Платежи:**
  - план по месяцам;
  - отметка «получено» с созданием дохода в Финансах;
  - частичные оплаты;
  - один платёж на несколько доработок;
  - просроченные подсвечиваются и попадают в напоминания.
- **Трекер времени:**
  - старт и стоп таймера из карточки проекта или задачи, из виджета Android, из трея Windows;
  - всегда один активный таймер, он синхронизируется;
  - ручные записи, Pomodoro-режим (опционально);
  - на Android — постоянное уведомление с идущим временем;
  - напоминание «таймер идёт уже 4 часа»;
  - отчёт: часы по проектам, дням и задачам.
- **Импорт из Excel:** разовый мастер для «Эдвард_Рома.xlsx» и «Финансовая таблица.xlsx» переносит проекты, доработки, оплаты по месяцам, долги и счета, чтобы стартовать с реальными данными.

**Как реализуем:**
- сущности из 5.3; все итоги считаются в доменном слое;
- «Моя доля» и «через партнёра»: если деньги идут через Рому, поступление от заказчика — это дебиторка партнёра (PartnerSettlement). Когда Рома переводит мою часть, взаиморасчёт закрывается, и появляется доход в Финансах;
- доход в час считается в двух вариантах:
  - «кассовый» — полученные деньги / часы;
  - «начисленный» — сумма закрытых доработок × доля / часы.

**API-эндпоинты:**
- через синхронизацию;
- загрузить Excel, предпросмотр распознанной структуры, подтвердить импорт (разбор на сервере через openpyxl: строки-проекты и строки-доработки различаются по отступу или форматированию, колонки месяцев — по заголовкам);
- отчёт по времени и доходу за период (PDF/CSV для себя или заказчика, позже).

**Сложности и риски:**
- **неоднозначность исходных таблиц** (раздел 11). Сумма колонок «до сентября + сентябрь + октябрь + остаток» не равна итоговой сумме, а остаток «Рома» в двух таблицах разный (20 000 против 60 500). Модель должна уметь и полную сумму проекта, и мою долю — уточнить у заказчика;
- забытые таймеры;
- проекты в разных валютах (редко).

**Готовые решения и референсы:**
- **solidtime-io/solidtime**: современный open-source трекер времени с клиентами, проектами, оплачиваемыми ставками. Модель данных и отчёты;
- **kimai/kimai**: трекинг, ставки, бюджеты проектов;
- **johannesjo/super-productivity**: UX таймера, привязанного к задачам;
- **invoiceninja/invoiceninja**: модель платежей и частичных оплат (для вдохновения).

### 6.6 Серверы: мониторинг, бэкапы, Telegram

Сами проверки HTTP, TCP, DNS и SSL тривиальны, а ценность — в логике инцидентов и антиспама, которую переносим из Gatus и Healthchecks. **План Б для ускорения:** в фазе мониторинга сначала поднять Gatus сайдкаром и отрисовать его данные в нашем UI, затем заменить своим движком.

#### 6.6.2 Проверки (worker, снаружи)
- **HTTP(S):** метод, ожидаемые коды, ключевое слово или JSON-условие, максимальное время ответа, следование редиректам, собственные заголовки (например, токен health-эндпоинта — имя переменной окружения, не значение).
- **TCP:** хост и порт, время соединения.
- **DNS:** запись A, AAAA, CNAME или MX, ожидаемое значение, резолвер.
- **SSL:** дней до истечения, валидность цепочки. Предупреждения за 30, 14, 7, 3 и 1 день — каждое по одному разу.
- **ICMP ping:** опционально, из контейнера нужна capability NET_RAW.
- **Push/heartbeat:** уникальный URL. Если пинга нет дольше «период + grace», сервис считается упавшим. Нужно для cron-задач пользователя и отчётов агента о бэкапах.
- **Планировщик:** у каждой проверки своё «следующее время запуска». Выполнение асинхронное, одновременно не больше ~50 проверок. Равномерный разброс (jitter), чтобы не бить всё в одну секунду.
- **«Проверить»** — внеочередной прогон всех проверок сервиса, результат приходит в UI через SSE.
- **Подтверждение падения:** после первой неудачи — повтор через 10–20 секунд. Инцидент открывается только после N неудач подряд (по умолчанию 3).

#### 6.6.3 Агент (изнутри сервера)

**Развёртывание:** Docker-контейнер (или systemd-бинарник). Доступ к Docker socket только через docker-socket-proxy: разрешены чтение контейнеров, событий и info плюс exec. Входящих портов **нет**.

**Регистрация:**
1. В приложении нажимаем «Добавить сервер» и получаем **одноразовый код регистрации** со сроком 1 час и команду установки.
2. Агент обменивает код на постоянный токен (на сервере хранится хеш) и открывает WSS-соединение к api.
3. Токен можно отозвать в UI.

**Что отправляет агент:**
- heartbeat каждые 30 секунд;
- список контейнеров (имя, образ, состояние, health, рестарты, CPU и RAM);
- события Docker (die, oom, restart) — сразу;
- метрики хоста (CPU, RAM, диск, load) раз в минуту.

**«Контейнеры X из Y»:** Y — ожидаемые контейнеры сервиса (задаются именами или меткой), X — запущенные и здоровые. Отсутствующий или остановленный ожидаемый контейнер — это down.

**Команды** (строго типизированные, **без произвольного shell**):
- выполнить задание бэкапа по id;
- перепроверить контейнеры;
- обновить агент;
- (опционально, с подтверждением в UI) перезапустить контейнер из списка разрешённых.

Параметры проверяются агентом по **локальному allow-list** контейнеров и путей в его конфигурации на сервере. Даже скомпрометированный бэкенд не выполнит на сервере чужой код.

**Агент как сторож бэкенда:** если api недоступен дольше 5 минут, агент (если так настроено) сам отправляет сообщение в Telegram «My Tasker VPS недоступен». Для этого ему выдаётся тот же `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` через переменные окружения. По умолчанию выключено; основной механизм — внешний healthchecks.

**Запасной вариант без агента:** SSH из worker с отдельным пользователем и принудительной командой в authorized_keys, только вывод списка контейнеров. Хуже по безопасности, потому что бэкенд держит SSH-ключи ко всем серверам. Используем, только если агент поставить нельзя.

#### 6.6.4 Инциденты и антиспам

**Жизненный цикл инцидента:**
- открывается после N подряд неудач;
- закрывается после M подряд успехов (по умолчанию 2);
- одно открытое событие на сервис; все проверки сервиса — внутри него.

**Правила алертов:**
1. **Подтверждённое падение** → одно сообщение: сервис, проверка, причина, время, ссылка в приложение.
2. **Напоминания**, пока лежит: через 30 минут, 1 час, 2 часа, дальше каждые 4 часа (экспоненциальная пауза, настраивается).
3. **Восстановление** → всегда одно сообщение с длительностью простоя.
4. **Флаппинг:** больше K смен статуса за T минут (по умолчанию 4 за 30 минут) → одно сообщение «нестабилен», дальше тишина до стабилизации.
5. **Группировка по зависимостям:**
   - нет heartbeat агента и не отвечают проверки хоста → один инцидент «Сервер X недоступен, затронуто 6 сервисов», дочерние алерты подавляются;
   - при массовом падении одно сводное сообщение в течение 60 секунд.
6. **Окна обслуживания и пауза** («Выключить» в карточке) → проверки продолжаются или останавливаются (настройка), алертов нет, в UI статус «обслуживание».
7. **Тихие часы** для некритичных сервисов → алерты копятся и приходят утром одним дайджестом. Критичные сервисы звонят всегда.
8. **Отправка через очередь** с ограничением скорости: ~1 сообщение в секунду на чат, 20 в минуту на группу. Retry-After при 429 соблюдается, неотправленные сообщения склеиваются.
9. **Inline-кнопки в Telegram:** «Проверить сейчас», «Заглушить на 1 час», «Подтвердить (ack)». Колбэки приходят на webhook api, секретный путь плюс проверка secret_token.

#### 6.6.5 Метрики «Пульса»
- **Доступность %** = успешные проверки / все проверки за окно (24 часа, 7 дней, 30 дней). Окна обслуживания исключаются. Берётся из почасовых агрегатов.
- **Отклик** = медиана или последний (настройка), плюс p95 в деталях.
- **Мини-график** = последние 60 результатов или почасовые средние за 24 часа.
- **Хранение:** сырые результаты — 14 дней (партиции по дням), почасовые агрегаты — 180 дней, дневные — бессрочно.

#### 6.6.6 Бэкапы
- **Расписание:** ежедневно в заданное время (по умолчанию ночью, со сдвигом между проектами), cron на задание. Кнопка «Сделать сейчас».
- **Шаги агента:**
  1. Опционально pre-hook: остановить контейнер или включить режим чтения — только если задано.
  2. **Дамп БД** через exec в контейнер: логический дамп PostgreSQL в собственном формате; MySQL и MariaDB — с единым снимком транзакции; MongoDB — архив; Redis — копия снимка; SQLite — через безопасный механизм резервного копирования.
  3. **Тома и файлы:** tar-поток с исключениями.
  4. **Сжатие** zstd.
  5. **Шифрование age** публичным ключом (получатель) из `BACKUP_AGE_RECIPIENT`. **Приватного ключа на серверах нет.**
  6. SHA-256.
  7. **Проверки:** размер не меньше ожидаемого минимума и не упал больше чем на 50% относительно прошлого раза, иначе предупреждение. Для PostgreSQL — проверка оглавления дампа.
  8. **Загрузка:**
     - **S3-совместимое хранилище** (основное off-site: Yandex Object Storage, Selectel, Backblaze B2 или второй VPS с MinIO); при большом размере — multipart;
     - **Telegram** (по требованию заказчика), см. ниже.
  9. Отчёт в api: размер, хеш, места хранения, длительность. Api закрывает dead-man's switch задания.
- **Telegram и лимит 50 МБ.** Облачный Bot API принимает на загрузку до 50 МБ и отдаёт на скачивание до 20 МБ; изменений на 2026 год нет. Стратегия по размеру:
  - **≤ 45 МБ** — sendDocument целиком в тему «Бэкапы»;
  - **45 МБ – 2 ГБ** — если поднят **локальный telegram-bot-api server** (контейнер на VPS, нужны `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` с my.telegram.org), файл отправляется целиком: лимит там до 2000 МБ. Если нет — архив **режется на части по 45 МБ**, каждая шифруется отдельно, части идут медиагруппой, в подписи инструкция по склейке;
  - **> 2 ГБ или > 20 частей** — в Telegram уходит только отчёт: размер, хеш, ключ в S3, срок действия временной ссылки для скачивания (например 7 дней).
- **Ротация (GFS):**
  - в S3: 7 дневных, 4 недельных, 6 месячных, настраивается по заданию;
  - в Telegram сообщения не удаляются: это журнал. Индекс file_id хранится в BackupRun, чтобы восстановить можно было и оттуда.
- **Ежедневный отчёт:** одно сообщение в 08:00 по всем заданиям: ✓ и ✗, размеры, что не выполнилось.
- **Восстановление:**
  - в UI для каждого запуска — «Скачать» (из S3 или Telegram) и пошаговая инструкция;
  - расшифровка приватным ключом age делается **на ПК пользователя**: десктоп-клиент умеет расшифровать архив, если пользователь укажет файл ключа, ключ никуда не отправляется;
  - раз в месяц (опционально) — тестовое восстановление дампа PostgreSQL во временный контейнер на VPS с проверкой, что БД поднимается.
- **Первым бэкапится сам My Tasker:** worker каждые сутки делает дамп собственной PostgreSQL тем же конвейером.

#### 6.6.7 Самопроверка (вкладка)
- отставание планировщика проверок и время последнего цикла;
- возраст heartbeat каждого агента и версии агентов;
- доставка Telegram: последняя успешная отправка, кнопка «тестовое сообщение»;
- **внешний dead-man's switch:** worker пингует healthchecks раз в минуту, иначе алерт от healthchecks в Telegram (единственный способ узнать, что лёг сам VPS);
- свободное место на диске VPS, размер БД;
- срок SSL собственного домена;
- время: синхронизация часов;
- свежесть бэкапов (последний успешный по каждому заданию);
- статус синхронизации ZenMoney;
- баланс polza.ai (предупреждение ниже порога).

#### 6.6.8 API-эндпоинты (словами)
- серверы: список, создать (выдать одноразовый код регистрации агента и команду установки), изменить, удалить, отозвать токен агента;
- сервисы и проверки: CRUD, пауза и возобновление («Выключить»), «проверить сейчас»;
- дашборд: карточки со статусом, аптаймом 24 ч и 30 дней, откликом, контейнерами X из Y, мини-графиком, сводкой «N лежит из M»;
- история проверок и график отклика за период; контейнеры и метрики хоста;
- инциденты: список, детали с хронологией, подтвердить, заметка;
- бэкапы: задания (CRUD), запуски, «сделать сейчас», скачать (ссылка из S3 или проксирование из Telegram);
- самопроверка: сводный статус;
- агенты: обмен кода на токен, WSS-канал агента (heartbeat, состояние, события, команды и результаты), отчёт о бэкапе;

- webhook Telegram-бота с секретным путём и заголовком;
- поток событий для клиентов (SSE): изменение статусов и инциденты в реальном времени.

#### 6.6.10 Сложности и риски
- VPS с бэкендом — единая точка отказа мониторинга. Решается внешним healthchecks и опционально агентом-сторожем.
- Права агента: доступ к Docker socket равен root. Решается socket-proxy, allow-list, отсутствием произвольных команд и выделенным токеном.
- Telegram — ненадёжное основное хранилище бэкапов: нет API листинга, при удалении чата всё теряется. Поэтому S3 обязателен как второе место.
- Большие тома — долгие бэкапы и нагрузка: сдвиг расписания, ionice/nice, restic для инкрементальности.
- Ложные срабатывания из-за сети самого VPS: повтор перед открытием инцидента; при массовом падении помечаем «возможна проблема на стороне мониторинга».

### 6.7 Трекер сна

**Функционал:**
- **Быстрый ввод:**
  - утреннее уведомление «Как спал?»: время отбоя и подъёма предзаполнено из Health Connect или по вчерашнему шаблону, качество звёздами;
  - вечерняя кнопка «Ложусь спать» и утренняя «Проснулся» (в том числе с виджета);
- **Автоимпорт:**
  - из **Health Connect**: Samsung Health пишет туда сессии сна, если включить синхронизацию в Samsung Health;
  - Galaxy Watch и фитнес-браслеты дают стадии сна.
- **Экран:**
  - крупные цифры «среднее за 7 дней», «цель 8 ч», «регулярность отбоя»;
  - **heatmap 30 дней** в стиле ref2;
  - график длительности и времени отбоя;
  - «социальный джетлаг» (сдвиг в выходные).
- **Связь с продуктивностью:**
  - вечерний чек-ин DailyReview: продуктивность 1–10, энергия, настроение — одна строка;
  - автоматические метрики дня: выполненные задачи с весом приоритета, часы трекера, пары;
  - экран корреляций:
    - точечный график «сон ↔ продуктивность следующего дня»;
    - средняя продуктивность при сне < 6 ч, 6–7 ч, 7–8 ч, > 8 ч;
    - влияние времени отбоя;
    - коэффициент Спирмена с пометкой «мало данных», если меньше 21 дня;
  - инсайты дня для ИИ-агента темы «сон».

**Как реализуем:**
- SleepEntry, DailyReview и вычисляемые DailyMetrics из 5.6;
- Health Connect читается на Android через пакет **health** (carp-dk/carp-health-flutter): разрешение на чтение SleepSession, импорт при открытии приложения и фоном раз в сутки, дедупликация по внешнему id;
- известная проблема пакета (стадии сна пишутся отдельными сессиями) касается **записи**, а мы только читаем;
- при чтении склеиваем соседние сегменты с разрывом меньше 30 минут в одну сессию.

**API-эндпоинты:** через синхронизацию.

**Риски:**
- Samsung Health не всегда пишет в Health Connect без ручного включения — нужна инструкция;
- ручной ввод забывают: помогают напоминание и виджет;
- корреляция не причинность: формулировки в UI аккуратные.

**Референсы:** документация Samsung Developer «Managing Sleep Data with Samsung Health and Health Connect»; **Sleep as Android** (UX); **openwearables** (the-momentum/open_wearables_health_sdk) — фоновая синхронизация Health Connect во Flutter.

## 7. Уведомления

### 7.1 Локальные уведомления (на устройстве, работают офлайн)

**Источник:** локальная БД. Напоминания о событиях, задачах, парах, кредитках, долгах, сне, вечернем чек-ине и забытом таймере **вычисляются на устройстве**. Сервер для них не нужен, поэтому они работают без сети.

**Android:**
- `flutter_local_notifications` с точным планированием (zonedSchedule) плюс разрешения на точные будильники и на показ уведомлений. Для sideload-приложения календарного типа это допустимо;
- планируется горизонт 14 дней, но не больше ~400 уведомлений. Лимит Android на запланированные тревоги соблюдается: дальние ставятся по мере приближения;
- перепланирование при старте, после синхронизации, после перезагрузки устройства и периодически через WorkManager;
- **каналы:** «Напоминания задач», «Пары», «Финансы», «Трекер времени» (постоянное уведомление), «Сон»;
- **действия прямо в уведомлении:** «Выполнено», «Отложить 15 минут», «Был / Пропустил» для пар;
- обязательный онбординг-шаг: исключить приложение из оптимизации батареи Samsung («Приложения без ограничений»), иначе One UI откладывает будильники и убивает слушатель уведомлений.

**Windows:**
- toast-уведомления через `flutter_local_notifications` (реализация для Windows) или `local_notifier`;
- у Windows-реализации нет повторяющихся уведомлений, а отмена и список активных работают только в **MSIX**. Поэтому приложение упаковывается в MSIX и планирует уведомления само: внутренний таймер плюс перепланирование;
- приложение живёт в **трее** (`tray_manager`), автозапуск при входе в Windows, закрытие окна сворачивает в трей. Если приложение закрыто совсем, уведомления на ПК не приходят. Это приемлемо: телефон остаётся основным каналом.

**Дубли между устройствами:** напоминание срабатывает на обоих устройствах. Отметка «выполнено» на одном после синхронизации снимает уведомление на другом (перепланирование после pull).

### 7.2 Telegram

**Что уходит в Telegram:**
- алерты мониторинга, инциденты, восстановления;
- отчёты о бэкапах и сами файлы;
- ежедневный утренний дайджест (опционально): задачи и пары на сегодня, просроченные, ожидаемые платежи, статус серверов, сон за ночь;
- критичные финансовые напоминания: платёж по кредитке завтра.

**Бот — только для одного пользователя:** сообщения принимаются только из `TELEGRAM_CHAT_ID`, остальное игнорируется.

**Команды (позже):**
- «/task текст» — создать задачу во «Входящих»;
- «/status» — сводка серверов;
- «/spent 500 кофе» — быстрая трата.

Запись идёт на сервер, на устройства приходит через синхронизацию.

**Правила:** антиспам и очередь с ограничением скорости (6.6.4). Темы супергруппы разделяют алерты, бэкапы и дайджест.

### 7.3 Push с сервера на телефон (не обязательно)

Для событий, которые рождаются на сервере (новые операции из ZenMoney, инцидент), Telegram покрывает потребность. Если понадобится нативный push:
- **FCM** — на Samsung с Google-сервисами работает, но это зависимость от Google;
- **self-hosted ntfy** (binwiederhier/ntfy) по стандарту UnifiedPush — без Google.

Решение откладываем до фазы полировки.

## 8. Безопасность

**Авторизация (однопользовательская, но строгая):**
- один аккаунт владельца: пароль (хеш **Argon2id**) плюс **TOTP** (2FA) при входе нового устройства;
- после входа устройство получает **refresh-токен** (длинный, со ротацией и детектом повторного использования) и короткоживущий access-токен (~15 минут);
- refresh-токен хранится в защищённом хранилище ОС: Android Keystore и Windows Credential Manager / DPAPI через `flutter_secure_storage`;
- экран «Устройства» с отзывом; отзыв удаляет refresh-токены и блокирует синхронизацию устройства;
- защита от перебора: ограничение попыток входа по IP и глобально, задержки, алерт в Telegram о входе с нового устройства;
- **локальная блокировка приложения** (опционально): PIN или биометрия через `local_auth` при открытии и после N минут в фоне; отдельно для раздела «Финансы».

**Секреты:**
- только в переменных окружения на VPS: `.env` с правами 600 вне репозитория или Docker secrets;
- в репозитории — только `.env.example` с **именами** без значений: `DATABASE_URL`, `APP_SECRET_KEY` (подпись токенов), `APP_ENCRYPTION_KEY` (шифрование секретов в БД, например токена ZenMoney), `POLZA_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `HEALTHCHECKS_PING_URL`, `BACKUP_S3_*`, `BACKUP_AGE_RECIPIENT`, `GLITCHTIP_DSN`;
- в CI — **gitleaks** на каждый push;
- токен ZenMoney хранится в БД в зашифрованном виде (AES-GCM, ключ из `APP_ENCRYPTION_KEY`), в логи не попадает;
- клиенты не получают серверных секретов никогда. Ключ polza.ai используется только api.

**Данные на устройстве:**
- локальная БД целиком зашифрована **SQLCipher**. Ключ — случайные 256 бит, сгенерированные при первом запуске и хранимые в Keystore или DPAPI;
- на Android файлы БД исключены из облачного автобэкапа;
- FLAG_SECURE на экранах финансов (скриншоты и превью в списке задач) — опционально;
- сырые тексты банковских уведомлений хранятся только локально, 30 дней.

**Сервер и сеть:**
- наружу открыты только 80 и 443 (Caddy) и SSH (только ключи, нестандартный порт, fail2ban);
- PostgreSQL только во внутренней Docker-сети;
- контейнеры запускаются не от root, образы фиксируются по digest, автообновления безопасности ОС включены;
- HSTS, CORS не нужен (нативные клиенты), лимиты размера тел запросов;
- агенты: исходящее соединение, токен на каждый агент, allow-list команд, socket-proxy;
- webhook Telegram защищён секретным путём и проверкой secret_token.

**Бэкапы:**
- шифрование age: на серверах только публичный ключ;
- off-site копия в S3 у другого провайдера, ключи S3 с правами только на запись в префикс (без удаления, если провайдер позволяет — object lock или версионирование);
- дамп собственной БД My Tasker ежедневно;
- ежемесячное тестовое восстановление.

**ИИ и приватность:**
- флаг «чувствительное» в пресетах контекста;
- по умолчанию операции по счетам и суммы долгов по людям не уходят в облако, только агрегаты; пользователь может разрешить;
- локальная модель для чувствительных вопросов;
- логи api не содержат текстов сообщений чата, только метаданные: модель, токены, стоимость.

## 9. Развёртывание, CI/CD, наблюдаемость

**Состав docker compose на VPS:**
- `caddy`;
- `api`;
- `worker` (тот же образ, другая команда запуска);
- `migrate` (одноразовый запуск миграций перед стартом api и worker);
- `postgres` (том на диске);
- опционально: `telegram-bot-api` (локальный Bot API server), `glitchtip` с зависимостями (или внешний Sentry-совместимый сервис), `healthchecks` — только если нет второго сервера (лучше вынести).

Ориентир по ресурсам: без GlitchTip ~0,5–1 ГБ RAM и 1 vCPU. Если VPS пользователя сам мониторится, на нём ставится и агент.

**CI (GitHub Actions):**
- **backend:** линтер и типизация (ruff, mypy), тесты pytest на PostgreSQL в сервис-контейнере (включая property-based тесты синхронизации и общие тестовые векторы), сборка образа и публикация в GHCR с тегом версии;
- **agent:** go vet и тесты, сборка статических бинарников linux/amd64 и arm64, образ в GHCR;
- **app:** flutter analyze, unit- и widget-тесты (доменные расчёты, развёртка RRULE, парсеры уведомлений на обезличенных примерах, конструктор контекста), golden-тесты ключевых экранов;
- **сборка APK** (release, подпись ключом из секретов CI);
- **сборка MSIX** на Windows-раннере. Нужен сертификат подписи: самоподписанный, установленный на ПК пользователя, либо покупной;
- **секреты:** gitleaks.

**CD:**
- **бэкенд:** по тегу релиза деплой по SSH: подтянуть образы, прогнать миграции, перезапустить api и worker. Проверка health-эндпоинта; откат на предыдущий тег при неудаче;
- **миграции** Alembic только «вперёд» и совместимые назад в пределах одной версии: сначала добавить колонку, потом использовать. Старые клиенты продолжают синхронизироваться;
- **обновления клиентов:** api отдаёт эндпоинт «последняя версия» (номер, changelog, ссылка на APK или MSIX из GitHub Releases или со своего хранилища). Android-клиент предлагает обновиться и запускает установщик пакета (разрешение «установка из этого источника»). Windows — MSIX с App Installer. Альтернатива для Android — **Obtainium**, который отслеживает GitHub Releases.

**Наблюдаемость:**
- **логи:** structlog в JSON с request_id и device_id, ротация Docker-логов;
- **ошибки:** GlitchTip (совместим с Sentry SDK) — sentry-sdk в api и worker, sentry_flutter в клиентах (без персональных данных в событиях);
- **метрики:** внутренний эндпоинт Prometheus (закрыт снаружи) — задержки, размер outbox по устройствам, длительность цикла проверок, очередь Telegram. На старте хватает вкладки «Самопроверка»;
- **health-эндпоинты:** жив ли процесс, готов ли (БД доступна, миграции применены);
- **самомониторинг:** собственный api — один из сервисов модуля «Серверы», плюс внешний healthchecks.

**Окружения:** локальная разработка (compose с Postgres, Flutter против локального api) и прод. Staging не нужен: один пользователь; перед релизом — прогон на копии прод-БД из бэкапа.

**Что делать первым:** фаза 0, затем 1. Синхронизация — фундамент: ошибки в ней дороже всего исправлять потом.

**Порядок 2 → 3 → 4** соответствует приоритетам заказчика:
- календарь — главный экран;
- работа — самый важный модуль;
- финансы опираются на работу.

**Фазы 5–6** почти полностью серверные и могут идти **параллельно** с 2–4, если над проектом работает больше одного исполнителя или субагента.

Итого MVP (фазы 0–4) ≈ 9–13 недель; полный объём брифа (0–10) ≈ 18–26 недель.

## 11. Риски и открытые вопросы к заказчику

### 11.1 Основные риски

| Риск | Вероятность / влияние | Митигация |
|---|---|---|
| Ошибки собственной синхронизации (потеря или дублирование данных) | Средняя / высокое | Property-based тесты, журнал конфликтов, мягкое удаление, ежедневные бэкапы БД. План Б — PowerSync. |
| Локальная LLM на A55 медленная или плохо говорит по-русски | Средняя / среднее | Спайк в фазе 0; две ветки (Gemma 4 E2B / LiteRT-LM и Qwen3.5 / llama.cpp); урезанный офлайн-сценарий (создание задач плюс короткие ответы). |
| GPU Exynos в LiteRT-LM не работает | Подтверждено | Только CPU; следим за issue #2611. |
| ZenMoney API изменят или закроют; синхронизация ВТБ ломается | Средняя / среднее | Уведомления, выписки и ручной ввод как независимые источники; маппинг изолирован в одном адаптере. |
| Банки меняют тексты пушей | Высокая / низкое | Парсеры покрыты тестами на реальных текстах; нераспознанное уходит в «требует проверки»; быстрые правки парсера. |
| One UI убивает фоновые сервисы и откладывает напоминания | Высокая / среднее | Онбординг с инструкцией исключения из оптимизации, WorkManager, проверка «уведомления работают» в самопроверке клиента. |
| VPS упал — нет мониторинга, синхронизации и чата | Низкая / среднее | Внешний healthchecks, клиенты работают офлайн, агенты-сторожа. |
| Telegram теряет бэкапы или ограничивает бота | Низкая / высокое | S3 как основное off-site хранилище, Telegram — дополнительное. |
| Модели в polza.ai меняются, id «5 sol» или «5 nano» исчезают | Средняя / низкое | Живой каталог и проверка избранного при старте. |
| Утечка данных в облачную LLM | Средняя / среднее | Флаг чувствительности, агрегаты вместо сырых операций, локальный режим. |
| Раздутие объёма (7 модулей + серверы) | Высокая / высокое | Строгие фазы, MVP 0–4, каждый модуль полезен сам по себе. |
